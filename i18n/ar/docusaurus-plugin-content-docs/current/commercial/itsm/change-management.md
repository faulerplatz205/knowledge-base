# إدارة التغيير

## نظرة عامة {/*#overview*/}

**إدارة التغيير** (Change Management) هي المستوى الثالث في ITSM. وتتولى الموافقة على التغييرات في نظام تقنية المعلومات وتخطيطها.

**الهدف:** ضمان ألا تُجرى التغييرات على عجل ودون رؤية شاملة. يقيّم متخصصون من مجالات مختلفة المخاطر لتفادي الأخطاء اللاحقة. ولا يتجاوز هذه العملية سوى التغييرات الطارئة، لأن الأولوية القصوى فيها هي استعادة النظام بأسرع ما يمكن.

## طلب التغيير (RFC) {/*#request-for-change-rfc*/}

قبل تنفيذ التغيير يُنشأ **طلب تغيير** (Request for Change, RFC)، عادة من [إدارة المشكلات](./problem-management.md). وطلب التغيير هو طلب رسمي لتنفيذ تغيير. ويتضمن:

- وصف التغيير
- سبب التغيير
- الجدول الزمني
- الأولوية
- الآثار الجانبية المتوقعة
- التكاليف المقدرة

يصف طلب التغيير **ما** يجب فعله، لا **كيف**، إذ يُحدَّد الكيف في عملية إدارة التغيير.

## تحديد أولوية طلبات التغيير {/*#rfc-prioritisation*/}

تُحدَّد أولوية طلبات التغيير الواردة وفق **الإلحاح** و**الأثر**:

### مستويات الإلحاح {/*#urgency-levels*/}

| المستوى                  | الوصف               |
| ---------------------- | ------------------------- |
| **أولوية منخفضة (Priority Low)**       | مرغوب فيه لكنه غير ملح  |
| **أولوية متوسطة (Priority Middle)**    | ضروري لكنه غير ملح  |
| **أولوية عالية (Priority High)**      | يلزم إجراء فوري |
| **أولوية فورية (Priority Immediate)** | يلزم إجراء فوري |

### مستويات الأثر {/*#impact-levels*/}

| المستوى             | الوصف                                  | مثال                |
| ----------------- | -------------------------------------------- | ---------------------- |
| **أثر منخفض (Effect Low)**    | أثر ضئيل في خدمات تقنية المعلومات وجهد قليل | استبدال حاسوب واحد        |
| **أثر متوسط (Effect Middle)** | أثر معتدل وجهد متزايد            | ترقية نظام التشغيل لجميع الحواسيب  |
| **أثر مرتفع (Effect High)**   | أثر مرتفع في خدمات تقنية المعلومات وجهد كبير جدًا | تعطل كامل للخادم |

## أنواع التغيير {/*#change-types*/}

| النوع                                  | الخصائص                                                                               | الموافقة             |
| ------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------- |
| **التغيير القياسي (Standard Change)**                   | تغييرات روتينية معتمدة مسبقًا من كتالوج، منخفضة المخاطر، ومصرَّح بها تلقائيًا             | مدير التغيير وحده |
| **التغيير العادي (Normal Change)**                     | مخاطر متوسطة وتعقيد متوسط وإلحاح معتدل، ويتطلب تقييم الخبراء              | CAB + CIO            |
| **التغيير الطارئ (Emergency Change / Notfall Change)** | إلحاح مرتفع ويلزم حل قصير الأمد، ويُتجاوز مسار الموافقة المنظم لكسب السرعة | EC / ECAB            |

## جهات الموافقة {/*#approval-bodies*/}

| الجهة                                | الوصف                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **مدير التغيير (Change Manager, CM)**             | يقرر منفردًا في التغييرات محدودة النطاق (التغيير القياسي)، ومسؤول عن إدارة الوقت والمراقبة                           |
| **المجلس الاستشاري للتغيير (Change Advisory Board, CAB)**     | لجنة خبراء من مجالات عمل متنوعة، تقرر في التغييرات متوسطة النطاق (التغيير العادي)                                  |
| **رئيس قسم المعلومات (Chief Information Officer, CIO)** | شخص على مستوى المجلس/الإدارة يمثل مصالح تقنية المعلومات، ويشارك في القرارات ذات النطاق التجاري الكبير (مثل تدريب الموظفين) |
| **لجنة الطوارئ (Emergency Committee, EC / ECAB)** | فريق خبراء صغير ذو صلاحيات واسعة للقرارات العاجلة، ويتولى التغييرات الطارئة                                           |

## تخطيط التغيير {/*#change-planning*/}

### جدول التغييرات المستقبلية (Forward Schedule of Change, FSC) {/*#forward-schedule-of-change-fsc*/}

تقويم تُوثَّق فيه جميع التغييرات الطويلة الأمد المخطط لها. وينبغي أن يهدف التخطيط دائمًا إلى تقليل فترات التوقف.

### قاعدة بيانات إدارة التهيئة (Configuration Management Database, CMDB) {/*#configuration-management-database-cmdb*/}

قاعدة بيانات مركزية تُخزَّن فيها جميع عناصر التهيئة (CI) مع مواصفاتها وأرقام تراخيصها. وتُوثَّق فيها مركزيًا جميع التغييرات على عناصر التهيئة.

مدير التغيير (CM) مسؤول عن التنفيذ المنضبط زمنيًا للتغييرات ومراقبتها.

## الموافقة على التغييرات وتنفيذها {/*#approving-and-executing-changes*/}

الفصل بين الموافقة/التصريح من جهة والتخطيط/التنفيذ من جهة أخرى مقصود في ITSM. وهذا يضمن:

- قرارات مستدامة يتخذها متخصصون يراعون النظام ككل
- منع إصلاح الأخطاء بردود الفعل دون مراعاة السياق الأوسع
- مساءلة موثَّقة

## إغلاق التغيير (PIR) {/*#closing-a-change-pir*/}

بعد تنفيذ التغيير، توثق إدارة التغيير جميع الإجراءات والسبب الجذري للإخفاق في CMDB وKEDB للرجوع إليها مستقبلًا.

يوثق **مراجعة ما بعد التنفيذ** (Post Implementation Review, PIR) جميع النقاط الرئيسية للتغيير:

- نتائج الاختبار
- تفاصيل التنفيذ
- التغييرات مقارنة بحالة النظام السابقة
- التكاليف والجهد
- الطوابع الزمنية

**هدف PIR:** دفع التحسين المستمر عبر مراجعة التغييرات المنجزة وتقييمها.

## ملخص أنواع التغيير والموافقة {/*#change-types-and-approval-summary*/}

| نوع التغيير      | جهة الموافقة  | الخاصية الرئيسية                         |
| ---------------- | -------------- | ------------------------------------------ |
| تغيير قياسي  | مدير التغيير | قائم على كتالوج، معتمد مسبقًا، منخفض المخاطر    |
| تغيير عادي    | CAB + CIO      | مخاطر متوسطة، وCAB مشارك                  |
| تغيير طارئ | EC / ECAB      | أقصى سرعة، ويُتجاوز المسار المنظم |
