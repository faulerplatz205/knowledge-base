# مخطط آلة الحالة

## نظرة عامة {/*#overview*/}

مخطط آلة الحالة هو مخطط UML **سلوكي**. يصف دورة حياة كائن *واحد* أو مكوِّن أو نظام: الحالات التي يمكن أن يكون فيها، والأحداث التي تنقله من حالة إلى التالية، وما يحدث في الطريق.

التطبيقات النموذجية:

- حالة الطلب في نظام متجر (`New`، `Paid`، `Shipped`، `Delivered`، `Cancelled`)
- معالجة الجلسات أو تسجيل الدخول (`Anonymous`، `Authenticated`، `Locked`، `Expired`)
- حالات الأجهزة والاتصالات (`Off`، `Booting`، `Ready`، `Error`)
- منطق البروتوكولات والمحللات (parsers)، حيث يُفسَّر الحرف التالي تفسيرًا مختلفًا بحسب الحالة
- السلوك الداخلي لصنف لا يُسمح باستدعاء دواله إلا في حالات معينة

## الترميز {/*#notation*/}

| العنصر                | الترميز                                               | المعنى                                                                   |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| حالة ابتدائية زائفة   | دائرة ممتلئة `●`                                      | حيث تبدأ دورة الحياة، واحدة بالضبط لكل منطقة                             |
| حالة                  | مستطيل بزوايا مستديرة مع اسم                          | وضع ينتظر فيه الكائن، يُسمّى بصفة أو باسم                                |
| انتقال                | سهم من حالة إلى أخرى                                  | تغير حالة، يُوسَم `trigger [guard] / effect`، وكل جزء اختياري            |
| مُشغِّل (Trigger)     | اسم الحدث على الانتقال                                | الحدث الذي يتيح الانتقال، مثل `cancel`، `timeout`                        |
| انتقال الإكمال        | انتقال بلا مُشغِّل                                    | يُنفَّذ حالما ينتهي سلوك الحالة المصدر                                   |
| حارس (Guard)          | `[condition]` على الانتقال                             | شرط منطقي، لا يُنفَّذ الانتقال إلا إذا كان تقييمه صحيحًا                 |
| تأثير (Effect)        | `/ action` على الانتقال                                 | إجراء يُنفَّذ أثناء الانتقال، ويجب ألا يحجب                              |
| انتقال ذاتي           | سهم يغادر الحالة نفسها ويعود إليها                    | تُغادَر الحالة ويُدخَل إليها من جديد، ويُنفَّذ `exit` و`entry`           |
| انتقال داخلي          | `trigger / effect` داخل مربع الحالة                    | رد فعل دون تغيير الحالة، ولا يُنفَّذ `exit` ولا `entry` **أبدًا**        |
| نشاط الدخول (Entry)   | `entry / action` داخل مربع الحالة                       | يُنفَّذ كلما دُخلت الحالة، بصرف النظر عن الانتقال المستخدم               |
| نشاط do               | `do / activity` داخل مربع الحالة                        | يُنفَّذ باستمرار ما دامت الحالة نشطة، ويمكن مقاطعته                      |
| نشاط الخروج (Exit)    | `exit / action` داخل مربع الحالة                        | يُنفَّذ كلما غُادرت الحالة، بصرف النظر عن الانتقال المستخدم              |
| حالة مركبة            | مربع حالة يحتوي حالات أخرى                            | حالة مفصَّلة إلى حالات فرعية                                             |
| منطقة (Region)        | جزء من حالة مركبة، يُفصل بخط متقطع                    | حالات فرعية نشطة في الوقت نفسه                                           |
| اختيار (Choice)       | معيّن على انتقال                                      | تفرع يُقيَّم بعد التأثير، وتحمل الانتقالات الصادرة حراسًا                |
| تاريخ ضحل             | دائرة تحتوي `H`                                       | عند إعادة الدخول تُستأنف الحالة الفرعية التي كانت نشطة آخر مرة في تلك الحالة المركبة |
| تاريخ عميق            | دائرة تحتوي `H*`                                      | يستأنف آخر حالة فرعية نشطة بما في ذلك كل المستويات المتداخلة             |
| حالة نهائية           | دائرة ممتلئة داخل حلقة `◉`                            | تنتهي دورة الحياة هنا، ولا يقبل الكائن أحداثًا أخرى                      |

قواعد التسمية التي تُبقي المخطط مقروءًا:

- تصف الحالات شرطًا لا نشاطًا: `Paid`، `Waiting for payment`، وليس `Pay`
- تُسمّى المُشغِّلات باسم الحدث لا باسم الدالة التي تعالجه: `cancel`، وليس `handleCancel`
- تُسمّى التأثيرات والأنشطة الداخلية عمليات مع أقواس: `/ refundPayment()`

## اللبنات الأساسية {/*#building-blocks*/}

### الحالات والانتقالات {/*#states-and-transitions*/}

```text
              ●
              │
              ▼
   ╭────────────────────────╮
   │         Idle           │
   ╰────────────────────────╯
              │
              │ coinInserted [amount >= price] / unlock()
              ▼
   ╭────────────────────────╮
   │        Ready           │
   ╰────────────────────────╯
              │
              │ productSelected / dispense()
              ▼
              ◉
```

القراءة بوصفها جملة: *في الحالة `Idle`، عندما يقع الحدث `coinInserted` ويتحقق الشرط `amount >= price`، يُنفَّذ `unlock()` وتنتقل الآلة إلى `Ready`*. وإذا وقع الحدث لكن الحارس كان خاطئًا، يُهمَل الحدث ولا تتغير الحالة.

### الانتقال الذاتي {/*#self-transition*/}

بعد انتقال ذاتي يكون الكائن في الحالة نفسها التي كان فيها. وفي الطريق تُغادَر الحالة ويُدخَل إليها من جديد، فيُنفَّذ `exit` و`entry` ويُعاد تشغيل نشاط `do`.

```text
        ┌───────────────────────────────────┐
        │   digitPressed / appendDigit()    │
        │                                   │
        │   ╭───────────────────────────╮   │
        └──►│        Collecting         │───┘
            ╰───────────────────────────╯
```

وإذا لم يكن مرغوبًا في إعادة تشغيل `entry` و`do` و`exit`، يُستخدم **انتقال داخلي** بدلًا من ذلك. يُكتب داخل مربع الحالة ويُبقي الحالة نشطة:

```text
╭───────────────────────────────────────────╮
│               Collecting                  │
├───────────────────────────────────────────┤
│ digitPressed / appendDigit()              │
╰───────────────────────────────────────────╯
```

مثلًا، المهلة الزمنية المنفذة بصيغة `entry / startTimer()` تُعاد تهيئتها بانتقال ذاتي وتظل تعمل مع انتقال داخلي.

### الأنشطة الداخلية {/*#internal-activities*/}

ثلاث كلمات مفتاحية تصف سلوكًا يخص الحالة نفسها لا الانتقال:

- `entry / action`: يُنفَّذ مرة واحدة عند كل دخول، قبل أي نشاط do
- `do / activity`: يُنفَّذ ما دامت الحالة نشطة، وقد يعمل مدة طويلة وقد يقاطعه انتقال صادر
- `exit / action`: يُنفَّذ مرة واحدة عند كل خروج، بعد انتهاء نشاط do أو إيقافه

```text
╭───────────────────────────────────────────╮
│                 Heating                   │
├───────────────────────────────────────────┤
│ entry / switchHeaterOn()                  │
│ do / measureTemperature()                 │
│ exit / switchHeaterOff()                  │
╰───────────────────────────────────────────╯
```

ترتيب تغيير الحالة هو دائمًا: `exit` للحالة المصدر، ثم تأثير الانتقال، ثم `entry` للحالة الهدف.

إن وضع إجراء في `entry` بدلًا من وضعه على كل انتقال وارد يزيل التكرار ويضمن ألا يُنسى الإجراء عند إضافة انتقال جديد إلى تلك الحالة لاحقًا.

### الحالات المركبة {/*#composite-states*/}

تحتوي الحالة المركبة آلة حالة خاصة بها. وهي تُبقي المخططات صغيرة وتتيح رسم انتقال واحد مرة واحدة لمجموعة كاملة من الحالات الفرعية.

```text
╭────────────────────────────────────────────────────────╮
│ Active                                                 │
│                                                        │
│    ●                                                   │
│    │                                                   │
│    ▼                                                   │
│  ╭───────────────────╮  connected  ╭───────────────────╮
│  │     Dialling      │────────────►│    Talking        │
│  ╰───────────────────╯             ╰───────────────────╯
│                                                        │
╰────────────────────────────────────────────────────────╯
              │
              │ hangUp
              ▼
   ╭───────────────────╮
   │       Idle        │
   ╰───────────────────╯
```

يبدأ الانتقال `hangUp` عند *حدّ* الحالة المركبة، ولذلك ينطبق على `Dialling` و`Talking` على السواء.

قواعد جديرة بالتذكر:

- تحتاج الحالة المركبة حالة ابتدائية زائفة خاصة بها، وإلا لم يكن معروفًا أي حالة فرعية تصبح نشطة
- تكون حالة فرعية واحدة بالضبط نشطة في كل وقت لكل منطقة، مع الحالة المركبة التي تحتويها
- يمكن لانتقال أن يشير مباشرةً إلى حالة فرعية، فيتجاوز الحالة الابتدائية الزائفة
- تنهي الحالة النهائية داخل حالة مركبة تلك الآلة الداخلية، فتُطلق عندئذ انتقال الإكمال الصادر من الحالة المركبة

### المناطق والحالات المتوازية {/*#regions-and-parallel-states*/}

يمكن تقسيم حالة مركبة إلى **مناطق** بخط متقطع. لكل منطقة حالتها الابتدائية الزائفة وحالاتها الفرعية وانتقالاتها. وما دامت الحالة المركبة نشطة، تكون حالة فرعية واحدة نشطة في كل منطقة في الوقت نفسه. وهذا ينمذج جوانب مستقلة لكائن واحد، كالصوت والفيديو في تسجيل.

```text
╭──────────────────────────────────────────────────────────╮
│ Recording                                                │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮   muteAudio   ╭───────────────╮       │
│  │ AudioRunning  │──────────────►│  AudioMuted   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮  pauseVideo   ╭───────────────╮       │
│  │ VideoRunning  │──────────────►│ VideoPaused   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
╰──────────────────────────────────────────────────────────╯
```

يُعرض الحدث على كل منطقة. وقد يُطلق انتقالًا في منطقة واحدة أو في عدة مناطق أو في لا واحدة.

### حالة التاريخ {/*#history-state*/}

تجيب حالة التاريخ عن السؤال *أين تستأنف الآلة بعد انقطاع*. ومن دونها يبدأ دخول حالة مركبة من جديد دائمًا عند حالتها الابتدائية الزائفة.

```text
              ╭──────────────────────────────────────────╮
              │ Playing                                  │
   resume     │                                          │
 ┌───────────►│   (H)                                    │
 │            │    │                                     │
 │            │    ▼                                     │
 │            │  ╭───────────╮        ╭───────────╮      │
 │            │  │  Track 1  │───────►│  Track 2  │      │
 │            │  ╰───────────╯        ╰───────────╯      │
 │            ╰──────────────────────────────────────────╯
 │                           │ pause
 │            ╭──────────────▼───────────╮
 └────────────│          Paused          │
              ╰──────────────────────────╯
```

يستعيد التاريخ الضحل `(H)` الحالة الفرعية التي كانت نشطة آخر مرة على هذا المستوى. ويستعيد التاريخ العميق `(H*)` آخر تشكيلة بما فيها كل المستويات المتداخلة. وإذا لم تُدخَل الحالة المركبة من قبل، يرتد الانتقال إلى حالة التاريخ إلى الحالة الابتدائية الزائفة.

## جدول انتقال الحالات {/*#state-transition-table*/}

يمكن كذلك كتابة مخطط آلة الحالة في صورة **جدول انتقال حالات**. ويسهل فحص اكتمال الجدول مقارنةً بالمخطط، لأن التوليفات المفقودة من الحالة والحدث تبرز عند تجميع الصفوف بحسب الحالة.

| الحالة الحالية | الحدث             | الحارس            | التأثير                | الحالة التالية |
| -------------- | ----------------- | ----------------- | ---------------------- | -------------- |
| `New`          | `itemAdded`       | –                 | `recalculateTotal()`   | –              |
| `New`          | `paymentReceived` | –                 | `capturePayment()`     | `Paid`         |
| `New`          | `cancel`          | –                 | `releaseReservation()` | `Cancelled`    |
| `Paid`         | `dispatched`      | `allItemsInStock` | `sendTrackingMail()`   | `Shipped`      |
| `Paid`         | `cancel`          | –                 | `refundPayment()`      | `Cancelled`    |
| `Shipped`      | `delivered`       | –                 | –                      | `Delivered`    |

التوليفة التي لا ترد في الجدول لا تُطلق أي انتقال. ويُهمَل الحدث دون أثر.

الصف الذي يكون فيه عمود *الحالة التالية* فارغًا وعمود *التأثير* ممتلئًا يصف انتقالًا داخليًا. والصف الذي تتطابق فيه الحالة الحالية والحالة التالية يصف انتقالًا ذاتيًا.

## مثال: حالة الطلب {/*#example-order-status*/}

دورة حياة طلب في نظام متجر، من الإنشاء حتى التسليم أو الإلغاء.

```text
                          ●
                          │
                          ▼
                ╭────────────────────────╮
                │          New           │
                │ entry / reserveItems() │
                ╰────────────────────────╯
                     │              │
    paymentReceived  │              │ cancel
    / capturePayment()              │ / releaseReservation()
         ┌───────────┘              └────────────┐
         ▼                                       │
╭────────────────────────╮                       │
│          Paid          │──────────────────────►┤
╰────────────────────────╯  cancel               │
         │                  / refundPayment()    │
         │ dispatched [allItemsInStock]          │
         │ / sendTrackingMail()                  ▼
         ▼                          ╭────────────────────────╮
╭────────────────────────╮          │       Cancelled        │
│        Shipped         │          ╰────────────────────────╯
╰────────────────────────╯                       │
         │                                       │
         │ delivered                             │
         ▼                                       │
╭────────────────────────╮                       │
│       Delivered        │                       │
╰────────────────────────╯                       │
         │                                       │
         └───────────────────┐   ┌───────────────┘
                             ▼   ▼
                             ◉
```

ما يُظهره هذا المثال:

- يقع الاسترداد على الانتقال `Paid => Cancelled` و**ليس** نشاط `entry` للحالة `Cancelled`، لأن الطلب الملغى من `New` لم يُدفع قط.
- يحمل `dispatched` حارسًا. وإذا كان المخزون ناقصًا، يبقى الطلب في `Paid`.
- ليس لدى `Shipped` انتقال من أجل `cancel`. وقاعدة العمل *لا يمكن إلغاء طلب أُرسل* يُعبَّر عنها بغياب الانتقال.

عند التنفيذ في الشيفرة تصبح كل حالة قيمة في enumeration، ويصبح الجدول `switch` على الحالة والحدث. وكل ما لا يرد في الجدول يقع في الفرع الافتراضي ويُرفَض. وبذلك يكون تغيير الحالة غير الصالح مستحيلًا بالبناء.

## التمييز عن مخطط النشاط {/*#delimitation-from-the-activity-diagram*/}

| الجانب           | مخطط آلة الحالة                  | [مخطط النشاط](./activity-diagram.md)            |
| ---------------- | -------------------------------- | ----------------------------------------------- |
| العقدة           | **حالة**، الكائن ينتظر           | **فعل**، يجري عمل                               |
| التسمية          | صفة أو اسم: `Paid`               | فعل + مفعول به: `Capture payment`                |
| السهم            | يُطلقه **حدث**                   | يُنفَّذ عندما **ينتهي** الفعل السابق            |
| النطاق           | دورة حياة كائن واحد              | تنفيذ عملية واحدة، ربما عبر عدة فاعلين          |
| التفرع           | حراس على الانتقالات الصادرة      | عقدة قرار مع تدفقات ذات حراس                    |
| التوازي          | مناطق داخل حالة مركبة            | Fork وjoin                                      |
| السؤال النموذجي  | *في أي حالة الطلب؟*              | *ما الخطوة التالية؟*                            |

إذا لم يمكن وسم السهم إلا بشيء مثل *بعد ذلك*، فمخطط النشاط هو الاختيار الصحيح. وإذا احتاج السهم إلى اسم مثل `cancel` أو `timeout` أو `paymentReceived`، فمخطط آلة الحالة هو المناسب.

## الأخطاء الشائعة {/*#common-mistakes*/}

1. **أنشطة مستخدمة بوصفها أسماء حالات:** `Pay` فعل ومكانه مخطط النشاط. أما الحالة فهي `Paid` أو `Waiting for payment`.
2. **انتقالات بلا مُشغِّل:** السهم بين حالتين دون حدث هو انتقال إكمال. ويُنفَّذ حالما تنهي الحالة المصدر سلوكها.
3. **حراس متداخلة:** إذا أمكن أن يكون حارسا انتقالين لهما المُشغِّل نفسه صحيحين معًا، فالسلوك غير معرَّف. ويجب أن يستبعد الحارسان أحدهما الآخر.
4. **الخلط بين الحارس والمُشغِّل:** `[cancel]` شرط وليس حدثًا. و`cancel [orderNotShipped]` يفصل بينهما فصلًا صحيحًا.
5. **غياب الحالة الابتدائية الزائفة:** من دونها تكون حالة البداية غير معرَّفة. ويحتاج كل مخطط وكل منطقة إلى واحدة بالضبط.
6. **حالات لا يمكن الوصول إليها أو حالات مسدودة:** لا تُبلَغ الحالة التي لا انتقال وارد إليها أبدًا. والحالة التي لا انتقال صادرًا منها وليست حالة نهائية تحبس الكائن.
7. **انتقال ذاتي حيث يُقصد انتقال داخلي:** يعيد الانتقال الذاتي تشغيل `entry` و`do` و`exit`. ويُعاد بذلك ضبط مؤقت بدأ في `entry`.
8. **انفجار الحالات:** يؤدي جمع جوانب مستقلة في مجموعة حالات مسطحة واحدة إلى تضاعف عدد الحالات. وتتجنب المناطق أو السمات الإضافية ذلك.
