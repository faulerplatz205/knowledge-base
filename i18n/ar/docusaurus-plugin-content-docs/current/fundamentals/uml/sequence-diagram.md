# مخطط التسلسل

## نظرة عامة {/*#overview*/}

مخطط التسلسل هو مخطط UML **سلوكي** وينتمي إلى مجموعة *مخططات التفاعل*. يبيّن أي شركاء التواصل يتبادلون أي رسائل، وبأي ترتيب يحدث ذلك. يُرتَّب الشركاء جنبًا إلى جنب ويجري الزمن من الأعلى إلى الأسفل.

التطبيقات النموذجية:

- تفصيل سيناريو واحد من [حالة استخدام](./use-case-diagram.md)، وعادةً المسار العادي مع استثناء واحد
- توثيق تعاون الكائنات أو المكونات لتنفيذ جزء واحد من الوظائف
- وصف بروتوكول بين أنظمة، كالعميل والخادم وقاعدة البيانات مثلًا
- مراجعة مسودة تصميم مقابل [مخطط الأصناف](./class-diagram.md) في الاتجاهين: الرسالة التي لا يقدمها أي صنف بوصفها عملية تكشف عملية مفقودة، وخط الحياة الذي لا تصل إليه أي رسالة يكشف صنفًا لا يمكن الوصول إليه

يبيّن مخطط التسلسل دائمًا تنفيذًا ملموسًا *واحدًا*. ويمكن التعبير عن البدائل والتكرارات بالأجزاء المركبة، لكن المخطط الذي يحاول تغطية كل الحالات دفعة واحدة يصبح غير مقروء. ولذلك تُفضَّل عدة مخططات صغيرة على مخطط واحد كبير.

## الترميز {/*#notation*/}

| العنصر                  | الترميز                                                | المعنى                                                         |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| الإطار                  | مستطيل بلسان خماسي يحمل `sd` مع اسم                  | حدود التفاعل واسمه                                             |
| رأس خط الحياة           | مستطيل مع `name : Class` أو `:Class` أو `name`      | شريك تواصل: كائن أو مكوِّن أو فاعل                             |
| خط الحياة               | خط رأسي متقطع أسفل الرأس                               | وجود ذلك الشريك عبر الزمن                                      |
| مواصفة التنفيذ          | مستطيل ضيق على خط الحياة (شريط التنشيط)                | الفترة التي يكون فيها الشريك نشطًا أو يعالج فيها استدعاءً      |
| رسالة متزامنة           | خط متصل، رأس سهم ممتلئ `──▶`                           | ينتظر المرسل حتى يصل الرد                                      |
| رسالة غير متزامنة       | خط متصل، رأس سهم مفتوح `──>`                           | يتابع المرسل فورًا دون انتظار                                  |
| رسالة رد                | خط متقطع، رأس سهم مفتوح `<- - -`                       | إعادة التحكم، ويمكن وسمها بالقيمة المرجعة                      |
| رسالة ذاتية             | سهم يغادر خط الحياة نفسه ويعود إليه                    | يستدعي الشريك إحدى عملياته الخاصة                              |
| رسالة إنشاء             | سهم متقطع بـ `«create»` على رأس خط حياة                 | يبدأ المستقبِل بالوجود أثناء التفاعل                           |
| حدوث التدمير            | علامة إكس `X` عند الطرف السفلي لخط الحياة               | يُدمَّر الكائن وينتهي خط الحياة هناك                           |
| جزء مركب                | مستطيل مع المعامل في الزاوية العلوية اليسرى            | بنية تحكم، مثل `alt` و`opt` و`loop` و`par`     |
| Operand                 | قسم من جزء، يُفصل بخط متقطع                            | حالة واحدة أو فرع واحد داخل الجزء                              |
| حارس (Guard)            | `[condition]` في بداية operand                          | الشرط الذي ينطبق بموجبه ذلك الـ operand                        |
| استخدام تفاعل           | جزء بالمعامل `ref`                                     | إحالة إلى تفاعل مرسوم في مخطط مستقل                            |
| ثابت الحالة             | `{condition}` على خط حياة                              | شرط يجب أن يتحقق عند تلك النقطة الزمنية                        |
| ملاحظة                  | مستطيل بزاوية مطوية على خط متقطع                       | تعليق بلا دلالة                                                |

قواعد التسمية التي تُبقي المخطط مقروءًا:

- تحمل الرسالة توقيع العملية المستدعاة، مثل `reserve(seatNo)`، وليس جملة مثل `the seat is reserved`
- يُوسَم الرد بالقيمة المرجعة، وليس باسم العملية مرة أخرى
- تُسمّى خطوط الحياة بأسماء كائنات، لا بأسماء أفعال: `:SeatRepository` شريك، و`Save seat` ليس شريكًا
- يُكتب الكائن المجهول بالصيغة `:Class`، والكائن المسمّى بالصيغة `seat : Seat`، والدور باسمه فقط

## اللبنات الأساسية {/*#building-blocks*/}

### خط الحياة ومواصفة التنفيذ والرد {/*#lifeline-execution-specification-and-reply*/}

تبدأ الرسالة من شريك إلى آخر مواصفةَ تنفيذ لدى المستقبِل، ويُنهيها الرد. وتناسب الرسالة المتزامنة استدعاءً يحتاج المستدعي إلى نتيجته قبل أن يتابع، مثل استدعاء method أو طلب HTTP يُنتظر ردّه.

```text
   :Client                  :AuthService
      │                           │
     ┌┴┐                          │
     │ │─── login(user, pw) ────▶┌┴┐
     │ │                         │ │
     │ │<- - - - - token - - - - └┬┘
     │ │                          │
     └┬┘                          │
      │                           │
```

يمكن حذف الرد إذا لم يحمل أي معلومة.

### الرسالة غير المتزامنة {/*#asynchronous-message*/}

تُسلَّم الرسالة غير المتزامنة ويتابع المرسل دون انتظار. وتناسب الأحداث والإشعارات والرسائل المرسلة إلى طابور والاستدعاءات التي تعمل في خيط (thread) منفصل ولا يحتاج المرسل فيها إلى نتيجة. وشريط المرسل مستقل عن شريط المستقبِل وقد ينتهي قبله.

```text
:OrderService                   :MailService
      │                               │
     ┌┴┐                              │
     │ │──── sendMail(order) ───────>┌┴┐
     └┬┘                             │ │
      │                              │ │
      │                              └┬┘
      │                               │
```

### الرسالة الذاتية {/*#self-message*/}

الرسالة الذاتية سهم يغادر خط حياة ويعود إلى خط الحياة نفسه أسفل قليلًا. وتُرسم عندما تكون خطوة داخلية لشريك ما، كالتحقق أو الحساب، مهمة لفهم التدفق. أما استدعاءات المساعدة الخاصة التي لا تحمل هذه الأهمية فتُحذف. ويُمنح الاستدعاء الذاتي المرسوم بدقة مواصفة تنفيذ متداخلة، أي شريطًا ثانيًا مزاحًا قليلًا فوق الشريط الأول.

```text
:OrderService
      │
     ┌┴┐
     │ ├───┐ validate()
     │ ┌─┐◀┘
     │ │ │
     │ └─┘
     │ │
     └┬┘
      │
```

### إنشاء الكائنات وتدميرها {/*#creation-and-destruction-of-objects*/}

يُرسم الكائن الذي لا يبدأ بالوجود إلا أثناء التفاعل برأسه عند الموضع الرأسي الذي يُنشأ فيه. وتشير رسالة الإنشاء إلى الرأس لا إلى خط الحياة. ويُعلَّم التدمير بعلامة إكس في نهاية خط الحياة.

```text
  :Session
      │
     ┌┴┐
     │ │        «create»
     │ │- - - - - - - - - ->┌─────────┐
     │ │                    │  :Cart  │
     │ │                    └────┬────┘
     │ │──── addItem(item) ────▶┌┴┐
     │ │                        └┬┘
     │ │──── «destroy» ────────▶ X
     └┬┘
      │
```

## الأجزاء المركبة {/*#combined-fragments*/}

الجزء المركب مستطيل يحيط بجزء من التفاعل. ويحدد المعامل في الزاوية العلوية اليسرى بنية التحكم المنطبقة على الرسائل المحاطة، كبديل أو حلقة مثلًا. وتقسم خطوط أفقية متقطعة الجزء إلى operands، وفي جزء `alt` يحمل كل operand حارسًا.

| المعامل    | المعنى                                                                          | يقابل                          |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------ |
| `alt`      | بدائل، يُنفَّذ operand واحد بالضبط، وتُوسم الحالة المتبقية بـ `[else]` | `if / else if / else`          |
| `opt`      | operand واحد يُنفَّذ فقط إذا تحقق الحارس                                        | `if` دون `else`            |
| `loop`     | تكرار، يُكتب بالصيغة `loop(min,max)` أو بحارس                                   | `while`، `for`، `do … while`   |
| `break`    | يحل الـ operand محل ما تبقى من التفاعل المحيط                                   | `return` مبكر، استثناء         |
| `par`      | تُنفَّذ الـ operands بالتزامن، ويجوز تداخل رسائلها                              | خيوط، مهام، استدعاءات متوازية  |
| `ref`      | إحالة إلى تفاعل مرسوم في مخطط مستقل                                             | استدعاء method، عملية فرعية    |
| `critical` | لا يجوز مقاطعة الـ operand بـ operands تعمل بالتزامن                            | مقطع حرج، قفل                  |
| `neg`      | التسلسل المحاط غير صالح ويجب ألا يحدث                                           | حالة اختبار سلبية              |
| `assert`   | التسلسل المحاط هو الاستمرار الصالح الوحيد                                       | تأكيد (Assertion)              |

عمليًا تغطي `alt` و`opt` و`loop` الغالبية العظمى من المخططات.

### البديل {/*#alternative*/}

```text
      :Client                        :Booking
         │                               │
        ┌┴┐                              │
        │ │──── reserve(seatNo) ───────▶┌┴┐
        │ │                             │ │
 ┌──────┼─┼─────────────────────────────┼─┼────────┐
 │ alt  │ │ [seat is free]              │ │        │
 │      │ │<- - - - reservationId - - - │ │        │
 ├╌╌╌╌╌╌┼╌┼╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┼╌┼╌╌╌╌╌╌╌╌┤
 │      │ │ [else]                      │ │        │
 │      │ │<- - - SeatTakenError - - - -│ │        │
 └──────┼─┼─────────────────────────────┼─┼────────┘
        └┬┘                             └┬┘
         │                               │
```

يجب أن تكون حراس جزء `alt` متنافية وينبغي أن تغطي كل الحالات.

### الحلقة {/*#loop*/}

```text
      :Order                         :LineItem
         │                               │
        ┌┴┐                              │
 ┌──────┼─┼──────────────────────────────┼─────────┐
 │ loop │ │ [more items]                 │         │
 │      │ │──── subtotal() ────────────▶┌┴┐        │
 │      │ │<- - - - amount - - - - - - -└┬┘        │
 └──────┼─┼──────────────────────────────┼─────────┘
        └┬┘                              │
         │                               │
```

يعبّر `loop(1,n)` عن عدد بدلًا من شرط، و`loop` دون إضافة تعني تكرارًا غير محدود.

## مثال: تفصيل حالة الاستخدام *حجز مقعد* {/*#example-detailing-the-use-case-book-seat*/}

السيناريو المفصَّل هنا هو المسار العادي لحالة الاستخدام *حجز مقعد*: يحجز عميل مقعدًا محددًا، ويبحث النظام عن المقعد ويعلّمه محجوزًا إذا كان ما زال شاغرًا. يُشتق المخطط من الوصف النصي لحالة الاستخدام بهذه الخطوات:

1. يُختار سيناريو واحد من حالة الاستخدام، وعادةً المسار العادي من الوصف النصي.
2. يصبح الفاعل المُطلِق خط الحياة الأقصى يسارًا.
3. تُضاف الشركاء الداخليون، وعادةً على امتداد طبقات المعمارية: واجهة المستخدم، والتحكم، وكائن المجال، والتخزين الدائم.
4. تصبح كل خطوة من المسار النصي رسالةً يطابق اسمها عملية لدى المستقبِل.
5. تصبح الاستثناءات من الوصف النصي أجزاء `alt` أو `break`، أو مخططًا منفصلًا لكل منها.

```text
┌────────────────┐
│ sd BookSeat    │
├────────────────┴─────────────────────────────────────────────────────┐
│                                                                      │
│       :Customer            :BookingService         :SeatRepository   │
│           │                       │                       │          │
│          ┌┴┐                      │                       │          │
│          │ │── bookSeat(id) ────▶┌┴┐                      │          │
│          │ │                     │ │── findSeat(id) ────▶┌┴┐         │
│          │ │                     │ │<- - seat - - - - - -└┬┘         │
│          │ │                     │ │                      │          │
│          │ │              ┌──────┼─┼──────────────────────┼───────┐  │
│          │ │              │ opt  │ │ [seat is free]       │       │  │
│          │ │              │      │ │── markBooked(id) ──▶┌┴┐      │  │
│          │ │              │      │ │<- - - - ok - - - - -└┬┘      │  │
│          │ │              └──────┼─┼──────────────────────┼───────┘  │
│          │ │<- - confirmation - -└┬┘                      │          │
│          └┬┘                      │                       │          │
│           │                       │                       │          │
└──────────────────────────────────────────────────────────────────────┘
```

ما يمكن قراءته من هذا المثال:

- لا تُرسم هنا الحالة الفاشلة لجزء `opt`، وكانت ستُنمذج إما بـ `alt` أو في مخطط منفصل.
- كانت خطوة الدفع ستُدرج بجزء `ref` كي يبقى هذا المخطط مقروءًا ويحصل الدفع على تفاعله الخاص.

## مخطط التسلسل أو النشاط أو الاتصال {/*#sequence-activity-or-communication-diagram*/}

الثلاثة كلها مخططات سلوكية.

| المعيار           | مخطط التسلسل                              | مخطط النشاط                             | مخطط الاتصال                              |
| ----------------- | ----------------------------------------- | --------------------------------------- | ----------------------------------------- |
| التركيز           | تبادل الرسائل عبر الزمن                   | تدفق التحكم في عملية                    | بنية التعاون                              |
| الزمن             | صريح، بوصفه المحور الرأسي                 | ضمني، عبر اتجاه التدفق                  | عبر ترقيم الرسائل فقط                     |
| المشاركون         | خطوط حياة جنبًا إلى جنب                   | اختياري، بوصفهم partitions              | كائنات موضوعة بحرية ومرتبطة بروابط        |
| التفرع            | أجزاء مركبة، يزدحم بسرعة                  | عقد قرار ودمج، مقروء جيدًا              | بالكاد مقروء                              |
| التزامن           | جزء `par`                                 | Fork وjoin                              | ممكن، لكن قراءته صعبة                     |
| الاستخدام النموذجي | تفصيل سيناريو واحد                       | نمذجة عملية كاملة                       | إظهار أي كائن يعرف أي كائن آخر            |

قواعد عملية:

- تفرعات وحلقات كثيرة ومشاركون قليلون => [مخطط النشاط](./activity-diagram.md)
- تفرعات قليلة ومشاركون كثيرون وترتيب مهم => مخطط التسلسل
- السؤال *من متصل بمن* لا *بأي ترتيب* => [مخطط الاتصال](./further-uml-diagrams.md#communication-diagram)
- سلوك كائن *واحد فقط* عبر دورة حياته كاملة => [مخطط آلة الحالة](./state-machine-diagram.md)

## الأخطاء الشائعة {/*#common-mistakes*/}

1. **تجاهل محور الزمن:** يجري الزمن من الأعلى إلى الأسفل عبر جميع خطوط الحياة. فالسهم المرسوم إلى الأعلى يعكس الترتيب المقصود. ورسالتان على الارتفاع نفسه ليس لهما ترتيب محدد.
2. **الرد بسهم متصل:** يُرسم الرد خطًا متقطعًا برأس سهم مفتوح. أما الخط المتصل برأس سهم ممتلئ فيُقرأ استدعاءً جديدًا في الاتجاه المعاكس.
3. **الخلط بين المتزامن وغير المتزامن:** رأس السهم الممتلئ يعني أن المرسل ينتظر الرد. والأحداث والإشعارات والرسائل المرسلة إلى طابور غير متزامنة وتأخذ رأس السهم المفتوح.
4. **مواصفات تنفيذ غير مغلقة:** يجب أن يمتد شريط المستدعي على الأقل حتى وصول الرد. والشريط الذي ينتهي قبل ذلك يعني أن المستدعي كان قد انتهى.
5. **أفعال بدلًا من كائنات على خطوط الحياة:** يمثل خط الحياة شريك تواصل مثل `:SeatRepository`. أما خطوة مثل `Check availability` فليست شريكًا وتصبح رسالة بدلًا من ذلك.
6. **حراس مفقودة في operands من نوع alt:** من دون حراس لا يبيّن المخطط الشرط الذي ينطبق بموجبه كل operand في جزء `alt`.
