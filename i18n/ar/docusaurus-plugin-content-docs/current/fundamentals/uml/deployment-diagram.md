# مخطط النشر

## نظرة عامة {/*#overview*/}

مخطط النشر هو مخطط UML **بنيوي**. يبيّن كيف يتوزع نظام منجز توزعًا فعليًا: ما العتاد وما بيئات التشغيل الموجودة، وما الملفات المثبتة عليها، وعبر أي مسارات اتصال تتبادل هذه الأجزاء البيانات.

التطبيقات النموذجية:

- توثيق مشهد النظام لتطبيق ما لأغراض التشغيل والتسليم
- عرض معمارية عميل-خادم أو معمارية ثلاثية الطبقات مع حدود الشبكة
- تخطيط عملية التثبيت: أي artifact يُنسخ إلى أي جهاز
- وصف نشر حاويات أو سحابي مع البروتوكولات وأعداد النسخ المتماثلة
- توفير أساس لمناقشات التوافرية والتوسع ومناطق الأمان

---

## الترميز {/*#notation*/}

| العنصر                | الترميز                                                                | المعنى                                                                                            |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| عقدة (Node)           | متوازي مستطيلات (صندوق ثلاثي الأبعاد)                                  | مورد تنفيذ يعمل عليه شيء ما أو يُخزَّن فيه                                                        |
| جهاز (Device)         | متوازي مستطيلات مع الكلمة المفتاحية `<<device>>`                        | عتاد فعلي: خادم، محطة عمل، هاتف ذكي، موجّه، طابعة                                                 |
| بيئة تنفيذ            | متوازي مستطيلات مع `<<executionEnvironment>>`، يكون عادةً متداخلًا داخل جهاز | برمجيات تستضيف الـ artifacts: نظام تشغيل، JVM، خادم تطبيقات، بيئة تشغيل حاويات، DBMS               |
| Artifact              | مستطيل مع الكلمة المفتاحية `<<artifact>>` أو أيقونة مستند              | ملف فعلي ناتج عن عملية التطوير                                                                    |
| نشر (Deployment)      | artifact مرسوم داخل عقدة، أو سهم متقطع `<<deploy>>`           | الـ artifact مثبت على تلك العقدة                                                                  |
| تجسيد (Manifestation) | سهم متقطع `<<manifest>>` من artifact إلى مكوِّن أو صنف                   | الـ artifact هو التحقق الفعلي لعنصر منطقي                                                         |
| مسار اتصال            | خط متصل بين عقدتين                                                     | اتصال تتبادل عبره العقدتان البيانات، دون اتجاه                                                    |
| بروتوكول              | Stereotype على المسار، مثل `<<HTTPS>>`، `<<TCP/IP>>`، `<<JDBC>>`     | البروتوكول المستخدم في ذلك الاتصال                                                                |
| تعددية                | رقم عند نهاية مسار الاتصال، مثل `2` أو `1..*`          | كم عقدة عند ذلك الطرف متصلة بعقدة واحدة عند الطرف الآخر                                           |
| تداخل                 | عقدة أو artifact مرسوم داخل عقدة                                       | احتواء: العتاد يحتوي بيئة التشغيل التي تحتوي الملف                                                |
| نسخة (Instance)       | اسم مسطَّر يسبقه نقطتان رأسيتان، مثل `:AppServer`                | نسخة ملموسة بدلًا من نوع                                                                          |
| ملاحظة                | مستطيل بزاوية مطوية على خط متقطع                                       | تعليق بلا دلالة                                                                                   |

قواعد التسمية التي تُبقي المخطط مقروءًا:

- تُسمّى العقدة باسم نوع، `ApplicationServer`، أو باسم جهاز ملموس، `appsrv01:ApplicationServer`. ويُسطَّر اسم النسخة في أداة الرسم.
- تحمل الـ artifacts اسم الملف الحقيقي بما فيه الامتداد: `shop.war`، وليس `Shop application`.
- يحمل كل مسار اتصال stereotype للبروتوكول، فالخط غير الموسوم لا يقول سوى *متصل بطريقة ما*.
- تُكتب الكلمات المفتاحية والـ stereotypes بين guillemets، `«device»`. والكتابة `<<device>>` هي الصيغة ASCII التي تستخدمها الأدوات النصية، وهي المستخدمة أدناه.

## اللبنات الأساسية {/*#building-blocks*/}

### العقدة {/*#node*/}

يُميَّز نوعان من العقد بالكلمة المفتاحية:

- **`<<device>>`:** عتاد فعلي كخادم أو محطة عمل أو هاتف محمول أو متحكم مدمج
- **`<<executionEnvironment>>`:** بيئة برمجية تستضيف الـ artifacts وتوفر لها خدمات كإدارة الذاكرة أو المعاملات أو توزيع الطلبات

تُوضع بيئة التنفيذ عادةً داخل جهاز. أما العقدة بلا كلمة مفتاحية فهي ببساطة *مورد تنفيذ ما*.

```text
        ┌────────────────────────────────────────┐
       ╱                                        ╱│
      ┌────────────────────────────────────────┐ │
      │  <<device>>                            │ │
      │  ApplicationServer                     │ │
      │                                        │ │
      │  ┌──────────────────────────────────┐  │ │
      │  │  <<executionEnvironment>>        │  │ │
      │  │  Tomcat 10                       │  │ │
      │  │                                  │  │ │
      │  │  ┌────────────────────────────┐  │  │ │
      │  │  │  <<artifact>>              │  │  │ │
      │  │  │  shop.war                  │  │  │ │
      │  │  └────────────────────────────┘  │  │ │
      │  └──────────────────────────────────┘  │ ╱
      └────────────────────────────────────────┘╱
```

في أداة الرسم تكون كل عقدة متوازي مستطيلات، بما فيها المتداخلة. وتُرسم العقد الداخلية في المخططات هنا مستطيلات عادية كي يبقى التداخل مقروءًا في النص العادي.

### الـ Artifact والنشر {/*#artifact-and-deployment*/}

الـ artifact في الممارسة العملية ملف. ومن أمثلته النموذجية `shop.war` و`payment-service.jar` و`setup.exe` و`schema.sql` و`nginx.conf` وصورة حاوية مثل `shop-app:2.4.0`.

يوجد ترميزان يبيّنان أن artifact مثبت على عقدة:

- **التداخل:** يُرسم مستطيل الـ artifact داخل العقدة. وهذه الصيغة أكثر إحكامًا وهي الأكثر شيوعًا بفارق كبير.
- **الاعتمادية:** سهم متقطع بالكلمة المفتاحية `<<deploy>>` يقود من الـ artifact إلى العقدة. وهذه الصيغة مفيدة عند نشر الـ artifact نفسه على عدة عقد.

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈┈ <<deploy>> ┈┈┈┈┈┈▶ │  <<device>>            │
 │  shop.war              │                          │  ApplicationServer     │
 └────────────────────────┘                          └────────────────────────┘
```

التجسيد (manifestation) هو النظير المتجه نحو التصميم. يقود سهم متقطع بالكلمة المفتاحية `<<manifest>>` من الـ artifact إلى المكوِّن أو الصنف الذي يحققه فعليًا، فيبيّن أي جزء من النموذج ينتهي في هذا الملف.

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈ <<manifest>> ┈┈┈┈┈▶ │  <<component>>         │
 │  payment-service.jar   │                          │  PaymentService        │
 └────────────────────────┘                          └────────────────────────┘
```

### مسار الاتصال {/*#communication-path*/}

مسار الاتصال خط متصل بلا رأس سهم، لأن الاتصال نفسه ليس له اتجاه، ويُوسَم بالبروتوكول في صورة stereotype.

```text
    ┌──────────────────────┐                  ┌──────────────────────┐
   ╱                      ╱│                 ╱                      ╱│
  ┌──────────────────────┐ │                ┌──────────────────────┐ │
  │  <<device>>          │ │ 2            1 │  <<device>>          │ │
  │  AppServer           │ ├──── <<JDBC>> ──┤  DatabaseServer      │ │
  │                      │ ╱                │                      │ ╱
  └──────────────────────┘╱                 └──────────────────────┘╱
```

الـ stereotypes الشائعة للبروتوكولات هي `<<HTTP>>` و`<<HTTPS>>` و`<<TCP/IP>>` و`<<JDBC>>` و`<<REST>>` و`<<AMQP>>` و`<<SSH>>` و`<<SMTP>>`. واختيار أحدها مسألة تتعلق بمستوى التفصيل المقصود: `<<TCP/IP>>` يسمّي وسيلة النقل، أما `<<HTTPS>>` فيبيّن إضافةً إلى ذلك أن الاتصال مشفَّر، وهذه عادةً المعلومة الأنفع.

### التعددية والتداخل {/*#multiplicity-and-nesting*/}

تُكتب التعددية عند نهاية مسار الاتصال وتتطلب أسماء أنواع: فالنسخة مثل `appsrv01:ApplicationServer` هي دائمًا جهاز واحد بالضبط.

يمكن أن يمتد التداخل عبر عدة مستويات، ويعمل كل مستوى على المستوى المحيط به:

```text
<<device>>                  ServerHardware
  <<executionEnvironment>>    Linux
    <<executionEnvironment>>    Docker Engine
      <<artifact>>                shop-app:2.4.0
```

تُحذف المستويات التي لا تهم غرض المخطط، مثل بيئة تشغيل الحاويات في خطة السعة. وعلى العكس، في خطة الإصدار يكون وسم إصدار الصورة هو المعلومة الأساسية.

## مثال: متجر ويب ثلاثي الطبقات {/*#example-three-tier-web-shop*/}

يتكون المتجر من واجهة أمامية في المتصفح وتطبيق في حاوية وقاعدة بيانات علائقية. تعمل كل طبقة على جهازها، وخادم التطبيقات موجود مرتين، ولا يمكن الوصول إلى قاعدة البيانات إلا من خادم التطبيقات.

```text
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ClientPC                                  │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Browser                             │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 0..*
               <<HTTPS>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ApplicationServer                         │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Docker Engine                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-app:2.4.0                │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 2
                <<JDBC>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  DatabaseServer                            │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  PostgreSQL 16                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-schema.sql               │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
```

ما يُظهره هذا المثال:

- تبيّن التعددية `2` عند طرف خادم التطبيقات من مسار `<<JDBC>>` أن خادمي تطبيقات يصلان إلى قاعدة البيانات، وتبيّن `0..*` عند طرف العميل أن أي عدد من العملاء يمكن أن يتصل، بما في ذلك عدم وجود أي عميل.
- لا يُذكر *متى* يحدث أي استدعاء. وترتيب الاستدعاءات مكانه [مخطط التسلسل](./sequence-diagram.md).

## الأخطاء الشائعة {/*#common-mistakes*/}

1. **أصناف أو مكونات داخل عقدة:** تحتوي العقدة artifacts. والعنصر المنطقي مكانه [مخطط الأصناف](./class-diagram.md) أو مخطط المكونات، ويُربط بالـ artifact بـ `<<manifest>>`.
2. **مسار اتصال بلا بروتوكول:** من دون `<<HTTPS>>` أو `<<JDBC>>` على الخط لا يعود المخطط يبيّن أي الاتصالات مشفَّرة ولا أي المنافذ يجب أن يفتحها جدار الحماية.
3. **الخلط بين الجهاز وبيئة التنفيذ:** `<<device>>` عتاد، و`<<executionEnvironment>>` برمجيات تعمل عليه. والحاوية ليست جهازًا.
4. **رؤوس أسهم على مسار الاتصال:** المسار غير موجَّه. والاتجاه يخص اعتمادية مثل `<<deploy>>` أو `<<manifest>>`.
5. **رسم كل ملف:** ما يهم التثبيت والتشغيل فقط هو ما يوضع في المخطط، وليس كل مكتبة وكل ملف إعدادات.
6. **تعددية مفقودة:** عنقود من أربعة أجهزة مرسوم بعقدة واحدة من دون `4` يخفي حجمه.
7. **مساواة الطبقات المنطقية بالعقد:** طبقات العرض والمنطق والبيانات تقسيم منطقي، أما العقد فتقسيم فعلي. ويمكن تمامًا أن تعمل ثلاث طبقات على جهاز واحد.
