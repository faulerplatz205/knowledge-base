# 問題管理

## 概要 {/*#overview*/}

問題管理(Problem Management)は**インシデント管理の第2段階**である。インシデント管理がサービスを可能な限り早く復旧することに重点を置くのに対し、問題管理は根本原因を特定して除去し、将来のインシデントを防ぐ。

## インシデント、問題、既知のエラーの比較 {/*#incident-vs-problem-vs-known-error*/}

| 用語               | 定義                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| **インシデント**   | 計画外のサービス中断。原因は不明な場合がある。サービスの復旧が優先される                |
| **問題**           | **根本原因が不明**な1件以上のインシデント。専門家が調査する                             |
| **既知のエラー**   | 根本原因が判明しており、回避策または修正が存在する問題                                  |

ファーストレベルサポートで解決策が見つからない場合、チケットは**エスカレーション**される。インシデントは、セカンドレベルサポートが管理する問題となる。

## 問題管理の3つの活動 {/*#the-three-activities-of-problem-management*/}

### 1. 問題コントロール {/*#1-problem-control*/}

すべての問題が体系的に分析され、文書化される。目標は、不明な原因を**既知のエラー**に変えることである。

手順:

1. 問題を記録し、既知のエラーデータベースと照合する
2. 回避策/解決策がすでに存在する場合 => 既知のエラーとして扱い、発生カウンターを更新する
3. 問題を分類する(カテゴリ、サブカテゴリ、優先度、ビジネスへの影響)
4. 根本原因を分析する([分析手法](./analysis-methods.md)を参照)
5. 結果を新しい既知のエラーとしてKEDBに記録する

### 2. エラーコントロール {/*#2-error-control*/}

既知のエラーが存在する場合、エラーコントロールは回避策から恒久的な修正までの経路を管理する。

- サービスを復旧するため、**回避策**が直ちに提供される
- 恒久的な修正は**[RFC](./change-management.md#request-for-change-rfc)**を通じて開始される
- 変更の実施後、問題管理は**[実施後レビュー(PIR)](./change-management.md#closing-a-change-pir)**を通じて確認を受け取る
- ファーストレベルサポートに通知され、顧客へ連絡できるようになる

### 3. プロアクティブな問題管理 {/*#3-proactive-problem-management*/}

インシデントが発生する前に防ぐ。

- 頻繁に再発する既知のエラーを分析する(発生カウンターが高いものはプロアクティブな問題管理の候補)
- ソフトウェア/ハードウェアの今後の問題に関するメーカーからの情報を評価する
- 自動的な警告や例外を監視する

## 回避策 {/*#workaround*/}

**回避策(Workaround)**とは、問題の迂回、代替手段、または暫定的な解決策(問題を「回避して作業する」こと)であり、根本原因への対処が進められている間、サービスを暫定的に素早く復旧させるために用いられる。

**重要:** 暫定的な修正が恒久的な状態にならないよう、回避策はシステム上で一時的な措置であることを明確に示さなければならない。

**例:**

| 障害                                 | 回避策                                         |
| ------------------------------------ | ---------------------------------------------- |
| 内蔵Webカメラの故障                  | USBカメラを接続する                            |
| モバイルデータ収集端末の故障         | 貸出機を使用する                               |
| 有線ネットワークポートの故障         | WLANスティックまたはLANアダプターを使用する    |
| DVIモニターポートの故障              | 利用可能であればDisplayPortまたはHDMIを使用する |
| レーザープリンターが起動しない       | 電源を抜いて再起動する                         |
| ブラウザに空白のページが表示される   | ブラウザのキャッシュを消去するか、別のブラウザを使用する |

## 既知のエラーデータベース(KEDB) {/*#known-error-database-kedb*/}

KEDBは、既知のすべての問題をその回避策または解決策とともに格納する。ファーストレベルサポートは、セカンドレベルへエスカレーションすることなく迅速に支援を行うために、これを利用する。

各エントリには、問題が再発する頻度を追跡する**発生カウンター**(Vorfallszähler)がある。カウンターが高い場合は、プロアクティブな問題管理の候補となる。

## 主要KPI {/*#key-kpis*/}

| KPI                                       | 意味                                                                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **新規問題の件数**                        | 一定期間に登録された問題の総数。プロアクティブな問題管理は、エラーがインシデントになる前に解決することで、この数を最小化することを目指す  |
| **既知の問題あたりのインシデント件数**    | 同一の問題に関連づけられたインシデントの平均件数。影響の広がりを示し、プロアクティブな問題管理の候補を特定する                              |
| **問題解決の工数**                        | 問題の解決にかかる平均作業工数をカテゴリ別に分けたもの。どのカテゴリに最も工数がかかるかを示す                                              |

## 問題の特定と問題の解決の分離 {/*#separation-of-problem-localisation-and-problem-resolution*/}

問題管理は根本原因を特定し、[変更管理](./change-management.md)がそれを解決する。この分離により、次のことが可能になる。

- 一度に1つのタスクに集中できる
- 根本原因の調査が完了する前にサービスを復旧できる(回避策)
- 必ずしも異なるチームが関与するわけではないが、プロセスの手順が分離される
