# 変更管理

## 概要 {/*#overview*/}

**変更管理**は、ITSMの第3レベルである。ITシステムに対する変更の承認と計画を扱う。

**目的:** 変更が、全体像を把握しないまま性急に行われないようにすること。さまざまな分野の専門家がリスクを評価し、後続のエラーを避ける。このプロセスを迂回できるのは緊急変更のみであり、その場合は可能な限り早いシステムの復旧が最優先となるためである。

## 変更要求 (RFC) {/*#request-for-change-rfc*/}

変更が実行される前に、通常は[問題管理](./problem-management.md)によって、**変更要求 (RFC)** が作成される。RFCは、変更の実施を求める正式な要求である。次の内容を含む。

- 変更の説明
- 変更の理由
- スケジュール
- 優先度
- 想定される副作用
- 見積コスト

RFCは**何を**行うべきかを記述するが、**どのように**行うかは記述しない。その方法は、変更管理のプロセスで詰められるためである。

## RFCの優先順位付け {/*#rfc-prioritisation*/}

受け付けたRFCは、**緊急度**と**影響度**によって優先順位が付けられる。

### 緊急度のレベル {/*#urgency-levels*/}

| レベル                | 説明                 |
| --------------------- | -------------------- |
| **優先度 低**         | 望ましいが緊急ではない |
| **優先度 中**         | 必要だが緊急ではない   |
| **優先度 高**         | 直ちに対応が必要       |
| **優先度 即時**       | 直ちに対応が必要       |

### 影響度のレベル {/*#impact-levels*/}

| レベル         | 説明                                         | 例                     |
| -------------- | -------------------------------------------- | ---------------------- |
| **影響 小**    | ITサービスへの影響が最小で、手間も少ない     | PC1台の交換            |
| **影響 中**    | 影響は中程度で、手間が増える                 | 全PCのOSのアップグレード |
| **影響 大**    | ITサービスへの影響が大きく、手間が非常に大きい | サーバーの全面停止     |

## 変更の種類 {/*#change-types*/}

| 種類                                       | 特徴                                                                                      | 承認                     |
| ------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------ |
| **標準変更**                               | カタログに基づく事前承認済みの定型的な変更。低リスク。自動的に承認される                  | チェンジマネージャーのみ |
| **通常変更**                               | 中程度のリスク、中程度の複雑さ、中程度の緊急度。専門家による評価が必要                    | CAB + CIO                |
| **緊急変更 (Notfall Change)**              | 緊急度が高く、短期的な解決策が必要。速度を優先して、構造化された承認プロセスは迂回される  | EC / ECAB                |

## 承認機関 {/*#approval-bodies*/}

| 機関                                 | 説明                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **チェンジマネージャー (CM)**        | 影響範囲の小さい変更 (標準変更) を単独で決定する。時間管理と監視を担当する                                            |
| **変更諮問委員会 (CAB)**             | さまざまな事業分野の専門家による委員会。影響範囲が中程度の変更 (通常変更) を決定する                                  |
| **最高情報責任者 (CIO)**             | ITの利益を代表する、取締役会/経営層レベルの人物。事業上の範囲が大きい決定 (例: 職員研修) に関与する                    |
| **緊急委員会 (EC / ECAB)**           | 緊急の決定のための、高い権限を持つ少人数の専門家チーム。緊急変更を扱う                                                |

## 変更の計画 {/*#change-planning*/}

### 変更の先行スケジュール (FSC) {/*#forward-schedule-of-change-fsc*/}

計画されたすべての長期的な変更を記録するカレンダー。計画は常にダウンタイムの最小化を目指すべきである。

### 構成管理データベース (CMDB) {/*#configuration-management-database-cmdb*/}

すべてのCIを、その仕様とライセンス番号とともに保管する中央データベース。CIに対するすべての変更は、ここで一元的に記録される。

チェンジマネージャー (CM) は、変更の時間管理された実施と監視を担当する。

## 変更の承認と実行 {/*#approving-and-executing-changes*/}

変更の承認・認可と、計画・実行の分離は、ITSMにおいて意図的なものである。これにより、次のことが確保される。

- システム全体を考慮する専門家による、持続可能な決定
- より広い文脈を考慮しない、場当たり的なエラー修正の防止
- 文書化された責任の所在

## 変更の終結 (PIR) {/*#closing-a-change-pir*/}

変更の実施後、変更管理はすべての措置と障害の根本原因を、将来の参照のためにCMDBとKEDBに記録する。

**実施後レビュー (PIR)** は、変更のすべての重要点を記録する。

- テスト結果
- 実施の詳細
- 従前のシステム状態からの変更点
- コストと工数
- タイムスタンプ

**PIRの目的:** 完了した変更をレビューし評価することで、継続的な改善を推進すること。

## 変更の種類と承認のまとめ {/*#change-types-and-approval-summary*/}

| 変更の種類 | 承認機関             | 主な特徴                                 |
| ---------- | -------------------- | ---------------------------------------- |
| 標準変更   | チェンジマネージャー | カタログに基づく、事前承認済み、低リスク |
| 通常変更   | CAB + CIO            | 中程度のリスク、CABが関与                |
| 緊急変更   | EC / ECAB            | 最高速度、構造化されたプロセスは迂回     |
