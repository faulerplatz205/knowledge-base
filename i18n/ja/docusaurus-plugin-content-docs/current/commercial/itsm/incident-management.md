# インシデント管理

## 概要 {/*#overview*/}

**インシデント管理** (Incident Management) は**ITSMの最初の段階**であり、IT障害の後にユーザーが可能な限り早く業務を再開できるよう支援することに重点を置く。

## 構成アイテム(CI) {/*#configuration-items-ci*/}

**構成アイテム** (Configuration Item、CI) は、ほぼすべてのハードウェアとソフトウェアを含む広範な用語である。CIは属性によって特徴づけられ、他のCIと関連づけられる。

| カテゴリ            | 例                                                     |
| ------------------- | ------------------------------------------------------ |
| ハードウェアシステム | PC、ノートPC、サーバー、シンクライアント               |
| ハードウェアコンポーネント | グラフィックスカード、ネットワークカード、ハードドライブ、プロセッサ |
| ソフトウェアコンポーネント | オペレーティングシステム、アプリケーションソフトウェア |
| ネットワークコンポーネント | ルーター、スイッチ、ハブ、リピーター、パッチパネル、NAS |
| 周辺機器            | プリンター、スキャナー、Webカメラ                      |
| モバイル機器        | タブレット、スマートフォン、データ収集端末             |

## インシデントの定義 {/*#incident-definition*/}

**インシデント**とは、ITサービスの計画外の中断または品質低下をいう。将来ITサービスを損なう可能性のある事象もインシデントに該当する。空になったトナーカートリッジの交換のような軽微な事象も含まれる。

**最優先の目標: 影響を受けたサービスを可能な限り早く復旧すること。**

## 分類 {/*#categorisation*/}

インシデントは、課題管理システムに最初に記録される時点で分類される。

- **HW** = ハードウェアの問題
- **SW** = ソフトウェアの問題
- **NW** = ネットワークの問題

目的: 適切なチームが担当することを保証し、重大度を正しく評価できるようにする。

## 優先度付け {/*#prioritisation*/}

優先度は2つの要素によって決まる。

- **緊急度(Dringlichkeit)**: 障害はユーザーの目標にどの程度深刻な影響を与えるか。
- **影響度(Auswirkung)**: 障害の影響を受ける人数はどれだけか。

[緊急度と影響度](./priorities.md#itil-priority-matrix)の組み合わせによって、受信したチケットの処理順序が決まる。

## サポートレベル {/*#support-levels*/}

| レベル                         | 説明                                                                                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ファーストレベルサポート**   | ヘルプデスク/SPOC。ナレッジベースを用いて単純な問題を処理し、顧客との直接のやり取りを担うことでセカンドレベルサポートの「ファイアウォール」として機能する |
| **セカンドレベルサポート**     | 根本原因分析([問題管理](./problem-management.md))を担う専門家。ファーストレベルが設定した初期優先度を再評価する                                              |
| **サードレベルサポート**       | セカンドレベルで解決できない場合の、メーカーサポートまたは外部の専門家                                                                                      |

## インシデントレコード {/*#incident-record*/}

**インシデントレコード** (Incident Record) は、インシデントに関するすべての情報を含む文書であり、最初の記録から解決までのライフサイクルを記録する。情報文書であり、プロセスインスタンスの終了後に変更してはならない。

17の標準構成要素:

1. ID/識別子
2. 初回記録(日時)
3. 通知の種類
4. サービスデスク担当者
5. 報告者/ユーザーのデータ
6. コミュニケーションチャネル
7. **症状の説明**(最も重要な項目。診断と解決策の調査に役立つ)
8. 影響を受けるユーザー、場所、業務領域
9. 影響を受けるサービス
10. 優先度付け
11. CIへの参照
12. インシデントカテゴリ
13. 他のインシデントレコードへのリンク
14. 問題レコードへのリンク
15. インシデントのステータス履歴
16. 活動履歴/タスク
17. 解決および終了のデータ

**常に記録しなければならない上位5項目:** 優先度付け、インシデントカテゴリ、ID、影響を受けるユーザー/サービス、コミュニケーションチャネル。

## 重大インシデント {/*#major-incident*/}

**重大インシデント** (Major Incident) とは、重要なサービスの停止や大規模な障害を引き起こし、業務運営に著しい影響を与える、優先度と影響度の高い事象をいう。通常、優先度は「クリティカル」または「高」に設定される。

特徴:

- 多数の顧客または重要な顧客グループが影響を受ける
- 顧客やサービス組織にとっての費用と損失が大きい
- サービスプロバイダーの評判が損なわれる可能性が高い
- インシデント解決にかかる作業と時間の負担が大きいと見込まれ、既存の[SLA](./sla.md)の合意に違反する可能性が高い

## サービスリクエストとインシデントの比較 {/*#service-request-vs-incident*/}

|                | サービスリクエスト                                         | インシデント                               |
| -------------- | ---------------------------------------------------------- | ------------------------------------------ |
| **きっかけ**   | ユーザーが質問や要望を持ってサポートに自ら連絡する         | 計画外のサービス障害                       |
| **例**         | パスワードの失念、ソフトウェアに関する質問、新しい作業環境のセットアップ | プリンターの故障、ERPに接続できない、ランサムウェア |
| **対応者**     | 通常はファーストレベルサポートで完全に解決される           | 第2/第3レベルへのエスカレーションが必要な場合がある |
| **プロセス**   | リクエストフルフィルメント                                 | インシデント管理                           |
