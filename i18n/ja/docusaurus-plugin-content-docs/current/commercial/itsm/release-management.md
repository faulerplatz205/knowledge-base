# リリース管理

## 概要 {/*#overview*/}

**リリース管理** (Release Management) はITSMの第4段階であり、変更管理の延長にある。変更管理が変更を承認して計画するのに対し、リリース管理は変更を**実行**し、円滑で中断のないロールアウトを目指す。

## 変更管理との関係 {/*#relationship-to-change-management*/}

| 変更管理                                                         | リリース管理                                                        |
| ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| 変更を承認し、計画する                                           | 変更を実行する                                                      |
| [RFC](./change-management.md#request-for-change-rfc)を作成する   | [RFC](./change-management.md#request-for-change-rfc)を実装する      |
| 何を、いつ行うかを決定する                                       | どのように行うかを決定し、ロールアウトする                          |

## リリースパッケージ {/*#release-package*/}

ロールアウトの前に、計画されたすべての変更を含む**リリースパッケージ**が作成される。テストは、稼働中の本番環境から取り出した[CI](./incident-management.md#configuration-items-ci)を更新し、テスト環境に戻して行うのが望ましい。定められた期間、問題なくテストが完了した後、リリースをすべての対象システムにロールアウトできる。

ソフトウェア配布システムは、多数の[CI](./incident-management.md#configuration-items-ci)へのリリースの効率的な配布を支援する。

## ロールアウトの方式 {/*#rollout-approaches*/}

### ビッグバン {/*#big-bang*/}

すべての受信者が同時にリリースを受け取る。

**利点:**

- 全体の実施が速い
- すべてのシステムが同時に同じ更新を受ける
- トラブルシューティングが効率的になる(バージョンの差異がない)

**欠点:**

- エラーが発生した場合のリスクが高い(すべてのシステムが一度に影響を受ける)
- ロールアウト中のインフラストラクチャへの負荷が高い

### 段階的 {/*#phased*/}

リリースはまず受信者の**一部**にロールアウトされ、その後段階的に対象が拡大される。

**利点:**

- リスクが低い(影響を受けるシステムは一部のみ)
- 大きな障害を伴わずにエラーを早期に検出できる

**欠点:**

- 実施に時間がかかる
- 移行期間中、異なるソフトウェアバージョンが同時に稼働する

## ロールバック {/*#rollback*/}

本番環境でリリースが想定外に失敗した場合に備え、以前の状態への**ロールバック**を常に利用可能にしておくべきである。ロールアウトの完了後、ユーザーにはプロセスインスタンスを通じて更新が通知される。

## リリース管理における仮想マシン {/*#virtual-machines-in-release-management*/}

**仮想マシン(VM)**:コンピューターシステムをソフトウェアでカプセル化したもので、ホストコンピューター上で実際のPCを模擬する。

**利点:**

- コピーの作成、起動、変更が容易で、リスクがない
- 物理システムをVMに変換できる(P2V = Physical to Virtual)

**リリース管理にとっての利点:** 新しいバージョン、更新、アプリケーションを、VM環境で安全にテストできる。古いバージョンを並行して稼働させ続けることもできる(リソース効率)。

## ITSMプロセスの概要 {/*#itsm-process-overview*/}

ITSMの4つの段階は、連鎖として連携する。

| プロセス                                            | 役割                                                         |
| --------------------------------------------------- | ------------------------------------------------------------ |
| [**インシデント管理**](./incident-management.md)    | 障害を記録し、問題を選別する                                 |
| [**問題管理**](./problem-management.md)             | 根本原因を特定し、可能な場合は回避策を提供する               |
| [**変更管理**](./change-management.md)              | 妥当な変更を承認し、計画する                                 |
| [**リリース管理**](./release-management.md)         | 変更を安全に実行する                                         |

**この分離の理由:** プロセスを組み合わせて運用することで持続可能性を目指し、複雑なワークフローに構造をもたらす。

## ITSMプロセスと[IMAC/R/Dフェーズ](./service-types.md#imacrd-lifecycle) {/*#itsm-processes-and-imacrd-phases*/}

| IMAC/R/Dの活動             | 関連するITSMプロセス                                                           |
| -------------------------- | ------------------------------------------------------------------------------ |
| Wartung(保守)              | 変更管理、リリース管理                                                         |
| Inspektion(点検)           | 問題管理、変更管理、リリース管理                                               |
| Instandsetzung(修理)       | インシデント管理、問題管理、変更管理、リリース管理                             |
| Verbesserung(改善)         | 変更管理、リリース管理                                                         |
