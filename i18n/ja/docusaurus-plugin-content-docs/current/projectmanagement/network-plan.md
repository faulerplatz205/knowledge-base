# ネットワーク図

## 概要 {/*#overview*/}

:::info
ネットワーク計画の手法には、CPM(クリティカルパス法)、PERT、MPMなど、さまざまなものがある。この記事ではCPMを扱う。
:::

ネットワーク図は、タスクをノードとし、依存関係を矢印で表す有向グラフである。正確なスケジューリングとボトルネックの特定を可能にする。

## ノードの構造 {/*#node-structure*/}

ネットワーク図の各ノードには、次のフィールドが含まれる。

```text
┌──────────────────────────┐
│         Task Name        │
├─────────────┬────────────┤
│ EAT         │ EET        │
├─────────────┼────────────┤
│ Total Float │ Free Float │
├─────────────┼────────────┤
│ LAT         │ LET        │
├─────────────┴────────────┤
|          Duration        |
└──────────────────────────┘
```

- **EAT**(最早開始時刻): タスクを開始できる最も早い時刻
- **EET**(最早終了時刻): タスクを終了できる最も早い時刻
- **LAT**(最遅開始時刻): プロジェクトを遅延させずにタスクを開始できる最も遅い時刻
- **LET**(最遅終了時刻): タスクを終了できる最も遅い時刻
- **フリーフロート:** `min(EAT of all successors) − EET`; 直後の後続タスクを遅延させずに、タスクを遅らせることができる範囲
- **トータルフロート:** `LAT − EAT`; プロジェクトの終了日を遅延させずに、タスクを遅らせることができる時間

## バッファの種類 {/*#buffer-types*/}

**フリーフロート**は*局所的な*余裕を表す。直後の後続タスクを遅延させる前に、タスクがどれだけずれ込めるかを示す。ネットワーク内で1ステップ先のみを見る。

**トータルフロート**は*全体的な*余裕を表す。途中の影響にかかわらず、プロジェクト全体の終了日に影響が及ぶ前に、タスクがどれだけずれ込めるかを示す。

この2つは常に`Free Float ≤ Total Float`を満たす。`Total Float > Free Float`の場合、フリーフロートより大きな遅延は連鎖の手前にある後続タスクをずらすが、その後続タスクは自身のトータルフロートで影響を吸収できるため、プロジェクトの終了は遅れない。クリティカルパス上のタスクでは、両方の値がゼロである。

## プランの計算 {/*#calculating-the-plan*/}

**前進計算** – EATとEETを左から右へ計算する。

- EET = EAT + 所要期間
- タスクに複数の先行タスクがある場合 => EAT = すべての先行タスクのEETの最大値

**後進計算** – LATとLETを右から左へ計算する。

- LAT = LET − 所要期間
- タスクに複数の後続タスクがある場合 => LET = すべての後続タスクのLATの最小値

## クリティカルパス {/*#critical-path*/}

クリティカルパスは、プロジェクトの開始から終了までの依存するタスクの最長の連なりである。クリティカルパス上のタスクは**トータルフロートがゼロ**であり、遅延はそのままプロジェクト全体の終了日の遅れとなる。

## 利点 {/*#advantages*/}

- タスクの依存関係を明示的にモデル化できる
- クリティカルパスとスケジュール上のボトルネックを特定できる
- 最早・最遅の開始/終了時刻を正確に計算できる
- 複雑で依存関係の多いプロジェクトにより適している

## 欠点 {/*#disadvantages*/}

- [ガントチャート](./gantt.md)よりも作成と読み取りが複雑である
- 技術者でないステークホルダーには直感的でない
- 意味のある結果を得るには正確な所要期間の見積もりが必要である

## 例 {/*#example*/}

**プロジェクト:** Webサイトのローンチ

| ID | タスク                | 所要期間 | 先行タスク |
|----|-----------------------|----------|--------------|
| A  | 要件分析              | 2日      | —            |
| B  | UIデザイン            | 3日      | A            |
| C  | バックエンド開発      | 5日      | A            |
| D  | フロントエンド開発    | 4日      | B            |
| E  | 統合                  | 2日      | C, D         |
| F  | テスト                | 3日      | E            |
| G  | デプロイ              | 1日      | F            |

**ネットワークの構造:**

```text
    ┌──► B ──► D ───┐
A ──┤               ├──► E ──► F ──► G
    └──► C ─────────┘
```

**算出されたノードの値:**

```text
┌──────────────────────┐      ┌──────────────────────┐      ┌──────────────────────┐
│  A: Requirements     │      │  B: UI Design        │      │  C: Backend Dev      │
├──────────┬───────────┤      ├──────────┬───────────┤      ├──────────┬───────────┤
│  EAT: 0  │  EET: 2   │      │  EAT: 2  │  EET: 5   │      │  EAT: 2  │  EET: 7   │
├──────────┼───────────┤      ├──────────┼───────────┤      ├──────────┼───────────┤
```

**クリティカルパス:** A => B => D => E => F => G (合計15日)

タスクCのトータルフロートは2日(ここではフリーフロートとも等しい)で、クリティカルパス上にないため、バックエンド開発は後続タスクにもプロジェクトの終了日にも影響を与えずに最大2日遅れて開始できる。
