# コンパイラとインタープリター

## 概要 {/*#overview*/}

プロセッサが実行できるのは機械語だけである。そのため、高水準言語で書かれたソースコードは、先に変換する必要がある。基本的なアプローチは2つある。

- **コンパイラ**: 実行の**前に**プログラム全体を、独立した機械可読な成果物へ変換する
- **インタープリター**: 実行の**最中に**ソースコードを読み取り、各文をただちに実行する

言語がコンパイル型かインタープリター型かは、言語そのものではなく**実装**の性質である。Cは通常コンパイルされるが、Cのインタープリターも存在する。JavaScriptは歴史的にはインタープリター型であったが、現代のエンジンでは実行時にコンパイルされる。

---

## コンパイラ {/*#compiler*/}

### 変換プロセス {/*#translation-process*/}

変換は通常、複数のフェーズで行われる。

1. **字句解析**: 文字列がトークン(キーワード、識別子、演算子)に分割される
2. **構文解析**: トークンが文法に照らして検査され、構文木に変換される
3. **意味解析**: 型の互換性、宣言、スコープが検証される
4. **最適化**: 中間表現が改善される(例: デッドコードの除去、ループ展開)
5. **コード生成**: 機械語が出力される。通常はオブジェクトファイルとして出力される

その後、**リンカー**がオブジェクトファイルを必要なライブラリと結合し、実行可能なプログラムにする。

```text
Source Code => [Compiler] => Object Code => [Linker] => Executable => [CPU]
```

エラーはコンパイル時に報告されるため、構文エラーや型エラーのあるプログラムが実行に至ることはない。

### 利点 {/*#advantages*/}

- **実行速度**: 変換された機械語がプロセッサ上で直接実行される
- **早期のエラー検出**: 構文エラーや多くの意味エラーが、プログラムの出荷前に表面化する
- **最適化**: プログラム全体が見えるため、広範な最適化が可能になる
- **ソースコードの保護**: 配布する必要があるのはコンパイル済みの成果物のみである
- **実行時の依存がない**: 対象システムにコンパイラツールをインストールする必要がない

### 欠点 {/*#disadvantages*/}

- **コンパイル時間**: 変更のたびに、テストの前に新しいビルドが必要となる
- **プラットフォーム依存**: 機械語はプロセッサアーキテクチャとオペレーティングシステムに束縛されるため、対象プラットフォームごとに別のビルドが必要となる
- **デバッグの手間**: 実行される機械語はもはやソースコードに似ておらず、デバッグシンボルが必要となる

---

## インタープリター {/*#interpreter*/}

インタープリターは、ソースコードを文ごとに読み取り、解析して、ただちに実行する。単独で実行可能なファイルは生成されない。インタープリターは対象システム上に存在していなければならない。

```text
Source Code => [Interpreter] => Statement analysed and executed => [CPU]
```

エラーは、該当する行に実際に到達したときにのみ明らかになる。そのため、あまり使われない分岐にある構文エラーが、長期間気づかれないままになることがある。

### 利点 {/*#advantages-1*/}

- **高速な開発サイクル**: 変更したコードを、ビルドの手順なしにただちに実行できる
- **プラットフォーム非依存**: インタープリターが利用できる環境であれば、同じソースコードがどこでも動作する
- **デバッグの容易さ**: エラーは元のソース行を参照して報告される
- **柔軟性**: 実行時にコードを生成して実行できる

### 欠点 {/*#disadvantages-1*/}

- **実行速度**: 変換のオーバーヘッドが実行のたびに発生し、ループ内のコードでは繰り返し発生する
- **エラー検出の遅れ**: エラーは実行時にしか現れない
- **実行時の依存**: インタープリターが対象システムにインストールされている必要がある
- **ソースコードの開示**: プログラムは通常、読めるソースコードとして配布される

---

## バイトコードと仮想マシン {/*#bytecode-and-virtual-machines*/}

現代のプラットフォームの多くは、両方のアプローチを組み合わせている。ソースコードは**バイトコード**にコンパイルされる。これは、特定のプロセッサに結び付けられていないコンパクトな中間コードである。その後、**仮想マシン** (VM) が、このバイトコードを対象システム上で実行する。

```text
Source Code => [Compiler] => Bytecode => [Virtual Machine] => Machine Code => [CPU]
```

| プラットフォーム  | コンパイラ | 中間コード                  | ランタイム                       |
| --------- | -------- | ---------------------------------- | ----------------------------- |
| Java      | `javac`  | バイトコード(`.class`)                | JVM (Java Virtual Machine)    |
| C# / .NET | `csc`    | CIL (Common Intermediate Language) | CLR (Common Language Runtime) |
| Python    | 組み込み | バイトコード(`.pyc`)                  | Python VM                     |

これにより、プラットフォームに依存する2つの関心事が分離される。コンパイラは1回実行されて移植可能なバイトコードを生成し、仮想マシンだけがプラットフォームごとに実装されればよい。その結果が*write once, run anywhere*(一度書けばどこでも動く)の原則であり、その代償として、プログラムとハードウェアの間に追加の層が入る。

## ジャストインタイムコンパイル {/*#just-in-time-compilation*/}

**ジャストインタイムコンパイラ** (JIT) は、仮想マシンの一部である。バイトコードは最初はインタープリターで実行され、ランタイムはどの部分がどれだけ頻繁に実行されるかを記録する。頻繁に使われる部分、いわゆる*ホットスポット*は、実行時にネイティブの機械語へコンパイルされてキャッシュされ、以降の呼び出しはネイティブの速度で実行される。

```text
Bytecode => [Interpretation + Profiling] => hot code => [JIT Compiler] => cached Machine Code
```

### 利点 {/*#advantages-2*/}

- バイトコードの移植性を保ちながら、**ネイティブに近い速度**を実現する
- 実際のデータ型や分岐頻度といった**実行時の情報**により、静的コンパイラには行えない最適化が可能になる

### 欠点 {/*#disadvantages-2*/}

- **ウォームアップ期間**: 最初の数回の実行は遅く、短時間で終了するプログラムでは目立つ
- **メモリ消費**: プロファイリングデータとコンパイル済みコードが、追加のメモリを占有する
- **予測しにくいタイミング**: 実行中のコンパイルにより実行時間が変動し、リアルタイムシステムでは問題となる

対になるものが**事前コンパイル** (AOT) であり、バイトコードが実行の前に完全に変換される。これによりウォームアップ期間がなくなり、起動時間が短縮されるが、実行時の情報が失われるため、コマンドラインツールやサーバーレス関数のような短時間のプロセスに用いられる。

### JITとAOTの比較 {/*#jit-vs-aot*/}

| 基準                 | ジャストインタイム (JIT)                           | 事前コンパイル (AOT)                          |
| ------------------------- | -------------------------------------------- | -------------------------------------------- |
| 変換の時点      | 実行時、頻繁に使われるコードに対して         | 実行の前に完全に                  |
| 起動時間              | 遅い、ウォームアップ期間あり                          | 速い、ウォームアップなし                             |
| ピーク性能          | 高い、実行時の最適化による           | 限定的、静的な最適化のみ            |
| 最適化の基盤    | 実際の実行時プロファイル(ホットスポット、型)    | 静的なコード解析のみ                    |
| メモリ消費        | 高い、プロファイリングデータとコードキャッシュ        | 低い                                        |
| タイミングの予測可能性     | 変動する                                  | 予測可能                                  |
| 動的な言語機能 | 制限なし                                 | 制限あり、設定が必要           |
| 典型的な用途         | 長時間稼働するサーバーおよびデスクトップアプリケーション | 短時間のプロセス、CLIツール、サーバーレス |

## トランスパイラ {/*#transpiler*/}

**トランスパイラ**(ソースツーソースコンパイラ)は、ソースコードを機械語ではなく、同じ抽象度の別の言語のソースコードに変換する。典型的な例は、JavaScriptにトランスパイルされるTypeScriptと、CSSにトランスパイルされるSassである。

```text
TypeScript => [Transpiler] => JavaScript => [Engine with JIT] => Machine Code
```

---

## 比較 {/*#comparison*/}

| 基準                    | コンパイラ                    | インタープリター                              |
| ---------------------------- | --------------------------- | ---------------------------------------- |
| 変換の時点         | 実行の前に完全に | 実行中、文ごとに |
| 結果                       | 実行可能ファイル             | 別個の成果物なし                     |
| 実行速度              | 高い                        | 低い                                     |
| エラー検出              | コンパイル時             | 実行時、実行されたコードのみ        |
| 開発サイクル            | 遅い、ビルドが必要       | 速い、ただちに実行              |
| プラットフォーム非依存        | 低い、プラットフォームごとに1つのビルド | 高い、インタープリターが必要            |
| 対象システムへの要件 | なし                        | インタープリターのインストールが必要            |
| ソースコードの保護       | 保たれる                       | 通常は保たれない                        |

## 代表的な言語 {/*#typical-representatives*/}

- **機械語にコンパイルされる**: C、C++、Rust、Go、Delphi
- **インタープリター型**: シェルスクリプト、Perl、PHP、Ruby、Python
- **VMとJITを伴うバイトコード**: Java、Kotlin、C#、およびV8のようなエンジン上のJavaScript
