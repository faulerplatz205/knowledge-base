# UDP (User Datagram Protocol)

## 概要 {/*#overview*/}

UDPは[OSI参照モデル](./osi-model.md)のレイヤ4にあたるコネクションレス型のトランスポートプロトコルで、RFC 768で規定されている。IPのパケット配送に加えるものはほとんどなく、ポート番号、長さフィールド、チェックサムのみである。各データグラムは、事前の接続確立、共有状態、確認応答、再送を伴わず、個別にアドレス指定およびルーティングされる。データグラムは送信され、到着するか否かのいずれかとなり、そのどちらであったかが送信側に通知されることはない。UDPのエンドポイントは、IPアドレスとポート番号の組み合わせでアドレス指定される。

---

## 特性 {/*#characteristics*/}

| 項目                  | UDPでの挙動                                                          |
| --------------------- | -------------------------------------------------------------------- |
| 接続                  | コネクションレス、データグラムを即座に送信できる                     |
| 配送                  | 信頼性なし、失われたデータグラムは検知されず再送されない             |
| 順序                  | 保証なし、データグラムは異なる順序で到着することがある               |
| 重複                  | 発生しうる、検出はアプリケーションに委ねられる                       |
| データモデル          | メッセージ指向、1回の送信操作が正確に1つのデータグラムになる         |
| 方向                  | 双方がいつでも送信でき、各データグラムは独立している                 |
| フロー制御            | なし                                                                 |
| 輻輳制御              | なし、送信側がネットワークを溢れさせることがある                     |
| ヘッダサイズ          | 8バイト、固定                                                        |
| ブロードキャスト / マルチキャスト | 対応、1つのデータグラムで多数の受信者に宛てることができる |

オーバーヘッドが小さい代わりに、UDPは何も保証しない。

---

## データグラムヘッダ {/*#datagram-header*/}

ヘッダは各2バイトの4つのフィールドで構成される。

| フィールド     | 用途                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| 送信元ポート   | 送信側アプリケーションのポート、応答が不要な場合は0でもよい                                           |
| 宛先ポート     | 受信側アプリケーションのポート                                                                        |
| 長さ           | ヘッダとペイロードを合わせたバイト長                                                                  |
| チェックサム   | ヘッダ、ペイロード、IPヘッダの一部に対する誤り検出、IPv4ではオプション、IPv6では必須                  |

破損したデータグラムは通知なく破棄される。

---

## コネクションなしの通信 {/*#communication-without-a-connection*/}

3ウェイハンドシェイクの後にはじめてペイロードが続くTCPとは異なり、UDPでは最初のデータグラムがすでにペイロードを運ぶ。最後のデータグラムの後には、どちら側にも接続状態が残らない。

```text
Client                                           Server

  | ---- datagram (query) ---------------------> |   application reads it
  |                                              |
  | <--- datagram (answer) --------------------- |
  |                                              |
  | ---- datagram (query) --------X              |   lost, nobody is informed
  |                                              |
  |  (timeout in the application)                |
  |                                              |
  | ---- datagram (query, repeated) -----------> |
```

- クライアントは、応答が届いてはじめて問い合わせが到着したことを知る。応答がない場合、問い合わせの喪失、応答の喪失、サーバの利用不能のいずれもありうる。
- データグラムの送信元アドレスは、ハンドシェイクによって検証されることがない。そのため偽装されたリクエストが可能であり、DNSやNTPを経由する増幅攻撃はこれを悪用する。
- 閉じたポートに送信されたデータグラムには、ICMPメッセージ *port unreachable* が返される。開いているポートとフィルタされているポートは、通常どちらも無応答のままであるため、UDPポートスキャンでは両者を区別できないことが多い。

## フロー制御・輻輳制御の欠如 {/*#no-flow-or-congestion-control*/}

UDPは、アプリケーションが送信する速度のままデータグラムを転送する。受信バッファが満杯の場合、以降のデータグラムは通知なく破棄される。ネットワークが過負荷の場合、データグラムはルータのキューで失われる。

UDPで大量のデータを送るアプリケーションは、自ら送信レートを制限する必要がある(RFC 8085)。そうしないと、TCPがパケット損失時に速度を下げ、UDPが空いた帯域を奪うため、TCPトラフィックを圧迫する。

## 代表的な用途 {/*#typical-use-cases*/}

### UDPとTCPの比較 {/*#udp-vs-tcp*/}

|          | UDP                                                                                   | [TCP](./tcp.md)                                                               |
| -------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 基準     | 遅れたパケットが無価値である、またはコネクションのオーバーヘッドがペイロードを上回る | 遅延よりも完全性が重要である                                                  |
| 例       | ライブ音声・映像、オンラインゲーム、短い問い合わせ、テレメトリ、マルチキャストによる探索 | ファイル転送、Webページ、電子メール、リモート管理、データベース接続        |

### 主なUDPポート {/*#well-known-udp-ports*/}

| ポート   | サービス      | UDPを使う理由                                                            |
| -------- | ------------- | ------------------------------------------------------------------------ |
| 53       | DNS           | 短い問い合わせ1回と短い応答1回であり、再試行のほうがコネクションより安価 |
| 67/68    | DHCP          | クライアントにまだIPアドレスがなく、ブロードキャストに依存する           |
| 69       | TFTP          | 意図的に最小限の仕様で、ブート環境で使われる                             |
| 123      | NTP           | 再送されたタイムスタンプはすでに古くなっている                           |
| 161/162  | SNMP          | 小さな状態メッセージが多数あり、1件の損失は許容できる                    |
| 443      | QUIC / HTTP/3 | 信頼性はUDPの上位でQUICが実装する                                        |
| 500/4500 | IPsec (IKE)   | 鍵交換とNATトラバーサル                                                  |
| 5060     | SIP           | 音声通話のシグナリング                                                   |

DNSでは2つのプロトコルが併用される。問い合わせと短い応答はUDPで行われ、ゾーン転送やUDPのサイズ制限を超える応答にはTCPが使われる。この制限は512バイト、またはクライアントがEDNS(0)で通知するバッファサイズである。
