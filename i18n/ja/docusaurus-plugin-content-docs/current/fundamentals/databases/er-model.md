# ERモデル

エンティティ・リレーションシップ(ER)モデルは、データベースの構造を高い抽象度で、特定のデータベースシステムに依存せずに記述する概念データモデルである。1976年にピーター・チェンによって提唱された。次の設計ステップで、ERモデルは、テーブル、主キー、外部キーからなる[データベーススキーマ](./database-schema.md)に変換される。

## 基本概念 {/*#core-concepts*/}

### エンティティ {/*#entities*/}

エンティティは**エンティティインスタンス**とも呼ばれ、現実世界または思考の中の一意に識別可能なオブジェクトである。例:特定の顧客や特定の注文。同種のエンティティは**エンティティ型**にまとめられる(例:`Customer`、`Product`、`Order`)。

### 属性 {/*#attributes*/}

属性は、エンティティ型の性質を記述する。

| 種類        | 説明                            | 例                              |
| ----------- | ------------------------------- | ------------------------------- |
| 単純        | 原子的で分割できない値          | `FirstName`、`Age`              |
| 複合        | 下位属性で構成される            | `Address` = (Street, City, ZIP) |
| 多値        | 複数の値を保持できる            | `PhoneNumbers`                  |
| 導出        | 別の属性から計算される          | `BirthDate`から導出される`Age`  |

**キー属性**は各エンティティインスタンスを一意に識別する。例:`CustomerID`。これはデータベーススキーマの主キーになる。

### リレーションシップ {/*#relationships*/}

リレーションシップは、2つ以上のエンティティ型の間の関連を記述する。エンティティと同様に、リレーションシップは**リレーションシップ型**にまとめられる(例:`Customer`が`Order`を*行う*)。リレーションシップ型自体がこの関連を表現するため、ERモデルには外部キーは含まれない。外部キーは、モデルがデータベーススキーマに変換される際に初めて現れる。リレーションシップは独自の属性を持つこともできる(例:`WorksFor`リレーションシップが`StartDate`を持つ場合)。

## カーディナリティ {/*#cardinality*/}

カーディナリティは、あるエンティティのインスタンスが、別のエンティティのインスタンスといくつ関連づけられるかを定義する。

| 種類 | 説明                                      | 例                                                                  |
| ---- | ----------------------------------------- | ------------------------------------------------------------------- |
| 1:1  | 1つのインスタンスがちょうど1つの相手と関連する | 1人が1つのパスポートを持つ                                     |
| 1:N  | 1つのインスタンスが複数の相手と関連する   | 1人の顧客が複数の注文を行う                                         |
| N:M  | 複数のインスタンスが複数の相手と関連する  | 学生は複数のコースに登録する。コースには複数の学生がいる            |

**参加**は、すべてのエンティティインスタンスがリレーションシップに参加しなければならないかどうかをさらに規定する。

- **全面的参加**(必須): すべてのインスタンスが少なくとも1つのリレーションシップに含まれなければならない。例:すべての注文は顧客に属さなければならない。
- **部分的参加**(任意): 参加しないインスタンスがあってもよい。例:すべての顧客が注文を行っているとは限らない。

## 弱エンティティ {/*#weak-entities*/}

**弱エンティティ**は、自身の属性だけでは一意に識別できない。識別のために**強い(所有者の)エンティティ**に依存する。

- 弱エンティティは、所有者の文脈の中でのみ一意となる**部分キー**(識別子)を持つ。
- 弱エンティティを所有者に結びつけるリレーションシップは**識別リレーションシップ**と呼ばれる。
- 弱エンティティは、識別リレーションシップに常に全面的に参加する。

**例:** `OrderItem`は弱エンティティである。その部分キー`LineNumber`は、特定の`Order`の中でのみ一意である。完全な識別子は`(OrderID, LineNumber)`である。

## 表記法 {/*#notation*/}

| 要素                            | 表すもの                                   |
| ------------------------------- | ------------------------------------------ |
| 長方形                          | エンティティ型                             |
| 二重線の長方形                  | 弱エンティティ型                           |
| ひし形                          | リレーションシップ型                       |
| 二重線のひし形                  | 識別リレーションシップ                     |
| 楕円                            | 属性                                       |
| 名前に下線のある楕円            | キー属性                                   |
| 破線の下線のある楕円            | 弱エンティティの部分キー                   |
| 二重線の楕円                    | 多値属性                                   |
| 破線の楕円                      | 導出属性                                   |
| さらに楕円が接続された楕円      | 複合属性とその下位属性                     |
| 一重線                          | 部分的参加                                 |
| 二重線                          | 全面的参加                                 |
| 線の横の`1`、`N`、`M` | カーディナリティ                         |

**重要:** [テーブル図](./database-schema.md#table-diagram)や[UMLクラス図](../uml/class-diagram.md)とは異なり、エンティティの属性はその長方形の内部には書かれない。各属性は独自の楕円を持ち、線でエンティティに接続される。

## よくある間違い {/*#common-mistakes*/}

1. **エンティティの長方形内部の属性:** 列の一覧を持つ長方形は、データベーススキーマのテーブルであり、チェン表記のエンティティ型ではない。
2. **属性としての外部キー:** `Order`の属性としての`CustomerID`は、`places`リレーションシップと重複し、データベーススキーマでのみ外部キーとして存在すべきものである。
3. **チェン図でのUMLの多重度:** チェン表記は、`1..*`や`0..1`のようなUMLの範囲の代わりに`1`、`N`、`M`を用い、最小値は一重線または二重線で表現する。
4. **識別リレーションシップのない弱エンティティ:** 二重線の長方形には、所有者に接続する二重線のひし形が必要である。
