# UML概要

## 概要 {/* #overview */}

**統一モデリング言語(Unified Modeling Language、UML)**は、ソフトウェアシステムをモデリングするための標準化されたグラフィカルな表記法である。**Object Management Group(OMG)**によって管理されている。現行バージョンは**UML 2.5**(2017年以降は2.5.1)で、**14種類のダイアグラム**を定義している。

UMLは実務上の1つの問題に対応する。文章は曖昧であり、ソースコードは議論するには詳細すぎる。ダイアグラムはその中間に位置する。現在議論されているシステムの部分を示し、それ以外は意図的に省略する。

代表的な用途:

- 実装の前に、クライアントとともに要件を記録する
- オブジェクト指向システムの静的な構造を設計する
- チームや部門の境界を越えて、プロセスやアルゴリズムを明確にする
- 引き継ぎや拡張ができるように、既存のシステムを文書化する
- コードを読まずにアーキテクチャ上の決定について議論する

## UMLとは何か、何でないか {/* #what-uml-is-and-what-it-is-not */}

UMLは次のようなものである。

- **表記法:** 定義された意味を持つ記号の固定された語彙
- **標準:** すべての企業とすべてのツールで、同じ記号が同じ意味を持つ
- **言語に依存しない:** クラス図はJava、C#、TypeScriptについて何も述べない
- **選択的:** すべてのダイアグラムは1つの側面をモデル化し、システム全体をモデル化することはない

UMLは次のようなものではない。

- **方法論やプロセスモデル:** UMLは、どのダイアグラムを*いつ*、誰が作成するかについて何も述べない。それはプロセスモデル([スクラム](../../projectmanagement/scrum.md)、Vモデル、統一プロセス)によって決まる。UMLは表記法であり、プロセスモデルが方法論である。
- **プログラミング言語:** モデルからコードの骨組みを生成できるが、ダイアグラムは実行可能ではなく、実装の代わりにはならない。
- **完全な記述:** モデルは常に単純化されたものである。コードに含まれるすべてを含むダイアグラムには、コードに対する利点がない。
- **データモデリングの標準:** [ERモデル](../databases/er-model.md)はデータベース設計のための別個の表記法であり、クラス図が似た事実を表現できるとしてもUMLの一部ではない。
- **品質の保証:** 不適切に分割されたシステムは、どれほど綺麗に描かれても不適切に分割されたままである。

この分野で最も多い誤解は、UMLを方法論として扱うことである。ユースケース図を描けることは、要件が*いつ*収集され、*誰が*承認し、*どのように*プロジェクト計画に組み込まれるかについて何も語らない。

## 14種類のダイアグラム {/* #the-14-diagram-types */}

UML 2.5はダイアグラムを2つの最上位グループに分ける。**構造図**はシステムが何で構成されているかを記述し、**振る舞い図**はシステムが何をするかを記述する。**相互作用図**は振る舞い図のサブグループであり、参加者間のメッセージのやり取りを通じて振る舞いを記述する。

| #   | ダイアグラム                                              | グループ                | 答える問い                                                                            |
| --- | --------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------- |
| 1   | [クラス図](./class-diagram.md)                            | 構造                    | どのクラスが存在し、何を含み、どのように関連しているか。                              |
| 2   | [オブジェクト図](./further-uml-diagrams.md)               | 構造                    | ある時点で、どのような具体的なオブジェクトと値が存在するか。                          |
| 3   | [パッケージ図](./further-uml-diagrams.md)                 | 構造                    | 大規模なモデルはどのようにグループに分割され、何が何に依存しているか。                |
| 4   | [コンポーネント図](./component-diagram.md)                | 構造                    | ソフトウェアはどのような交換可能な部品で構成され、それらはどのようなインターフェースを持つか。 |
| 5   | [複合構造図](./further-uml-diagrams.md)                   | 構造                    | 単一の要素は、協調する部品からどのように内部的に構築されているか。                    |
| 6   | [配置図](./deployment-diagram.md)                         | 構造                    | どのアーティファクトがどのノード上で動作し、それらはどのように接続されているか。      |
| 7   | [プロファイル図](./further-uml-diagrams.md)               | 構造                    | UML自体は、ある領域に向けてどのように拡張されるか(ステレオタイプ、タグ付き値)。       |
| 8   | [ユースケース図](./use-case-diagram.md)                   | 振る舞い                | システムは何をし、どのアクターのためのものか。                                        |
| 9   | [アクティビティ図](./activity-diagram.md)                 | 振る舞い                | 分岐、ループ、並列作業を含め、どの順序でステップが実行されるか。                      |
| 10  | [ステートマシン図](./state-machine-diagram.md)            | 振る舞い                | オブジェクトはどの状態を取り得て、どのイベントが遷移を引き起こすか。                  |
| 11  | [シーケンス図](./sequence-diagram.md)                     | 振る舞い / 相互作用     | オブジェクトはどのメッセージを、どの時系列順で交換するか。                            |
| 12  | [コミュニケーション図](./further-uml-diagrams.md)         | 振る舞い / 相互作用     | 誰が誰と通信し、参加者はどのように結び付いているか。                                  |
| 13  | [タイミング図](./further-uml-diagrams.md)                 | 振る舞い / 相互作用     | 状態は時間軸に沿ってどのように変化し、どのタイミング制約が適用されるか。              |
| 14  | [相互作用概要図](./further-uml-diagrams.md)               | 振る舞い / 相互作用     | 複数の相互作用は、どのように1つの全体的なフローに統合されるか。                       |

すべてに共通する記号の集合は、[表記の基礎](./uml-notation-basics.md)で説明されている。

## 構造図 {/* #structure-diagrams */}

構造図は、静止した状態のシステムを示す。時間は関係せず、実行順序も含まない。

- **クラス図:** オブジェクト指向設計の中心的なダイアグラム。属性と操作を持つクラスが、関連、集約、コンポジション、汎化、依存によって結ばれ、可視性と多重度が注記される。
- **オブジェクト図:** クラス図のスナップショット。クラス`Order`の代わりに、実際の属性値を持つオブジェクト`order42`を示す。複雑な関連の集合を例で具体化するのに有用である。
- **パッケージ図:** モデル要素をパッケージにまとめ、その間の依存関係を示す。アーキテクチャの意図した階層構造を可視化し、循環依存を明らかにする。
- **コンポーネント図:** 提供インターフェースと要求インターフェースを持つコンポーネント(ボールとソケットの表記)。ソフトウェアが交換可能な単位にどのように分割されるかを記述する。
- **複合構造図:** 単一のクラシファイアの内部を見て、その部品、ポート、コネクタを示す。組み込みシステムやシステムズエンジニアリング以外ではほとんど使われない。
- **配置図:** ノード(ハードウェアまたは実行環境)、そこに配置されるアーティファクト、およびそれらの間の通信経路。ソフトウェア設計から運用への橋渡しとなる。
- **プロファイル図:** UML自体の拡張メカニズム。ステレオタイプ、タグ付き値、制約によって、言語を特定の領域に適合させる。例えば`«entity»`や`«controller»`がある。

## 振る舞い図 {/* #behavioural-diagrams */}

振る舞い図は、時間の経過とともに何が起こるかを示す。どのような順序で、何をきっかけに、どのような結果になるかである。

- **ユースケース図:** アクター、ユースケース、システム境界。意図的に粗く、プロセスの記述ではなく、要件の目次として機能する。
- **アクティビティ図:** アクションを通る制御フロー。デシジョン、マージ、フォーク、ジョインを持ち、必要に応じてスイムレーンにまとめられる。従来のフローチャートに最も近いUMLのダイアグラムで、ビジネスプロセスにもアルゴリズムにも適している。
- **ステートマシン図:** 単一のオブジェクトのライフサイクル。状態、イベントによって引き起こされる遷移、ガード、エントリーアクションとイグジットアクション。同じ入力に対して、オブジェクトが履歴に応じて異なる反応をする場合に選ばれるダイアグラムである。

### 相互作用図 {/* #interaction-diagrams */}

4つの相互作用図はすべて、同じ対象を異なる角度から記述する。メッセージを交換する参加者である。

- **シーケンス図:** ライフラインが水平に配置され、時間が下向きに流れ、メッセージはライフライン間の矢印で表される。時系列順に最も重点が置かれており、4つの中で最も広く使われている。
- **コミュニケーション図:** 同じ情報を、結び付いた参加者のネットワークとして配置したもの。メッセージは位置による順序ではなく、番号で順序付けされる。*誰が誰と接続されているか*に最も重点が置かれている。
- **タイミング図:** 参加者の状態変化を、明示的な時間軸に沿ってプロットしたもの。リアルタイムシステムや組み込みシステムなど、継続時間とタイミング制約が重要な場面で使われる。
- **相互作用概要図:** ノードが単一のアクションではなく、完全な相互作用であるアクティビティ図。複数のシーケンス図を1つの全体的なフローに配置するために使われる。

シーケンス図とコミュニケーション図は意味的にほぼ等価であり、多くのツールが一方から他方へ自動的に変換する。

## 適切なダイアグラムの選択 {/* #choosing-the-right-diagram */}

| 答える必要がある問い                                          | 適したダイアグラム        |
| ------------------------------------------------------------- | ------------------------- |
| 誰がシステムを使い、何のために使うか。                        | ユースケース図            |
| プロセスのステップはどの順序で実行されるか。                  | アクティビティ図          |
| コーディングを始める前に、アルゴリズムはどう構成されるか。    | アクティビティ図          |
| どのクラスが必要で、どのように関連しているか。                | クラス図                  |
| 具体的なケースでデータはどのように見えるか。                  | オブジェクト図            |
| ユースケースを実現するために、オブジェクトはどう協調するか。  | シーケンス図              |
| 注文、チケット、デバイスはどの状態を経由するか。              | ステートマシン図          |
| システムは交換可能なモジュールにどう分割されるか。            | コンポーネント図          |
| どのサーバー、どのコンテナ、どのクライアントか。              | 配置図                    |
| 大規模なモデルをどのように整理しておくか。                    | パッケージ図              |
| どのタイミング制約を守る必要があるか。                        | タイミング図              |

選択のための経験則:

- **1つの問いに1つのダイアグラム。** 3つの問いに同時に答えるダイアグラムは、通常どれにも明確に答えない。
- **構造と振る舞いのどちらが先か。** 要件は振る舞い(ユースケース、アクティビティ)から始まり、実装は構造(クラス、コンポーネント)から始まる。
- **抽象度を一定に保つ。** ビジネス用語とデータベースのカラムが混在するダイアグラムは、どちらの読者にとっても使いにくい。
- **誰も読まないダイアグラムは無駄である。** 読者によって詳細度が決まる。クライアントにはユースケース図とアクティビティ図、開発者にはクラス図とシーケンス図、運用担当者には配置図が必要である。
- **保守コストが重要である。** コードと同期しなくなったダイアグラムは、信頼されながら誤っているため、ダイアグラムがないよりも悪い。

実際には、少数のダイアグラムの種類がほとんどの作業を担う。クラス図、アクティビティ図、ユースケース図、シーケンス図、ステートマシン図である。それ以外の種類は専門的であり、固有の問いが生じたときにのみ現れる。

## ソフトウェア設計プロセスにおけるUML {/* #uml-in-the-software-design-process */}

UMLは単一のプロセスモデルに縛られていないが、そのダイアグラムは開発のフェーズに自然に対応する。

| フェーズ              | 問い                                   | 代表的なダイアグラム                        |
| --------------------- | -------------------------------------- | ------------------------------------------- |
| 要件分析              | システムは何をするべきか。             | ユースケース、アクティビティ                |
| ドメインモデリング    | ドメインにどの概念が存在するか。       | クラス(ドメインモデルとして)、オブジェクト  |
| 設計                  | 解決策はどのように構築されるか。       | クラス、シーケンス、ステートマシン          |
| アーキテクチャ        | システムはどのように分割・分散されるか。 | コンポーネント、パッケージ、配置          |
| 実装                  | 設計はどのように実現されるか。         | コードの骨組みとしてのクラス図              |
| テスト                | どのフローをカバーする必要があるか。   | アクティビティ、シーケンス、ステートマシン  |
| ドキュメント          | システムはどのように動作するか。       | 上記すべて、要点に絞ったもの                |

ソフトウェア設計におけるモデリングは、3つの目的に役立つ。

- **コミュニケーション:** 異なる背景を持つ人々のための共通のイメージ
- **分析:** 実装される前に、矛盾や欠落が可視化される
- **ドキュメント:** ソースコードをすべて読まなくても、システムを理解できる

## よくある間違い {/* #common-mistakes */}

1. **方法論として扱われるUML:** UMLが定義するのは記号であり、手順ではない。手順はプロセスモデルから来る。
2. **相互作用図が3つ目の主要グループとして数えられる:** 相互作用図は振る舞い図のサブグループである。
3. **アクティビティ図とシーケンス図の混同:** アクティビティ図はアクション間の制御フローを示し、シーケンス図はオブジェクト間のメッセージを示す。
4. **クラス図とオブジェクト図の混同:** クラス図は型を示し、オブジェクト図は具体的な値を持つインスタンスを示す。
5. **プロセスの記述として使われるユースケース図:** ユースケース図はシステムが提供するものを列挙する。ユースケース内のフローはアクティビティ図に属する。
6. **UMLのダイアグラムとして数えられるERモデル:** ERモデルはデータモデリングのための別個の表記法である。
7. **すべてをモデル化する:** システム全体を詳細にすべて網羅するモデルは、得られる利益よりもコストが大きく、最初の変更で古くなる。
8. **その場で考案された表記法:** UMLの価値は、記号がどこでも同じ意味を持つことにある。独自に考案した矢印は、まさにそれを損なう。
