# UML表記の基礎

## 概要 {/*#overview*/}

いくつかの表記要素は、図の種類に関係なく、ほぼすべてのUML図に現れる。可視性マーカー、多重度、キーワードとステレオタイプ、ノート、制約、図のフレームは、[クラス図](./class-diagram.md)、[コンポーネント図](./component-diagram.md)、[ステートマシン図](./state-machine-diagram.md)のいずれでも同じ意味を持つ。

---

## 可視性 {/*#visibility*/}

可視性は、誰がフィーチャー（属性、操作、またはパッケージやコンポーネントのメンバー）にアクセスできるかを表す。フィーチャー名の直前に1文字で書く。

| マーカー | 名称      | アクセスが許可される対象                            | 典型的な用途                      |
| -------- | --------- | --------------------------------------------------- | --------------------------------- |
| `+`    | public    | 分類子を参照できるすべての要素                      | クラスのインターフェース          |
| `-`    | private   | 分類子自身のみ                                      | 内部状態、ヘルパー操作            |
| `#`    | protected | 分類子とその特化（サブクラス）                      | サブクラスのための拡張ポイント    |
| `~`    | package   | 同じパッケージ内のすべての要素                      | 1つのモジュール内での協調         |

さらに2つのマーカーは、可視性と混同されやすいが、別のことを表す。

- 名前の前の `/` は**派生**フィーチャーを示し、その値は他のフィーチャーから計算される（`dateOfBirth` から `/ age`）。
- 下線付きの名前は**静的**フィーチャーを示し、個々のオブジェクトではなく分類子に属する。

次のクラスは、これらのマーカーをすべて使っている。プレーンテキストでは下線を表示できないため、静的属性 `MAX_LIMIT` は代わりに `(static)` で示している。

```text
┌──────────────────────────────────────┐
│               Account                │
├──────────────────────────────────────┤
│ + accountNumber: String              │
│ - balance: Decimal                   │
│ # owner: Customer                    │
│ ~ auditLog: LogEntry [0..*]          │
│ / available: Decimal                 │
│ + MAX_LIMIT: Decimal = 5000 (static) │
├──────────────────────────────────────┤
│ + deposit(amount: Decimal)           │
│ + withdraw(amount: Decimal): Bool    │
│ - validate(amount: Decimal): Bool    │
└──────────────────────────────────────┘
```

UMLでは可視性は任意である。マーカーがない場合は、多くのツールが既定でpublicとするものの、*public*ではなく*未指定*を意味する。

## 多重度 {/*#multiplicities*/}

多重度は、関連の一方の端に何個のオブジェクトが参加しうるか、または属性が何個の値を保持しうるかを表す。関連端の横に、または属性の型の後ろの角括弧内に書く。

| 表記     | 範囲                 | 読み方                                             |
| -------- | -------------------- | -------------------------------------------------- |
| `1`      | ちょうど1            | 必須、ちょうど1つのオブジェクト                    |
| `0..1`   | 0または1             | 任意、多くても1つのオブジェクト                    |
| `*`      | 0から無制限          | `0..*` の短縮形で、下限1が暗黙に付くわけではない  |
| `0..*`   | 0から無制限          | 任意、いくつでもよい                               |
| `1..*`   | 1から無制限          | 必須、少なくとも1つ                                |
| `n..m`   | nからm               | 明示的な範囲。例: `2..4`                          |
| `5`      | ちょうど5            | 固定数                                             |
| `1..3,7` | 1から3、またはちょうど7 | 複数の範囲                                      |

多重度の読み書きに関する規則:

- 多重度は、それが説明するクラスの隣に置き、反対側の端にある1つのオブジェクトに、そのクラスのオブジェクトがいくつ結び付いているかを表す。
- 下限は、関係が任意（`0`）か必須（`1` 以上）かを決める。
- 上限は、実装が単一の参照（`1`）を保持するか、コレクション（`*`）を保持するかを決める。
- 省略された多重度は形式的には未定義であり、ほとんどのツールや教科書は `1` として読む。

### 関連の読み方 {/*#reading-an-association*/}

```text
┌──────────────┐ 1          0..* ┌──────────────┐
│   Customer   ├─────────────────┤    Order     │
└──────────────┘   places   ▶    └──────────────┘
```

この文は、一方の端のクラス、関連名、もう一方の端の多重度から組み立てられ、その後、逆方向でも繰り返される。

- `Customer` は **0個以上**の `Order` オブジェクトを置く。
- `Order` は、**ちょうど1つ**の `Customer` によって置かれる。

関連名の後ろにある小さな塗りつぶしの三角形 `▶` は、**読み取り方向**のマーカーである。名前がどちらの方向で文になるかを示し、それ以上の意味は持たない。三角形は任意であり、なければ名前は左から右、または上から下へと読まれる。

## キーワードとステレオタイプ {/*#keywords-and-stereotypes*/}

ギュメ（`«…»`）で囲んだラベルは、新しい図形を考案することなく、既存のモデル要素に意味を付け加える。要素名の上または前に書く。

```text
┌──────────────────────┐
│     «interface»      │
│      Printable       │
├──────────────────────┤
│ + print(): void      │
└──────────────────────┘
```

ギュメが使えない場合は、二重の山括弧 `<<interface>>` が代用として認められており、このため実際には両方の表記が現れる。

この形式で書かれるラベルは2種類ある。

- **キーワード**はUML自体によってあらかじめ定義されている。メタクラスまたはその固定された変種に名前を付け、予約されており、先に何かを宣言することなく使える。
- **ステレオタイプ**はモデラーまたはツールによって定義され、要素をドメイン、技術、または社内標準に適合させる。定義された場所でのみ意味を持つ。

UMLがあらかじめ定義しているキーワード:

| キーワード                 | 適用対象              | 意味                                       |
| -------------------------- | --------------------- | ------------------------------------------ |
| `<<interface>>`            | クラス                | 実装なしで操作を宣言する                   |
| `<<enumeration>>`          | クラス                | 固定されたリテラルの集合を持つ型           |
| `<<include>>`              | ユースケースの関係    | あるユースケースが常に別のものを使う       |
| `<<extend>>`               | ユースケースの関係    | あるユースケースが別のものを任意に拡張する |
| `<<use>>`                  | 依存関係              | クライアントがサプライヤを必要とする       |
| `<<create>>`               | メッセージ            | メッセージが受信側のオブジェクトを生成する |
| `<<destroy>>`              | メッセージ            | メッセージが受信側のオブジェクトを破棄する |
| `<<device>>`               | ノード                | 物理的なハードウェア                       |
| `<<executionEnvironment>>` | ノード                | デバイス上のランタイム環境                 |
| `<<artifact>>`             | アーティファクト      | 配置可能なファイル                         |

ステレオタイプはこれらの上に重ねられ、どこかで定義されている限り同様に正当である。小規模なプロジェクトでは、使用しているステレオタイプを列挙した短い凡例で十分である。分析モデリングの古典的な例は、永続的な業務オブジェクトを表す `<<entity>>`、システム境界にある要素を表す `<<boundary>>`、調整を行う要素を表す `<<control>>` である。

## ノートとコメント {/*#notes-and-comments*/}

ノートは、角が折れた長方形で、コメント対象の要素に破線で結び付けられる。意味は持たず、読み手のための自由なテキストである。

```text
┌──────────────┐         ┌───────────────────────────┐
│   Invoice    │- - - - -│ Net amounts only, VAT is  └─┐
└──────────────┘         │ added by the tax service.   │
                         └─────────────────────────────┘
```

ノートの使い方の指針:

- ノートは*何を*ではなく*なぜ*を説明する。要素名を文章で繰り返しても何も付け加わらない。
- ノートは、複数の破線で複数の要素に結び付けられる。
- 前提、未解決の問い、根拠を伴う判断が典型的な内容である。
- ノートを通じてはじめて理解できるモデルには、通常、構造上の問題がある。

## タグ付き値 {/*#tagged-values*/}

タグ付き値は、名前付きのプロパティをモデル要素に付与するもので、波括弧内に `name = value` として書かれる。タグ付き値は通常ステレオタイプによって導入され、ステレオタイプがどのタグが存在し、何を意味するかを定義する。

```text
┌───────────────────────────────────┐
│             «entity»              │
│             Customer              │
│ {table = "CUST", schema = "crm"}  │
└───────────────────────────────────┘
```

代表的な用途:

- 技術的なマッピング情報。たとえば、永続化のためのテーブル名や列名
- `{author = "Team A", version = "1.2", status = "reviewed"}` などのプロセスのメタデータ
- `{maxResponseTime = "200ms"}` などの非機能要件
- モデル駆動のツールチェーンが利用するコード生成のヒント

複数のタグ付き値は、1対の波括弧内でカンマで区切るか、要素に結び付けたノートに別々の行として書く。

## 制約 {/*#constraints*/}

制約は、モデルが妥当であるために成立しなければならない条件である。波括弧で囲み、要素に直接、または結び付けたノートに書く。

| 制約                   | 適用対象           | 意味                                                    |
| ---------------------- | ------------------ | ------------------------------------------------------- |
| `{readOnly}`           | 属性、関連端       | 値は一度設定され、その後は変更されない                  |
| `{abstract}`           | クラス、操作       | 実装がない。斜体の代替                                  |
| `{xor}`                | 2つの関連          | 2つの関連のうち、ちょうど1つだけがインスタンス化されうる |
| `{complete, disjoint}` | 汎化セット         | すべてのオブジェクトがちょうど1つのサブクラスに属する   |

自由記述の制約も同様に有効であり、実際にははるかに一般的である。

```text
┌──────────────┐         ┌─────────────────────────────┐
│   Account    │- - - - -│ {balance >= overdraftLimit} └─┐
└──────────────┘         └───────────────────────────────┘
```

### OCL {/*#ocl*/}

形式的に述べる必要がある条件のために、OMGは**Object Constraint Language**（OCL）を定義している。これはUMLと併用される別個のテキスト言語である。上のノートの条件をOCLで書くと次のようになる。

```text
context Account
  inv: balance >= overdraftLimit
```

`context` は条件が適用されるクラスを指定し、`inv` は不変条件、すなわち常に成立していなければならない条件を示す。実際には、波括弧内の非形式的な条件で通常は十分であり、重要なのは正しい要素に結び付けられていることである。

## ロール名とナビゲーション可能性 {/*#role-names-and-navigability*/}

関連端には**ロール名**を付けることができ、そのクラスがその関係で果たす役割を表す。ロール名は、それが説明する端に小文字で書かれ、実装では属性名になる。

```text
┌──────────────┐ employer        employee ┌──────────────┐
│   Company    ├──────────────────────────┤    Person    │
└──────────────┘ 1                    0..*└──────────────┘
```

読み方: `Person` は、ロール `employer` としてちょうど1つの `Company` を持ち、`Company` は、ロール `employee` として0個以上の `Person` オブジェクトを持つ。実装では、`Person` にフィールド `employer` が、`Company` にコレクション `employee` が置かれる。

ロール名は、2つのクラスが複数回接続される場合や、クラスが自分自身と関連付けられる場合に不可欠となる。

```text
┌────────────────────┐
│      Employee      │
└──┬──────────────┬──┘
   │ 0..1         │ 0..*
   │ supervisor   │ subordinate
   └──────────────┘
```

読み方: `Employee` は、ロール `supervisor` として高々1つの他の `Employee` を持ち、ロール `subordinate` として0個以上を持つ。

関連に方向を与える要素:

- **読み取り方向（`▶`）:** 関連名の隣にあり、純粋に読むための補助
- **ナビゲーション可能性（開いた矢じり）:** 一方の端にあり、その端に他方から到達できる
- **ナビゲーション不可（小さな×印 `x`）:** 一方の端にあり、その端に明示的に到達できない
- **矢じりなし:** ナビゲーション可能性は未指定で、実際には*双方向にナビゲーション可能*として読まれる

## 命名規則 {/*#naming-conventions*/}

以下の規則はUML仕様の一部ではないが、実際にはほぼ普遍的である。

| 要素             | 規則                              | 例                            |
| ---------------- | --------------------------------- | ----------------------------- |
| クラス           | PascalCase、単数形の名詞          | `Invoice`、`CustomerAccount`  |
| インターフェース | PascalCase、しばしば形容詞        | `Printable`、`Comparable`     |
| 属性             | camelCase、名詞                   | `orderDate`、`totalAmount`    |
| 操作             | camelCase、動詞 + 目的語          | `calculateTotal()`            |
| ロール名         | camelCase、役割を表す名詞         | `employer`、`lineItems`       |
| 関連名           | 三人称単数の動詞                  | `places`、`contains`          |
| パッケージ       | 小文字、単数形                    | `billing`、`reporting`        |
| ユースケース     | 動詞 + 目的語の不定詞形           | `Place order`                 |
| アクター         | 役割を表す名詞で、個人名は用いない | `Customer`、`Payment Service` |
| アクション       | 動詞 + 目的語の不定詞形           | `Validate order`              |
| 状態             | 形容詞または分詞                  | `Paid`、`Awaiting approval`   |
| コンポーネント   | サービスを表す名詞                | `OrderService`                |
| ノード           | デバイスまたはホストを表す名詞    | `Application Server`          |

すべてに当てはまる規則が2つある。

- モデル全体で1つの概念には1つの名前を用いる。ある図で `Customer` と名付けられたクラスは、次の図では `Client` ではない。
- モデルの言語は、モデル全体で一度だけ選び、混在させない。

## 図のフレーム {/*#diagram-frames*/}

すべてのUML図は、フレームの中に描くことができる。左上隅に、図の種類と図の名前を記した五角形のタグを持つ長方形である。

```text
┌─────────────────────────────────────────────┐
│ sd Place Order ╱                            │
├───────────────┘                             │
│                                             │
│          (contents of the diagram)          │
│                                             │
└─────────────────────────────────────────────┘
```

フレームのヘッダは `<kind> <name>` というパターンに従い、任意でパラメータを付ける。一般的な種類のキーワードを、短い形式とツールが受け付ける長い形式で示す。

| 短い形式 | 長い形式        | 図                              |
| -------- | --------------- | ------------------------------- |
| `sd`  | `interaction`   | シーケンス、コミュニケーション、タイミング |
| `act` | `activity`      | アクティビティ                  |
| `stm` | `state machine` | ステートマシン                  |
| `cmp` | `component`     | コンポーネント                  |
| `dep` | `deployment`    | 配置                            |
| `cls` | `class`         | クラス                          |
| `uc`  | `use case`      | ユースケース                    |
| `pkg` | `package`       | パッケージ                      |

フレームが任意ではなく必須となる場合:

- [シーケンス図](./sequence-diagram.md)では、フレームが標準であり、入れ子の複合フラグメント（`alt`、`opt`、`loop`、`ref`）はそれぞれ独自のフレームとして描かれる
- ある図が別の図から参照される場合は常に、参照がフレーム名を使うため
- 複数の図が1ページまたは1つの文書に現れ、区別する必要がある場合は常に

1ページに1つの図だけがある場合、フレームは通常省略され、見出しがその代わりとなる。

## コードへの対応 {/*#mapping-to-code*/}

| 表記                   | プログラムの構文                             |
| ---------------------- | -------------------------------------------- |
| `+`                    | `public`                                     |
| `-`                    | `private`                                    |
| `#`                    | `protected`                                  |
| `~`                    | Javaではパッケージプライベート、C#では `internal` |
| 下線付きの名前         | `static`                                     |
| 名前の前の `/`         | 値を計算するゲッターで、保存されたフィールドはない |
| `1`                    | `null` であってはならないフィールド          |
| `0..1`                 | null許容のフィールド、`Optional<T>`、`T?`          |
| `{readOnly}`           | `final`、`readonly`、`const`                 |
| `<<interface>>`        | `interface`                                  |
| `<<enumeration>>`      | `enum`                                       |
| `{abstract}`           | `abstract class`                             |
| ロール名               | 参照を保持するフィールドの名前               |
| OCLの `inv`           | コンストラクタとすべてのセッターでのチェック |

## よくある間違い {/*#common-mistakes*/}

1. **`-` をダッシュと取り違えること:** 先頭の `-` は可視性マーカーの*private*であり、装飾ではない。privateな属性は他のクラスからアクセスできない。
2. **`*` を「多数、ただし少なくとも1つ」と読むこと:** `*` は `0..*` を意味する。少なくとも1つのオブジェクトが必要な場合の表記は `1..*` である。
3. **多重度を誤った端に置くこと:** クラスの隣にある多重度は、反対側の端から見て、*そのクラス*のオブジェクトがいくつ参加するかを表す。
4. **波括弧とギュメの取り違え:** `{...}` は制約またはタグ付き値を、`«...»` はキーワードまたはステレオタイプを保持し、両者は交換できない。
5. **定義のないステレオタイプ:** どこにも説明されていない、考案されたステレオタイプは、情報ではなく装飾である。
6. **クラス名と同一のロール名:** `Customer` 上のロール `customer` は何も付け加えない。ロール名は、型より多くを語る場合にのみ書く価値がある。
7. **モデルの意味を担うノート:** システムが強制しなければならない条件は、文章のノートではなく制約に属する。
8. **読み取り方向とナビゲーション可能性の混同:** 塗りつぶした三角形 `▶` は文に関わり、開いた矢じりはアクセスに関わる。
9. **言語の混在と一貫性のない名前:** 同じ概念に2つの名前があると、読み手の頭の中に2つの概念が生まれる。
10. **あらゆる場所で可視性を省略し、すべてをpublicとして実装すること:** 未指定の可視性は、判断ではなくモデルの欠落である。
