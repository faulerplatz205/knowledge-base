# アクティビティ図

## 概要 {/*#overview*/}

アクティビティ図は、**振る舞い**を表すUML図である。プロセスを、制御フローで結ばれたアクションの連なりとして記述し、分岐、ループ、並行して実行されるステップも含められる。

代表的な用途:

- 複数の部門やシステムにまたがる業務プロセスのモデリング
- 実装前の、言語に依存しないアルゴリズムの記述
- 単一のユースケース内のステップの詳細化
- 非技術系のステークホルダーとレビューするための既存ワークフローの文書化

---

## 表記法 {/*#notation*/}

| 要素                | 表記                                   | 意味                                                               |
| ------------------- | -------------------------------------- | ------------------------------------------------------------------ |
| 初期ノード          | 塗りつぶした円 `●`                     | アクティビティの開始、1つの図につき必ず1つ                         |
| アクション          | 角丸の長方形                           | 分割できない1つの作業ステップ、*動詞 + 目的語*で命名する           |
| アクティビティ(呼び出し) | レーキ記号付きの角丸長方形      | 別の図で詳細化されるステップ                                       |
| 制御フロー          | 実線の矢印                             | 実行順序、あるアクションから次のアクションへ向かう                 |
| ガード              | フロー上に記述した `[condition]`               | そのフローを進むことができる条件                                   |
| デシジョンノード    | ひし形、入力1つ・出力複数              | 分岐、出力フローは互いに排他的なガードを持つ                       |
| マージノード        | ひし形、入力複数・出力1つ               | 代替の経路を再び合流させる、待機は**しない**                       |
| フォーク            | 太いバー、入力1つ・出力複数            | フローを並行フローに分割する                                       |
| ジョイン            | 太いバー、入力複数・出力1つ             | すべての入力フローが到着するまで待機する                           |
| アクティビティ終了  | 二重丸（塗りつぶした円を輪で囲む） `◉` | 実行中の経路も含め、アクティビティ全体を終了する                   |
| フロー終了          | ×印付きの円 `⊗`                      | そこに到達した経路のみを終了し、アクティビティは継続する           |
| オブジェクトノード  | フロー上の単純な長方形                 | あるアクションから次のアクションへ渡されるデータ                   |
| パーティション      | ラベル付きのレーン                     | そのレーン内のアクションに責任を持つアクター、ロール、システム     |
| ノート              | 破線につながる角折れ長方形             | 意味を持たないコメント                                             |

図を読みやすく保つための命名規則:

- アクションは*動詞 + 目的語*で命名する: `Validate order` とし、`Order` や `Validation` としない
- ガードは角括弧で囲み、フロー上に直接記述し、アクション内には書かない
- 分岐の残りのケースは、否定条件ではなく `[else]` とラベル付けする

## 構成要素 {/*#building-blocks*/}

### シーケンス {/*#sequence*/}

次々に実行されるアクション。フローは初期ノードを出て、すべてのアクションを通過し、アクティビティ終了ノードで終わる。

```text
          ●
          │
          ▼
 ╭─────────────────╮
 │  Receive order  │
 ╰─────────────────╯
          │
          ▼
 ╭─────────────────╮
 │   Check stock   │
 ╰─────────────────╯
          │
          ▼
          ◉
```

### デシジョンとマージ {/*#decision-and-merge*/}

デシジョンノードはフローを代替経路に分岐させる。出力フローのうちちょうど1つが選ばれるため、ガードは互いに排他的であり、考えられるすべてのケースを網羅しなければならない。マージノードは代替経路を再び合流させ、到着したすべての経路をそのまま通し、待機することはない。

```text
                    │
                    ▼
              ╱───────────╲
             ╱   amount    ╲
             ╲   > 100 ?   ╱
              ╲───────────╱
               │         │
        [yes]  │         │ [no]
        ┌──────┘         └──────┐
        │                       │
        ▼                       ▼
╭───────────────╮       ╭───────────────╮
│Apply discount │       │  Keep price   │
╰───────────────╯       ╰───────────────╯
        │                       │
        └──────┐         ┌──────┘
               ▼         ▼
              ╱───────────╲
             ╱             ╲
             ╲             ╱
              ╲───────────╱
                    │
                    ▼
```

結果が3つ以上の分岐では、ガード付きフローを複数持つ1つのデシジョンノードを用いる。これは `if / else if / else` または `switch` 文に対応する。マージノードは、合流する経路の数にかかわらず、1つのひし形のままである。

### ループ {/*#loop*/}

ループは、図中の前方の地点に戻る制御フローである。以下の図ではデシジョンがアクションの*後*にあるため、本体は少なくとも1回実行され、`do … while` ループに対応する。

```text
              ●
              │
              ▼
     ╭─────────────────╮
┌───►│   Read record   │
│    ╰─────────────────╯
│             │
│             ▼
│       ╱───────────╲
│      ╱    more     ╲
│      ╲  records ?  ╱
│       ╲───────────╱
│        │         │
│  [yes] │         │ [no]
└────────┘         ▼
                   ◉
```

デシジョンをアクションの*前*に置き、戻り辺をその上から入れると、同じ構造が、本体が0回実行されうる前判定の `while` ループになる。

### フォークとジョイン {/*#fork-and-join*/}

フォークは1つのフローを、並行して実行される複数のフローに分割する。ジョインはすべての入力フローが到着するまで待機し、その後はじめて単一のフローとして継続する。ジョインがなければ、並行するステップが実行中のままアクティビティが終了しうる。

```text
                  │
                  ▼
        ━━━━━━━━━━━━━━━━━━━━━
        │                   │
        ▼                   ▼
╭─────────────────╮ ╭─────────────────╮
│  Reserve stock  │ │   Charge card   │
╰─────────────────╯ ╰─────────────────╯
        │                   │
        ▼                   ▼
        ━━━━━━━━━━━━━━━━━━━━━
                  │
                  ▼
```

UMLにおける並行とは、*規定された順序がない*ことを意味し、必ずしも*別々のプロセッサで同時に*実行されることを意味しない。2つの分岐が2つのスレッドで動くのか、任意の順序で逐次的に動くのかは、実装上の判断である。

---

## パーティション(スイムレーン) {/*#partitions-swimlanes*/}

パーティションは、アクションを、それを実行するアクター、ロール、部門、システムごとにまとめる。レーンは縦にも横にも描くことができ、フローはレーンの境界をまたぐ。

押さえておくべき規則:

- アクションはちょうど1つのレーンに属し、レーンは*誰がこれを行うか*への答えである
- デシジョンノードとマージノードは、判断を下すアクターのレーンに属する
- フォークは複数のレーンにまたがってよく、異なるアクターによる並行作業はまさにこの形で表される
- レーンをまたぐ回数は、プロセスにおける調整工数の大まかな目安となる

## コードへの対応 {/*#mapping-to-code*/}

| アクティビティ図                       | プログラムの構文                                 |
| -------------------------------------- | ------------------------------------------------ |
| 連続するアクション                     | 順に並ぶ文                                       |
| 2つのガードを持つデシジョン + マージ   | `if / else`                                      |
| 複数のガードと `[else]` を持つデシジョン | `if / else if / else` または `switch`                |
| 本体の後にデシジョンがある戻り辺       | `do … while`                                     |
| 本体の前にデシジョンがある戻り辺       | `while` または `for`                                 |
| フォークとジョイン                     | スレッド、タスク、`Promise.all`、並列ストリーム   |
| 呼び出しアクティビティ                 | メソッドまたは関数の呼び出し                     |
| 2つのアクション間のオブジェクトノード | 戻り値をパラメータとして引き渡すこと             |
| アクティビティ終了                     | メソッドの終端、`return`                      |
| フロー終了                             | 1つの経路が終了し、残りは実行を続ける           |

## 例: オンライン注文の処理 {/*#example-processing-an-online-order*/}

顧客、ショップシステム、倉庫の3つのパーティションが関与する。注文はショップで検証され、無効な注文は拒否され、有効な注文は倉庫でピッキングされ出荷される。

```text
      Customer       │       Shop System        │      Warehouse
─────────────────────┼──────────────────────────┼─────────────────────
          ●          │                          │
          │          │                          │
          ▼          │                          │
 ╭─────────────────╮ │                          │
 │   Place order   │ │                          │
 ╰─────────────────╯ │                          │
          │          │                          │
          └──────────┼────────────┐             │
                     │            │             │
                     │            ▼             │
                     │   ╭─────────────────╮    │
                     │   │ Validate order  │    │
                     │   ╰─────────────────╯    │
                     │            │             │
                     │            ▼             │
                     │      ╱───────────╲       │
                     │     ╱    order    ╲      │
                     │     ╲   valid ?   ╱      │
                     │      ╲───────────╱       │
                     │       │         │        │
                     │ [no]  │         │ [yes]  │
          ┌──────────┼───────┘         └────────┼──────────┐
          │          │                          │          │
          ▼          │                          │          ▼
 ╭─────────────────╮ │                          │ ╭─────────────────╮
 │ Read rejection  │ │                          │ │   Pick items    │
 ╰─────────────────╯ │                          │ ╰─────────────────╯
          │          │                          │          │
          ▼          │                          │          ▼
          ◉          │                          │ ╭─────────────────╮
                     │                          │ │   Ship parcel   │
                     │                          │ ╰─────────────────╯
                     │                          │          │
          ┌──────────┼──────────────────────────┼──────────┘
          │          │                          │
          ▼          │                          │
 ╭─────────────────╮ │                          │
 │ Receive parcel  │ │                          │
 ╰─────────────────╯ │                          │
          │          │                          │
          ▼          │                          │
          ◉          │                          │
```

この例が示すこと:

- 顧客がプロセスを開始するため、初期ノードは顧客のレーンにある
- `Validate order` はここでは1つのアクションである。検証が複雑な場合は、独自の図を持つ呼び出しアクティビティになる
- ガード `[no]` と `[yes]` は互いに排他的で、すべてのケースを網羅しているため、デシジョンでフローが行き詰まることはない
- 両方の分岐がアクティビティ終了ノードで終わるため、プロセスには2つの結果がありうる
- 注文が*どのように*検証されるか、出荷に*どれだけ*かかるかには触れていない。アクティビティ図が表すのは制御フローであり、データ構造や時間ではない

現実的な拡張としては、`[yes]` の後にフォークし、ショップのレーンの `Charge card` と倉庫のレーンの `Pick items` を並行して実行し、`Ship parcel` の前で再びジョインさせる形が考えられる。

## よくある間違い {/*#common-mistakes*/}

1. **ガードの欠落または重複:** デシジョンのすべての出力フローにはガードが必要であり、ガードは互いに排他的かつ網羅的でなければならない。そうでなければ、フローは進む経路を持たないか、複数持つことになる。
2. **フォークの代わりにデシジョンを使用:** ひし形は*これらの経路のうち1つ*を意味し、バーは*これらすべての経路*を意味する。
3. **ジョインのないフォーク:** 並行フローが実行中のまま、アクティビティが終了ノードに到達しうる。その場合、終了ノードは実行中のフローを破棄する。
4. **フォークのないジョイン:** ジョインは到着することのないフローを待ち続け、プロセスがデッドロックする。
5. **名詞によるアクション名:** `Invoice` では何も伝わらず、`Create invoice` なら伝わる。
6. **アクション内の条件:** 条件は出力フローに置くべきである。アクションは行うことであり、確認することではない。
7. **複数の初期ノード:** アクティビティの開始点はちょうど1つである。並行した開始はフォークでモデル化する。
8. **装飾としてのレーン:** アクターが描かれていてもフローがレーンの境界をまたがない場合、パーティション分けは何も付加しない。
9. **制御フローとデータフローの混在:** アクション間で渡されるデータはオブジェクトノードに置くべきであり、制御フローのラベルには書かない。
