# その他のUML図

## 概要 {/*#overview*/}

UML 2.5は14種類の図を定義している。独立した項目で扱われない7種類をここに挙げる。

| 図                           | 分類   | 中心となる問い                                                             |
| ---------------------------- | ------ | -------------------------------------------------------------------------- |
| オブジェクト図               | 構造   | ある時点でどの具体的なインスタンスが存在し、どう結び付いているか           |
| パッケージ図                 | 構造   | モデルがどの単位に分割され、どの単位がどれに依存しているか                 |
| コミュニケーション図         | 振る舞い | どのオブジェクトが、どのリンクに沿ってメッセージを交換するか            |
| タイミング図                 | 振る舞い | 時間軸上のどの時点で、要素がどの状態にあるか                             |
| 相互作用概要図               | 振る舞い | 相互作用全体がどの順序で実行されるか                                     |
| 複合構造図                   | 構造   | 分類子が内部でどう構成され、どのポートを通じて通信するか                   |
| プロファイル図               | 構造   | UML自体を、ドメインやプラットフォームのためにどう拡張するか               |

---

## オブジェクト図 {/*#object-diagram*/}

ある特定の時点でのシステムのスナップショットで、存在するインスタンスとそれらの間のリンクを示す。表記は[クラス図](./class-diagram.md)のものと同じだが、インスタンスのレベルである。

中心となる表記要素:

- **インスタンス仕様:** `name : Class` の形式で下線付きの名前を持つ長方形。名前またはクラスは省略できる（`o7 : Order`、`: Order`、`o7`）
- **属性値:** 下側の区画に `attribute = value` として記述する
- **リンク:** 2つのインスタンス間の単純な実線で、関連のインスタンスレベルでの対応物。リンクは常にちょうど2つのインスタンスを結ぶため、多重度は付けない

プレーンテキストでは下線を表示できないが、実際の表記では名前 `m1 : Customer` と `o7 : Order` に下線が引かれる。

```text
 ┌────────────────────┐              ┌────────────────────┐
 │ m1 : Customer      │   places     │ o7 : Order         │
 ├────────────────────┤──────────────├────────────────────┤
 │ name = "Meier"     │              │ total = 249.90     │
 │ city = "Kiel"      │              │ status = "paid"    │
 └────────────────────┘              └────────────────────┘
```

典型的な用途: 複雑なクラス図を具体例で説明すること、1つの具体的なデータの組み合わせについて議論すること、テストデータや不具合が発生する状態を文書化すること。

## パッケージ図 {/*#package-diagram*/}

パッケージ図は、モデルがどの単位に分割され、どの単位がどれに依存しているかを示す。パッケージ自体は振る舞いを持たない。

中心となる表記要素:

- **パッケージ:** タブ付きの長方形。入れ子は図で、または `shop::service` として書く
- **依存関係:** 利用する側のパッケージから利用される側のパッケージへ向かう破線矢印
- **`«import»`:** 対象パッケージの公開要素を、修飾なしで利用できるようにする
- **`«access»`:** 同じ関係だが、インポートした名前をそれ以上伝播させない
- **`«merge»`:** 概念的に、対象パッケージの内容をソースのパッケージにコピーし、それと結合する
- **レイヤリング:** パッケージを上下に配置し、すべての依存関係が一方向を向くようにすること

```text
┌──────┐
│ shop │
├──────┴──────────────────┐
│                         │
│   ┌─────────┐           │
│   │ ui      │           │
│   ├─────────┴───────┐   │
│   │                 │   │
│   └────────┬────────┘   │
│            ┆ «import»   │
│            ▼            │
│   ┌─────────┐           │
│   │ service │           │
│   ├─────────┴───────┐   │
│   │                 │   │
│   └────────┬────────┘   │
│            ┆ «import»   │
│            ▼            │
│   ┌─────────────┐       │
│   │ persistence │       │
│   ├─────────────┴───┐   │
│   │                 │   │
│   └─────────────────┘   │
│                         │
└─────────────────────────┘
```

典型的な用途: 階層化アーキテクチャ、システムのモジュールへの分割、循環依存がコードに達する前に可視化すること。

境界: [コンポーネント図](./component-diagram.md)は実行時にインターフェースを提供・要求する交換可能な構成要素を記述するのに対し、パッケージ図は設計時にモデルとソースの要素を整理するだけである。

---

## コミュニケーション図 {/*#communication-diagram*/}

コミュニケーション図は、どのオブジェクトが、どのリンクに沿ってメッセージを交換するかを示す。オブジェクトは自由に配置され、メッセージの順序は番号付けから分かる。

中心となる表記要素:

- **オブジェクト:** オブジェクト図と同様に、下線付きの `name : Class` を持つ長方形
- **リンク:** 2つのオブジェクト間の実線
- **メッセージ:** リンクの横に描かれた小さな矢印で、`1: placeOrder()` とラベル付けされる
- **階層的なシーケンス番号:** `1`、`1.1`、`1.2`。`1.1` と `1.2` は、メッセージ `1` の処理の一部として順に送られる
- **反復マーカーとガード:** メッセージラベルの一部としての `*` と `[condition]`

```text
  ┌──────────┐   1: placeOrder() ►  ┌─────────────┐
  │ : Client │──────────────────────│ : OrderCtrl │
  └──────────┘   ◄ 1.3: confirm()   └─────────────┘
                                           │
                                           │ ▼ 1.1: checkStock()
                                           │ ▼ 1.2: reserve()
                                           │
                                    ┌─────────────┐
                                    │ : Warehouse │
                                    └─────────────┘
```

典型的な用途: どのオブジェクトが互いに通信するかの可視化、設計の結合度の評価、正確な順序よりも構造のほうが重要な小規模な相互作用。

境界: [シーケンス図](./sequence-diagram.md)は、同じ相互作用を、上から下への明示的な時間軸に沿って示し、`alt`、`opt`、`loop` などの複合フラグメントを備える。オブジェクト、メッセージ、およびその順序は一方の図から他方へ引き継げるが、複合フラグメントにはコミュニケーション図での対応物がない。選択やループはシーケンス図のほうが読みやすく、リンクのネットワークはコミュニケーション図のほうが見やすい。

## タイミング図 {/*#timing-diagram*/}

タイミング図は、1つ以上の要素の状態または値が、明示的な時間軸に沿ってどう変化するかを示す。

中心となる表記要素:

- **時間軸:** 水平方向で、目盛りを持ち、ライフラインごとに1つのレーンがある
- **状態ライフライン:** 縦軸に列挙された状態の間を結ぶ階段状の線
- **値ライフライン:** 交差が値の変化を示す、コンパクトな帯状の形式
- **期間と時間制約:** `{d..3*d}` と `{t = 0}`
- **イベントとメッセージ:** レーン間の矢印
- **目盛り:** 時間軸の単位

```text
 : Motor
           │
   active  │         ┌──────────────┐
           │         │              │
   idle    ├─────────┘              └──────────
           │         ├── {20..40} ──┤
           └────┬────┬────┬────┬────┬────┬────┬───► t
           0    10   20   30   40   50   60   70  ms
```

典型的な用途: リアルタイムシステムと組み込みシステム、バスやネットワークのプロトコル、ハードウェアに関わる制御、レイテンシ、タイムアウト、最小保持時間に関する要件。

境界: [ステートマシン図](./state-machine-diagram.md)は、時間軸なしで、どの状態と遷移が可能かを定義する。タイミング図は、要素がいつそれらの状態のどれにあるかを示す。

---

## 相互作用概要図 {/*#interaction-overview-diagram*/}

相互作用概要図は、複数のシーケンス図、コミュニケーション図、タイミング図を1つの制御フローに配置し、各ノードが完全な相互作用となる。

中心となる表記要素:

- **フレーム:** ヘッダ `sd <name>` を持つ
- **相互作用の利用:** キーワード `ref` と既存の相互作用図の名前を持つ長方形
- **インライン相互作用:** ノードとして直接埋め込まれた小さなシーケンス図
- **制御要素:** アクティビティ図のすべてのもの、すなわち初期ノード、デシジョン、マージ、フォーク、ジョイン、終了ノード

```text
 ┌ sd Checkout ─────────────────────────────┐
 │                  ●                       │
 │                  │                       │
 │                  ▼                       │
 │          ┌───────────────┐               │
 │          │ ref  Login    │               │
 │          └───────────────┘               │
 │                  │                       │
 │             ╱─────────╲                  │
 │            ╱  paid ?   ╲                 │
 │            ╲           ╱                 │
 │             ╲─────────╱                  │
 │       [yes]  │       │  [no]             │
 │     ┌────────┘       └────────┐          │
 │     ▼                         ▼          │
 │ ┌───────────────┐   ┌───────────────┐    │
 │ │ ref  Ship     │   │ ref  Cancel   │    │
 │ └───────────────┘   └───────────────┘    │
 │     │                         │          │
 │     └────────┐       ┌────────┘          │
 │              ▼       ▼                   │
 │                  ◉                       │
 └──────────────────────────────────────────┘
```

典型的な用途: 多数の個別の相互作用からなるプロトコルや、長時間にわたる業務トランザクションの全体像。

境界: [アクティビティ図](./activity-diagram.md)も同じ制御要素を使うが、そのノードは単一のアクションである。相互作用概要図は、入れ子になった `alt` と `loop` のフラグメントで埋め尽くされた、肥大化した1つのシーケンス図の代替にもなる。

---

## 複合構造図 {/*#composite-structure-diagram*/}

複合構造図は、単一の分類子の内部を見る。どの部品で構成され、それらの部品がどう結線され、どの相互作用点を通じて環境と接続されるかを示す。

中心となる表記要素:

- **部品:** 分類子のフレーム内にある長方形で、`role : Type` と書き、任意で多重度を付ける。例: `wheels : Wheel [4]`
- **ポート:** 分類子の境界上にある小さな正方形で、名前と型を持つ相互作用点
- **インターフェース:** 提供インターフェースはロリポップ `─○`、要求インターフェースはソケット `─(`
- **コネクタ:** 2つの部品間のアセンブリコネクタ、部品とポート間のデリゲーションコネクタ
- **コラボレーション:** 名前付きのロールを持つ破線の楕円で、具体的なクラスとは独立に協調のパターンを記述する

```text
 ┌ Car ──────────────────────────────────────┐
 │                                           │
 │ ┌────────────┐        ┌──────────────┐    │
 │ │ e : Engine │────────│ g : Gearbox  │────┼──□───○ Drive
 │ └────────────┘        └──────────────┘    │
 │                                           │
 └───────────────────────────────────────────┘
```

典型的な用途: コンポーネントの内部アーキテクチャ、システム設計や組み込み設計における部品の結線、ロールのコラボレーションとしてのデザインパターンの記述。

境界: [クラス図](./class-diagram.md)はどのクラスが一般に関連しているかを示すのに対し、複合構造図は、1つの全体の内部にあるインスタンスが特定のロールでどう結線されているかを示す。[コンポーネント図](./component-diagram.md)も同じロリポップとソケットの表記を使うが、1つの分類子の内部ではなく、システム全体の配置可能な構成要素のレベルで用いる。

## プロファイル図 {/*#profile-diagram*/}

プロファイル図は、ドメインや対象プラットフォームのためにUML自体を拡張する。

中心となる表記要素:

- **プロファイル:** キーワード `«profile»` を持つパッケージ
- **ステレオタイプ:** キーワード `«stereotype»` を持つ長方形で、既存のメタクラスを拡張する。あらかじめ定義されたUMLのキーワードではない、ギュメで囲まれた名前はすべて、何らかのプロファイルで定義されたステレオタイプである
- **拡張:** ステレオタイプからメタクラスへ向かう、塗りつぶした矢じりの実線。例: `«metaclass» Class`
- **タグ付き値:** ステレオタイプの属性。例: `table : String`。ステレオタイプを持つ要素で値が設定される
- **制約:** 波括弧で囲んだ規則で、OCLまたは自由なテキストで記述する
- **適用:** パッケージからプロファイルへの `«apply»` 依存関係。その要素は、`«entity»`、`«controller»` などを持てるようになる

```text
 ┌ «profile» Persistence ─────────────────────┐
 │                                            │
 │  ┌─────────────────┐     ┌───────────────┐ │
 │  │ «stereotype»    │────►│ «metaclass»   │ │
 │  │ Entity          │     │ Class         │ │
 │  ├─────────────────┤     └───────────────┘ │
 │  │ table : String  │                       │
 │  └─────────────────┘                       │
 └────────────────────────────────────────────┘
```

メタモデルとの関係: UMLは4層のアーキテクチャで記述される。`M0` は実際のオブジェクトを、`M1` はモデルを、`M2` はクラスや関連が何であるかを定義するUMLメタモデルを、`M3` はMOF（Meta Object Facility）、すなわちメタモデル自体を記述する言語を保持する。プロファイルはUMLの軽量な拡張機構であり、層 `M2` を変更せずに拡張するため、プロファイルを適用したモデルをツール間で交換できる。重量級の拡張は、メタモデルを直接変更し、それによって新しい言語を作り出すことになる。

典型的な用途: SysMLやMARTEなどのドメイン固有のモデリング言語、モデルのJPAやEJBなどのプラットフォームへのマッピング、全社的なモデリング規約。
