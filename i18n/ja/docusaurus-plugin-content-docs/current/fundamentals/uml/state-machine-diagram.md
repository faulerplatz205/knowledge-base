# ステートマシン図

## 概要 {/*#overview*/}

ステートマシン図は、**振る舞い**を表すUML図である。*単一*のオブジェクト、コンポーネント、またはシステムのライフサイクルを記述する。どの状態になりうるか、どのイベントがある状態から次の状態へ移すか、その途中で何が起こるかである。

代表的な用途:

- ショップシステムにおける注文のステータス（`New`、`Paid`、`Shipped`、`Delivered`、`Cancelled`）
- セッションまたはログインの処理（`Anonymous`、`Authenticated`、`Locked`、`Expired`）
- デバイスと接続の状態（`Off`、`Booting`、`Ready`、`Error`）
- プロトコルとパーサのロジック。状態に応じて次の文字が異なる解釈をされる
- 特定の状態でのみメソッドの実行が許されるクラスの内部の振る舞い

---

## 表記法 {/*#notation*/}

| 要素                  | 表記                                                  | 意味                                                                     |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------ |
| 初期疑似状態          | 塗りつぶした円 `●`                                    | ライフサイクルが始まる場所、リージョンごとにちょうど1つ                  |
| 状態                  | 名前を持つ角丸の長方形                                | オブジェクトが待機している状況で、形容詞または名詞で命名する             |
| 遷移                  | ある状態から別の状態への矢印                          | 状態の変化で、`trigger [guard] / effect` とラベル付けされ、どの部分も任意 |
| トリガー              | 遷移上のイベント名                                    | 遷移を可能にするイベント。例: `cancel`、`timeout`                           |
| 完了遷移              | トリガーのない遷移                                    | 遷移元の状態の振る舞いが完了した時点で発火する                           |
| ガード                | 遷移上の `[condition]`                                      | 真偽値の条件で、真と評価された場合にのみ遷移が発火する                   |
| エフェクト            | 遷移上の `/ action`                                      | 遷移の発火中に実行されるアクションで、ブロックしてはならない             |
| 自己遷移              | 同じ状態から出て同じ状態に戻る矢印                    | 状態を出て再び入る。`exit` と `entry` は実行される                      |
| 内部遷移              | 状態ボックス内の `trigger / effect`                              | 状態を変えない反応。`exit` と `entry` は実行**されない**                |
| entryアクティビティ   | 状態ボックス内の `entry / action`                              | 状態に入るたびに実行され、使われた遷移には依存しない                     |
| doアクティビティ      | 状態ボックス内の `do / activity`                              | 状態がアクティブな間、継続的に実行され、中断されうる                     |
| exitアクティビティ    | 状態ボックス内の `exit / action`                              | 状態を出るたびに実行され、使われた遷移には依存しない                     |
| 複合状態              | さらに状態を含む状態ボックス                          | サブ状態に分解された状態                                                 |
| リージョン            | 複合状態の一部で、破線で区切られる                    | 同時にアクティブとなるサブ状態                                           |
| 選択（choice）        | 遷移上のひし形                                        | エフェクトの後で評価される分岐で、出力遷移がガードを持つ                 |
| 浅い履歴              | `H` を含む円                                      | 再入時に、その複合状態で最後にアクティブだったサブ状態が再開される       |
| 深い履歴              | `H*` を含む円                                      | 入れ子のすべての階層を含め、最後にアクティブだったサブ状態を再開する     |
| 終了状態              | 輪に囲まれた塗りつぶした円 `◉`                    | ライフサイクルがここで終わり、オブジェクトはそれ以上のイベントを受け付けない |

図を読みやすく保つための命名規則:

- 状態は、アクティビティではなく状況を表す: `Paid`、`Waiting for payment` とし、`Pay` としない
- トリガーは、それを処理するメソッドではなくイベントにちなんで命名する: `cancel` とし、`handleCancel` としない
- エフェクトと内部アクティビティは、括弧付きの操作として命名する: `/ refundPayment()`

## 構成要素 {/*#building-blocks*/}

### 状態と遷移 {/*#states-and-transitions*/}

```text
              ●
              │
              ▼
   ╭────────────────────────╮
   │         Idle           │
   ╰────────────────────────╯
              │
              │ coinInserted [amount >= price] / unlock()
              ▼
   ╭────────────────────────╮
   │        Ready           │
   ╰────────────────────────╯
              │
              │ productSelected / dispense()
              ▼
              ◉
```

文として読むと次のようになる。*状態 `Idle` で、イベント `coinInserted` が発生し、条件 `amount >= price` が成立すると、`unlock()` が実行され、マシンは `Ready` に変わる*。イベントが発生してもガードが偽の場合、イベントは破棄され、状態は変わらない。

### 自己遷移 {/*#self-transition*/}

自己遷移の後、オブジェクトは以前と同じ状態にある。その途中で状態を出て再び入るため、`exit` と `entry` が実行され、`do` アクティビティが再開される。

```text
        ┌───────────────────────────────────┐
        │   digitPressed / appendDigit()    │
        │                                   │
        │   ╭───────────────────────────╮   │
        └──►│        Collecting         │───┘
            ╰───────────────────────────╯
```

`entry`、`do`、`exit` の再開が望ましくない場合は、代わりに**内部遷移**を用いる。これは状態ボックスの内部に書かれ、状態をアクティブなままにする。

```text
╭───────────────────────────────────────────╮
│               Collecting                  │
├───────────────────────────────────────────┤
│ digitPressed / appendDigit()              │
╰───────────────────────────────────────────╯
```

たとえば、`entry / startTimer()` として実装されたタイムアウトは、自己遷移ではリセットされ、内部遷移では動作し続ける。

### 内部アクティビティ {/*#internal-activities*/}

3つのキーワードが、遷移ではなく状態自体に属する振る舞いを記述する。

- `entry / action`: 入るたびに1回実行され、doアクティビティより前に実行される
- `do / activity`: 状態がアクティブな間に実行され、長時間実行されることがあり、出力遷移によって中断されうる
- `exit / action`: 出るたびに1回実行され、doアクティビティが終了または中止された後に実行される

```text
╭───────────────────────────────────────────╮
│                 Heating                   │
├───────────────────────────────────────────┤
│ entry / switchHeaterOn()                  │
│ do / measureTemperature()                 │
│ exit / switchHeaterOff()                  │
╰───────────────────────────────────────────╯
```

状態変化の順序は常に次のとおりである。遷移元の状態の `exit`、次に遷移のエフェクト、そして遷移先の状態の `entry`。

アクションを、その状態への各入力遷移ではなく `entry` に置くと、重複がなくなり、後でその状態への新たな遷移を追加したときにアクションが忘れられることがなくなる。

### 複合状態 {/*#composite-states*/}

複合状態は、独自のステートマシンを含む。図を小さく保ち、サブ状態のグループ全体に対して遷移を1回だけ描けるようにする。

```text
╭────────────────────────────────────────────────────────╮
│ Active                                                 │
│                                                        │
│    ●                                                   │
│    │                                                   │
│    ▼                                                   │
│  ╭───────────────────╮  connected  ╭───────────────────╮
│  │     Dialling      │────────────►│    Talking        │
│  ╰───────────────────╯             ╰───────────────────╯
│                                                        │
╰────────────────────────────────────────────────────────╯
              │
              │ hangUp
              ▼
   ╭───────────────────╮
   │       Idle        │
   ╰───────────────────╯
```

遷移 `hangUp` は複合状態の*境界*から始まるため、`Dialling` と `Talking` のどちらにも等しく適用される。

押さえておくべき規則:

- 複合状態には独自の初期疑似状態が必要であり、そうでなければどのサブ状態がアクティブになるかが未定義となる
- リージョンごとに、一度にちょうど1つのサブ状態がアクティブであり、それを含む複合状態もアクティブである
- 遷移は、サブ状態を直接指すこともでき、その場合は初期疑似状態を迂回する
- 複合状態内の終了状態は、その内側のマシンを終了させ、それが複合状態の出力側の完了遷移を発火させる

### リージョンと並行状態 {/*#regions-and-parallel-states*/}

複合状態は、破線によって**リージョン**に分割できる。各リージョンは、独自の初期疑似状態、サブ状態、遷移を持つ。複合状態がアクティブな間、すべてのリージョンで同時に1つのサブ状態がアクティブになる。これにより、録画の音声と映像のように、1つのオブジェクトの独立した側面をモデル化できる。

```text
╭──────────────────────────────────────────────────────────╮
│ Recording                                                │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮   muteAudio   ╭───────────────╮       │
│  │ AudioRunning  │──────────────►│  AudioMuted   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮  pauseVideo   ╭───────────────╮       │
│  │ VideoRunning  │──────────────►│ VideoPaused   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
╰──────────────────────────────────────────────────────────╯
```

イベントはすべてのリージョンに提示される。1つのリージョンで、複数のリージョンで、またはどこでも遷移を引き起こさないことがありうる。

### 履歴状態 {/*#history-state*/}

履歴状態は、*中断の後、マシンはどこから再開するか*という問いに答える。これがなければ、複合状態への再入は常にその初期疑似状態から始まる。

```text
              ╭──────────────────────────────────────────╮
              │ Playing                                  │
   resume     │                                          │
 ┌───────────►│   (H)                                    │
 │            │    │                                     │
 │            │    ▼                                     │
 │            │  ╭───────────╮        ╭───────────╮      │
 │            │  │  Track 1  │───────►│  Track 2  │      │
 │            │  ╰───────────╯        ╰───────────╯      │
 │            ╰──────────────────────────────────────────╯
 │                           │ pause
 │            ╭──────────────▼───────────╮
 └────────────│          Paused          │
              ╰──────────────────────────╯
```

浅い履歴 `(H)` は、この階層で最後にアクティブだったサブ状態を復元する。深い履歴 `(H*)` は、入れ子のすべての階層を含む最後の構成を復元する。複合状態に一度も入ったことがない場合、履歴状態への遷移は初期疑似状態にフォールバックする。

## 状態遷移表 {/*#state-transition-table*/}

ステートマシン図は、**状態遷移表**として書くこともできる。状態ごとに行をグループ化すると、状態とイベントの欠けている組み合わせが目立つため、この表は図よりも網羅性の確認がしやすい。

| 現在の状態    | イベント          | ガード            | エフェクト             | 次の状態    |
| ------------- | ----------------- | ----------------- | ---------------------- | ----------- |
| `New`         | `itemAdded`       | –                 | `recalculateTotal()`   | –           |
| `New`         | `paymentReceived` | –                 | `capturePayment()`     | `Paid`      |
| `New`         | `cancel`          | –                 | `releaseReservation()` | `Cancelled` |
| `Paid`        | `dispatched`      | `allItemsInStock` | `sendTrackingMail()`   | `Shipped`   |
| `Paid`        | `cancel`          | –                 | `refundPayment()`      | `Cancelled` |
| `Shipped`     | `delivered`       | –                 | –                      | `Delivered` |

表に現れない組み合わせは、遷移を引き起こさない。イベントは何の効果もなく破棄される。

*次の状態*の列が空で*エフェクト*の列が埋まっている行は、内部遷移を表す。現在の状態と次の状態が同一である行は、自己遷移を表す。

## 例: 注文ステータス {/*#example-order-status*/}

ショップシステムにおける注文のライフサイクルで、作成から配達またはキャンセルまでを示す。

```text
                          ●
                          │
                          ▼
                ╭────────────────────────╮
                │          New           │
                │ entry / reserveItems() │
                ╰────────────────────────╯
                     │              │
    paymentReceived  │              │ cancel
    / capturePayment()              │ / releaseReservation()
         ┌───────────┘              └────────────┐
         ▼                                       │
╭────────────────────────╮                       │
│          Paid          │──────────────────────►┤
╰────────────────────────╯  cancel               │
         │                  / refundPayment()    │
         │ dispatched [allItemsInStock]          │
         │ / sendTrackingMail()                  ▼
         ▼                          ╭────────────────────────╮
╭────────────────────────╮          │       Cancelled        │
│        Shipped         │          ╰────────────────────────╯
╰────────────────────────╯                       │
         │                                       │
         │ delivered                             │
         ▼                                       │
╭────────────────────────╮                       │
│       Delivered        │                       │
╰────────────────────────╯                       │
         │                                       │
         └───────────────────┐   ┌───────────────┘
                             ▼   ▼
                             ◉
```

この例が示すこと:

- 返金は遷移 `Paid => Cancelled` 上にあり、`Cancelled` の `entry` アクティビティとしては**置かれていない**。`New` からキャンセルされた注文は、支払われたことがないためである。
- `dispatched` はガードを持つ。在庫が不足している場合、注文は `Paid` にとどまる。
- `Shipped` には `cancel` への遷移がない。業務ルール*発送済みの注文はもうキャンセルできない*は、遷移の不在によって表現される。

コードで実装する場合、各状態は列挙型の値になり、表は状態とイベントに対する `switch` になる。表に挙げられていないものはすべてデフォルトの分岐に入り、拒否される。したがって、無効な状態変化は構造上起こりえない。

## アクティビティ図との区別 {/*#delimitation-from-the-activity-diagram*/}

| 観点             | ステートマシン図                 | [アクティビティ図](./activity-diagram.md)       |
| ---------------- | -------------------------------- | ----------------------------------------------- |
| ノード           | **状態**、オブジェクトは待機する | **アクション**、作業が行われる                  |
| 命名             | 形容詞または名詞: `Paid`         | 動詞 + 目的語: `Capture payment`                |
| 矢印             | **イベント**によって引き起こされる | 前のアクションが**完了した**ときに発火する    |
| 範囲             | 1つのオブジェクトのライフサイクル | 1回のプロセスの実行で、複数のアクターにまたがることがある |
| 分岐             | 出力遷移上のガード               | ガード付きフローを持つデシジョンノード          |
| 並行性           | 複合状態内のリージョン           | フォークとジョイン                              |
| 典型的な問い     | *注文はどの状態にあるか*         | *次のステップは何か*                            |

矢印に*その後*のようなラベルしか付けられない場合は、アクティビティ図が適している。矢印に `cancel`、`timeout`、`paymentReceived` のような名前が必要な場合は、ステートマシン図が適している。

## よくある間違い {/*#common-mistakes*/}

1. **アクティビティを状態名に使うこと:** `Pay` はアクションであり、アクティビティ図に属する。状態は `Paid` や `Waiting for payment` である。
2. **トリガーのない遷移:** イベントのない2つの状態間の矢印は完了遷移である。遷移元の状態が振る舞いを終えた時点で発火する。
3. **重複するガード:** 同じトリガーを持つ2つの遷移のガードが、両方とも真になりうる場合、振る舞いは未定義となる。ガードは互いに排他的でなければならない。
4. **ガードとトリガーの混同:** `[cancel]` はイベントではなく条件である。`cancel [orderNotShipped]` なら両者を正しく分けられる。
5. **初期疑似状態の欠落:** これがなければ、開始状態が未定義となる。すべての図とすべてのリージョンに、ちょうど1つ必要である。
6. **到達不能な状態や行き止まりの状態:** 入力遷移のない状態には決して到達しない。出力遷移がなく、終了状態でもない状態は、オブジェクトを閉じ込める。
7. **内部遷移を意図した箇所での自己遷移:** 自己遷移は `entry`、`do`、`exit` を再開する。その結果、`entry` で開始されたタイマーがリセットされる。
8. **状態爆発:** 独立した側面を1つのフラットな状態の集合にまとめると、状態の数が掛け算で増える。リージョンや追加の属性を用いればこれを避けられる。
