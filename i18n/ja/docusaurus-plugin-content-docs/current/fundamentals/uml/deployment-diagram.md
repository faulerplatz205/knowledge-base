# 配置図

## 概要 {/*#overview*/}

配置図は、**構造**を表すUML図である。完成したシステムが物理的にどのように分散されているかを示す。どのハードウェアとどの実行環境が存在し、どのファイルがそこにインストールされ、それらの部分がどの通信パスを通じてデータを交換するかである。

代表的な用途:

- 運用および引き継ぎのための、アプリケーションのシステム構成の文書化
- ネットワーク境界を含む、クライアントサーバまたは3層アーキテクチャの提示
- インストールの計画: どのアーティファクトをどのマシンにコピーするか
- プロトコルとレプリカ数を含む、コンテナまたはクラウドへの配置の記述
- 可用性、スケーリング、セキュリティゾーンに関する議論の土台の提供

---

## 表記法 {/*#notation*/}

| 要素                  | 表記                                                                   | 意味                                                                                              |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| ノード                | 直方体（立体的なボックス）                                             | 何かが実行または格納される実行リソース                                                            |
| デバイス              | キーワード `<<device>>` を付けた直方体                                 | 物理的なハードウェア: サーバ、ワークステーション、スマートフォン、ルータ、プリンタ                |
| 実行環境              | `<<executionEnvironment>>` を付けた直方体、通常はデバイスの内部に入れ子にする | アーティファクトをホストするソフトウェア: OS、JVM、アプリケーションサーバ、コンテナランタイム、DBMS |
| アーティファクト      | キーワード `<<artifact>>` を付けた長方形、またはドキュメントアイコン   | 開発プロセスによって生成される物理的なファイル                                                    |
| 配置                  | ノードの内部に描かれたアーティファクト、または破線の `<<deploy>>` 矢印 | そのアーティファクトがそのノードにインストールされている                                          |
| マニフェステーション  | アーティファクトからコンポーネントまたはクラスへ向かう破線の `<<manifest>>` 矢印 | アーティファクトが、論理的な要素の物理的な実現である                                      |
| 通信パス              | 2つのノード間の実線                                                    | ノードがデータを交換する接続で、方向を持たない                                                    |
| プロトコル            | パス上のステレオタイプ。例: `<<HTTPS>>`、`<<TCP/IP>>`、`<<JDBC>>`     | その接続で使われるプロトコル                                                                      |
| 多重度                | 通信パスの端にある数。例: `2` または `1..*`          | その端にあるいくつのノードが、反対側の端の1つのノードに接続されるか                               |
| 入れ子                | ノードの内部に描かれたノードまたはアーティファクト                     | 包含: ハードウェアがランタイムを含み、ランタイムがファイルを含む                                  |
| インスタンス          | 先頭にコロンを付けた下線付きの名前。例: `:AppServer`                | 型ではなく、具体的なインスタンス                                                                  |
| ノート                | 破線につながる角折れ長方形                                             | 意味を持たないコメント                                                                            |

図を読みやすく保つための命名規則:

- ノードは、型として `ApplicationServer` のように、または具体的なマシンとして `appsrv01:ApplicationServer` のように命名する。インスタンス名は、作図ツールでは下線が引かれる。
- アーティファクトには、拡張子を含む実際のファイル名を付ける: `shop.war` とし、`Shop application` としない。
- すべての通信パスにプロトコルのステレオタイプを付ける。ラベルのない線は*何らかの形でつながっている*ことしか表さない。
- キーワードとステレオタイプはギュメ(guillemets)で囲んで書く: `«device»`。表記 `<<device>>` はテキストベースのツールで使われるASCII形式であり、以下ではこちらを用いる。

## 構成要素 {/*#building-blocks*/}

### ノード {/*#node*/}

ノードは、キーワードによって2種類に区別される。

- **`<<device>>`:** サーバ、ワークステーション、携帯電話、組み込みコントローラなどの物理的なハードウェア
- **`<<executionEnvironment>>`:** アーティファクトをホストし、メモリ管理、トランザクション、リクエストのディスパッチなどのサービスを提供するソフトウェア環境

実行環境は通常、デバイスの内部に入れ子にされる。キーワードのないノードは、単に*何らかの*実行リソースである。

```text
        ┌────────────────────────────────────────┐
       ╱                                        ╱│
      ┌────────────────────────────────────────┐ │
      │  <<device>>                            │ │
      │  ApplicationServer                     │ │
      │                                        │ │
      │  ┌──────────────────────────────────┐  │ │
      │  │  <<executionEnvironment>>        │  │ │
      │  │  Tomcat 10                       │  │ │
      │  │                                  │  │ │
      │  │  ┌────────────────────────────┐  │  │ │
      │  │  │  <<artifact>>              │  │  │ │
      │  │  │  shop.war                  │  │  │ │
      │  │  └────────────────────────────┘  │  │ │
      │  └──────────────────────────────────┘  │ ╱
      └────────────────────────────────────────┘╱
```

作図ツールでは、入れ子になったものも含め、すべてのノードが直方体になる。ここでの図は、プレーンテキストでも入れ子が読み取れるよう、内側のノードを単純な長方形で描いている。

### アーティファクトと配置 {/*#artifact-and-deployment*/}

実際には、アーティファクトはファイルである。典型的な例は `shop.war`、`payment-service.jar`、`setup.exe`、`schema.sql`、`nginx.conf`、および `shop-app:2.4.0` のようなコンテナイメージである。

アーティファクトがノードにインストールされていることを示す表記は2つある。

- **入れ子:** アーティファクトの長方形をノードの内部に描く。この形式はより簡潔で、圧倒的によく使われる。
- **依存関係:** キーワード `<<deploy>>` を付けた破線矢印を、アーティファクトからノードへ引く。この形式は、同じアーティファクトが複数のノードに配置される場合に有用である。

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈┈ <<deploy>> ┈┈┈┈┈┈▶ │  <<device>>            │
 │  shop.war              │                          │  ApplicationServer     │
 └────────────────────────┘                          └────────────────────────┘
```

マニフェステーションは、設計の方向を指す対となる関係である。キーワード `<<manifest>>` を付けた破線矢印を、アーティファクトから、それが物理的に実現するコンポーネントまたはクラスへ引く。これにより、モデルのどの部分がこのファイルになるかが示される。

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈ <<manifest>> ┈┈┈┈┈▶ │  <<component>>         │
 │  payment-service.jar   │                          │  PaymentService        │
 └────────────────────────┘                          └────────────────────────┘
```

### 通信パス {/*#communication-path*/}

通信パスは、接続自体に方向がないため矢じりのない実線であり、プロトコルをステレオタイプとしてラベル付けする。

```text
    ┌──────────────────────┐                  ┌──────────────────────┐
   ╱                      ╱│                 ╱                      ╱│
  ┌──────────────────────┐ │                ┌──────────────────────┐ │
  │  <<device>>          │ │ 2            1 │  <<device>>          │ │
  │  AppServer           │ ├──── <<JDBC>> ──┤  DatabaseServer      │ │
  │                      │ ╱                │                      │ ╱
  └──────────────────────┘╱                 └──────────────────────┘╱
```

一般的なプロトコルのステレオタイプは、`<<HTTP>>`、`<<HTTPS>>`、`<<TCP/IP>>`、`<<JDBC>>`、`<<REST>>`、`<<AMQP>>`、`<<SSH>>`、`<<SMTP>>` である。どれを選ぶかは、意図する詳細度の問題である。`<<TCP/IP>>` はトランスポートを示し、`<<HTTPS>>` は接続が暗号化されていることも示すため、通常はこちらのほうが有用な情報となる。

### 多重度と入れ子 {/*#multiplicity-and-nesting*/}

多重度は通信パスの端に書き、型名を必要とする。`appsrv01:ApplicationServer` のようなインスタンスは、常にちょうど1台のマシンである。

入れ子は複数の階層にわたることができ、各階層はそれを囲む階層の上で動作する。

```text
<<device>>                  ServerHardware
  <<executionEnvironment>>    Linux
    <<executionEnvironment>>    Docker Engine
      <<artifact>>                shop-app:2.4.0
```

図の目的にとって重要でない階層は省略される。たとえば、キャパシティプランではコンテナランタイムを省く。一方、リリース計画では、イメージのバージョンタグが重要な情報となる。

## 例: 3層のWebショップ {/*#example-three-tier-web-shop*/}

ショップは、ブラウザのフロントエンド、コンテナ内のアプリケーション、リレーショナルデータベースで構成される。各層はそれぞれ独自のマシンで動作し、アプリケーションサーバは2台存在し、データベースにはアプリケーションサーバからのみ到達できる。

```text
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ClientPC                                  │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Browser                             │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 0..*
               <<HTTPS>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ApplicationServer                         │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Docker Engine                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-app:2.4.0                │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 2
                <<JDBC>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  DatabaseServer                            │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  PostgreSQL 16                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-schema.sql               │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
```

この例が示すこと:

- `<<JDBC>>` パスのアプリケーションサーバ側の端にある多重度 `2` は、2台のアプリケーションサーバがデータベースにアクセスすることを表す。クライアント側の端にある `0..*` は、0台を含め任意の数のクライアントが接続できることを表す。
- *いつ*どの呼び出しが行われるかには触れていない。呼び出しの順序は[シーケンス図](./sequence-diagram.md)に属する。

## よくある間違い {/*#common-mistakes*/}

1. **ノード内のクラスやコンポーネント:** ノードが含むのはアーティファクトである。論理的な要素は[クラス図](./class-diagram.md)またはコンポーネント図に属し、`<<manifest>>` でアーティファクトと結び付けられる。
2. **プロトコルのない通信パス:** 線上に `<<HTTPS>>` や `<<JDBC>>` がなければ、図はどの接続が暗号化されているか、ファイアウォールがどのポートを開ける必要があるかを示さなくなる。
3. **デバイスと実行環境の混同:** `<<device>>` はハードウェアであり、`<<executionEnvironment>>` はその上で動作するソフトウェアである。コンテナはデバイスではない。
4. **通信パス上の矢じり:** パスには方向がない。方向は、`<<deploy>>` や `<<manifest>>` などの依存関係に属する。
5. **すべてのファイルを描くこと:** インストールと運用に関わるものだけを図に含め、すべてのライブラリや設定ファイルは含めない。
6. **多重度の欠落:** 4台のマシンからなるクラスタを、`4` なしの単一のノードとして描くと、その規模が隠れてしまう。
7. **論理的な層とノードの同一視:** プレゼンテーション層、ロジック層、データ層は論理的な分割であり、ノードは物理的な分割である。3つの層が1台のマシンで動作することも十分ありうる。
