# シーケンス図

## 概要 {/*#overview*/}

シーケンス図は、**振る舞い**を表すUML図であり、*相互作用図*のグループに属する。どの通信相手が、どのメッセージを、どの順序で交換するかを示す。相手は横に並べて配置され、時間は上から下へ流れる。

代表的な用途:

- [ユースケース](./use-case-diagram.md)の単一のシナリオの詳細化。通常は基本系列に例外を1つ加えたもの
- 1つの機能に関するオブジェクトやコンポーネントの協調の文書化
- クライアント、サーバ、データベースなど、システム間のプロトコルの記述
- 設計案を[クラス図](./class-diagram.md)と双方向に照合するレビュー: どのクラスも操作として提供していないメッセージは不足している操作を、受信メッセージのないライフラインは到達できないクラスを示す

シーケンス図が示すのは、常に*1つ*の具体的な実行である。選択や繰り返しは複合フラグメントで表現できるが、あらゆるケースを一度に網羅しようとする図は読めなくなる。そのため、1つの大きな図よりも複数の小さな図のほうが望ましい。

## 表記法 {/*#notation*/}

| 要素                    | 表記                                                   | 意味                                                           |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| フレーム                | `sd` と名前を記した五角形のタブ付き長方形           | 相互作用の境界と名前                                           |
| ライフラインのヘッド    | `name : Class`、`:Class`、または `name` を持つ長方形          | 通信相手、オブジェクト、コンポーネント、またはアクター         |
| ライフライン            | ヘッドの下の破線の縦線                                 | 時間の経過に伴う、その相手の存在                               |
| 実行仕様                | ライフライン上の細い長方形（アクティベーションバー）   | 相手が活動中、または呼び出しを処理している期間                 |
| 同期メッセージ          | 実線、塗りつぶした矢じり `──▶`                         | 送信側は応答が届くまで待機する                                 |
| 非同期メッセージ        | 実線、開いた矢じり `──>`                               | 送信側は待たずにただちに続行する                               |
| 応答メッセージ          | 破線、開いた矢じり `<- - -`                            | 制御の返却。任意で戻り値をラベルとして付ける                   |
| 自己メッセージ          | 同じライフラインから出て同じライフラインに戻る矢印     | 相手が自身の操作の1つを呼び出す                                |
| 生成メッセージ          | ライフラインのヘッドに向かう `«create»` 付きの破線矢印   | 受信側が、相互作用の途中で生成される                           |
| 破棄の発生              | ライフラインの下端の×印 `X`                            | オブジェクトが破棄され、ライフラインがそこで終わる             |
| 複合フラグメント        | 左上隅に演算子を記した長方形                           | 制御構造。例: `alt`、`opt`、`loop`、`par`                |
| オペランド              | フラグメントの区画で、破線で区切られる                 | フラグメント内の1つのケースまたは1つの分岐                    |
| ガード                  | オペランドの先頭の `[condition]`                        | そのオペランドが適用される条件                                 |
| 相互作用の利用          | 演算子 `ref` を持つフラグメント                        | 別の図として描かれた相互作用への参照                           |
| 状態不変条件            | ライフライン上の `{condition}`                         | その時点で成立していなければならない条件                       |
| ノート                  | 破線につながる角折れ長方形                             | 意味を持たないコメント                                         |

図を読みやすく保つための命名規則:

- メッセージには、`the seat is reserved` のような文ではなく、`reserve(seatNo)` のように、呼び出される操作のシグネチャを付ける
- 応答には、操作名を繰り返さず、戻り値をラベルとして付ける
- ライフラインはアクションではなくオブジェクトにちなんで命名する: `:SeatRepository` は相手であり、`Save seat` は相手ではない
- 無名のオブジェクトは `:Class`、名前付きのオブジェクトは `seat : Seat` と書き、ロールは名前のみで書く

## 構成要素 {/*#building-blocks*/}

### ライフライン、実行仕様、応答 {/*#lifeline-execution-specification-and-reply*/}

ある相手から別の相手へのメッセージは、受信側で実行仕様を開始し、応答がそれを終了させる。同期メッセージは、呼び出し側が続行する前に結果を必要とする呼び出し、たとえばメソッド呼び出しや、応答を待つHTTPリクエストに適している。

```text
   :Client                  :AuthService
      │                           │
     ┌┴┐                          │
     │ │─── login(user, pw) ────▶┌┴┐
     │ │                         │ │
     │ │<- - - - - token - - - - └┬┘
     │ │                          │
     └┬┘                          │
      │                           │
```

応答が情報を持たない場合は、省略してもよい。

### 非同期メッセージ {/*#asynchronous-message*/}

非同期メッセージは引き渡され、送信側は待たずに続行する。イベント、通知、キューへのメッセージ、別スレッドで実行される呼び出しのように、送信側が結果を必要としない場合に適している。送信側のバーは受信側のバーから独立しており、それより先に終わってもよい。

```text
:OrderService                   :MailService
      │                               │
     ┌┴┐                              │
     │ │──── sendMail(order) ───────>┌┴┐
     └┬┘                             │ │
      │                              │ │
      │                              └┬┘
      │                               │
```

### 自己メッセージ {/*#self-message*/}

自己メッセージは、ライフラインから出て、少し下で同じライフラインに戻る矢印である。検証や計算など、相手の内部ステップがフローの理解に重要な場合に描かれる。その重要性のないプライベートなヘルパー呼び出しは省略される。厳密に描かれた自己呼び出しには、入れ子の実行仕様、すなわち最初のバーの上にわずかにずらした2本目のバーが付く。

```text
:OrderService
      │
     ┌┴┐
     │ ├───┐ validate()
     │ ┌─┐◀┘
     │ │ │
     │ └─┘
     │ │
     └┬┘
      │
```

### オブジェクトの生成と破棄 {/*#creation-and-destruction-of-objects*/}

相互作用の途中ではじめて存在するようになるオブジェクトは、そのヘッドを、生成される縦の位置に描く。生成メッセージが指すのはライフラインではなくヘッドである。破棄はライフラインの末尾の×印で示される。

```text
  :Session
      │
     ┌┴┐
     │ │        «create»
     │ │- - - - - - - - - ->┌─────────┐
     │ │                    │  :Cart  │
     │ │                    └────┬────┘
     │ │──── addItem(item) ────▶┌┴┐
     │ │                        └┬┘
     │ │──── «destroy» ────────▶ X
     └┬┘
      │
```

## 複合フラグメント {/*#combined-fragments*/}

複合フラグメントは、相互作用の一部を囲む長方形である。左上隅の演算子が、囲まれたメッセージにどの制御構造、たとえば選択やループが適用されるかを決める。破線の水平線がフラグメントをオペランドに分割し、`alt` フラグメントでは各オペランドにガードが付く。

| 演算子     | 意味                                                                            | 対応するもの                   |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------ |
| `alt`      | 選択。ちょうど1つのオペランドが実行され、残りのケースは `[else]` とラベル付けされる | `if / else if / else`          |
| `opt`      | ガードが成立する場合にのみ実行される単一のオペランド                            | `else` のない `if`            |
| `loop`     | 繰り返し。`loop(min,max)` として、またはガード付きで書く                        | `while`、`for`、`do … while`   |
| `break`    | オペランドが、それを囲む相互作用の残りに置き換わる                              | 早期の `return`、例外      |
| `par`      | オペランドが並行して実行され、そのメッセージは交互に挟まりうる                  | スレッド、タスク、並列呼び出し |
| `ref`      | 別の図として描かれた相互作用への参照                                            | メソッド呼び出し、サブプロセス |
| `critical` | オペランドは、並行して実行されるオペランドによって中断されてはならない          | クリティカルセクション、ロック |
| `neg`      | 囲まれた系列は無効であり、発生してはならない                                    | 否定的なテストケース           |
| `assert`   | 囲まれた系列が、唯一有効な継続である                                            | アサーション                   |

実際には、`alt`、`opt`、`loop` で大半の図をカバーできる。

### 選択 {/*#alternative*/}

```text
      :Client                        :Booking
         │                               │
        ┌┴┐                              │
        │ │──── reserve(seatNo) ───────▶┌┴┐
        │ │                             │ │
 ┌──────┼─┼─────────────────────────────┼─┼────────┐
 │ alt  │ │ [seat is free]              │ │        │
 │      │ │<- - - - reservationId - - - │ │        │
 ├╌╌╌╌╌╌┼╌┼╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┼╌┼╌╌╌╌╌╌╌╌┤
 │      │ │ [else]                      │ │        │
 │      │ │<- - - SeatTakenError - - - -│ │        │
 └──────┼─┼─────────────────────────────┼─┼────────┘
        └┬┘                             └┬┘
         │                               │
```

`alt` フラグメントのガードは互いに排他的でなければならず、すべてのケースを網羅すべきである。

### ループ {/*#loop*/}

```text
      :Order                         :LineItem
         │                               │
        ┌┴┐                              │
 ┌──────┼─┼──────────────────────────────┼─────────┐
 │ loop │ │ [more items]                 │         │
 │      │ │──── subtotal() ────────────▶┌┴┐        │
 │      │ │<- - - - amount - - - - - - -└┬┘        │
 └──────┼─┼──────────────────────────────┼─────────┘
        └┬┘                              │
         │                               │
```

`loop(1,n)` は条件ではなく回数を表し、追加指定のない `loop` は上限のない繰り返しを意味する。

## 例: ユースケース*座席を予約する*の詳細化 {/*#example-detailing-the-use-case-book-seat*/}

ここで詳細化するシナリオは、ユースケース*座席を予約する*の基本系列である。顧客が特定の座席を予約し、システムがその座席を検索し、まだ空いていれば予約済みにする。この図は、ユースケースのテキスト記述から次の手順で導かれる。

1. ユースケースの1つのシナリオを選ぶ。通常は、テキスト記述の基本系列である。
2. きっかけとなるアクターを、最も左のライフラインにする。
3. 内部の相手を、通常はアーキテクチャの層に沿って追加する: ユーザーインターフェース、制御、ドメインオブジェクト、永続化。
4. テキストの流れの各ステップを、受信側の操作に一致する名前を持つメッセージにする。
5. テキスト記述の例外は、`alt` または `break` フラグメントにするか、それぞれ別の図にする。

```text
┌────────────────┐
│ sd BookSeat    │
├────────────────┴─────────────────────────────────────────────────────┐
│                                                                      │
│       :Customer            :BookingService         :SeatRepository   │
│           │                       │                       │          │
│          ┌┴┐                      │                       │          │
│          │ │── bookSeat(id) ────▶┌┴┐                      │          │
│          │ │                     │ │── findSeat(id) ────▶┌┴┐         │
│          │ │                     │ │<- - seat - - - - - -└┬┘         │
│          │ │                     │ │                      │          │
│          │ │              ┌──────┼─┼──────────────────────┼───────┐  │
│          │ │              │ opt  │ │ [seat is free]       │       │  │
│          │ │              │      │ │── markBooked(id) ──▶┌┴┐      │  │
│          │ │              │      │ │<- - - - ok - - - - -└┬┘      │  │
│          │ │              └──────┼─┼──────────────────────┼───────┘  │
│          │ │<- - confirmation - -└┬┘                      │          │
│          └┬┘                      │                       │          │
│           │                       │                       │          │
└──────────────────────────────────────────────────────────────────────┘
```

この例から読み取れること:

- `opt` フラグメントの失敗ケースはここでは描かれていない。`alt` でモデル化するか、別の図で扱うことになる。
- 決済のステップは、この図を読みやすく保ち、決済に独自の相互作用を与えるために、`ref` フラグメントとして挿入される。

## シーケンス図、アクティビティ図、コミュニケーション図 {/*#sequence-activity-or-communication-diagram*/}

3つとも振る舞い図である。

| 基準         | シーケンス図                             | アクティビティ図                        | コミュニケーション図                      |
| ------------ | ---------------------------------------- | --------------------------------------- | ----------------------------------------- |
| 焦点         | 時間に沿ったメッセージ交換               | プロセスの制御フロー                    | 協調の構造                                |
| 時間         | 明示的、縦軸として                       | 暗黙的、フローの向きを通じて            | メッセージの番号付けを通じてのみ          |
| 参加者       | ライフラインを横に並べる                 | 任意、パーティションとして              | オブジェクトを自由に配置し、リンクで結ぶ  |
| 分岐         | 複合フラグメント、すぐに混み合う         | デシジョンノードとマージノード、読みやすい | ほとんど読めない                        |
| 並行性       | `par` フラグメント                       | フォークとジョイン                      | 可能だが読みにくい                        |
| 典型的な用途 | 1つのシナリオの詳細化                    | プロセス全体のモデリング                | どのオブジェクトがどのオブジェクトを知っているかの提示 |

目安:

- 分岐とループが多く、参加者が少ない => [アクティビティ図](./activity-diagram.md)
- 分岐が少なく、参加者が多く、順序が重要 => シーケンス図
- *どの順序で*ではなく*誰が誰とつながっているか*が問い => [コミュニケーション図](./further-uml-diagrams.md#communication-diagram)
- *単一の*オブジェクトの生涯全体にわたる振る舞い => [ステートマシン図](./state-machine-diagram.md)

## よくある間違い {/*#common-mistakes*/}

1. **時間軸の無視:** 時間はすべてのライフラインにわたって上から下へ流れる。そのため、上向きに描かれた矢印は意図した順序を逆転させる。同じ高さにある2つのメッセージには、定義された順序がない。
2. **応答を実線の矢印で描くこと:** 応答は、開いた矢じりの破線で描く。塗りつぶした矢じりの実線は、逆方向の新たな呼び出しとして読まれる。
3. **同期と非同期の混同:** 塗りつぶした矢じりは、送信側が応答を待つことを意味する。イベント、通知、キューへのメッセージは非同期であり、開いた矢じりを使う。
4. **閉じられていない実行仕様:** 呼び出し側のバーは、少なくとも応答が届くまで延びていなければならない。それより早く終わるバーは、呼び出し側がすでに終了していたことを表す。
5. **ライフライン上のオブジェクトではなくアクティビティ:** ライフラインは `:SeatRepository` のような通信相手を表す。`Check availability` のようなステップは相手ではなく、代わりにメッセージとなる。
6. **altのオペランドにガードがない:** ガードがなければ、図は `alt` フラグメントの各オペランドがどの条件で適用されるかを示さない。
