# コンポーネント図

## 概要 {/*#overview*/}

コンポーネント図は、**構造**を表すUML図である。システムが交換可能な構成要素にどのように分割されているか、またそれらの構成要素が互いにどのインターフェースを提供し、要求するかを示す。

UMLにおけるコンポーネントとは、内部が隠蔽され、振る舞いがそのインターフェースによって完全に定義される、システムのモジュール化された部分である。この定義から次の2つの帰結が導かれる。

- コンポーネントは、同じインターフェースを提供する任意の別のコンポーネントで置き換えられる。
- コンポーネントの外部にあるものは、そのコンポーネントの内部の動作に依存してはならない。

代表的な用途:

- 粗い粒度の概観としてのシステムアーキテクチャの文書化
- 実装開始前の、チーム間のインターフェース契約の確定
- 循環的または過剰な結合が明らかになるよう、依存関係を可視化すること
- どの部分を独立して構築、テスト、配置、置換できるかの計画

## 表記法 {/*#notation*/}

| 要素                                                                | 表記                                                            | 意味                                                                                        |
| ------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| [コンポーネント](#component)                                        | キーワード `<<component>>` を付けた長方形                       | システムの、交換可能で自己完結した部分                                                      |
| [コンポーネントアイコン](#component)                                | 右上に2つの突起を持つ小さな長方形                               | コンポーネントの代替表示で、キーワードの代わりに、または併用できる                           |
| [提供インターフェース](#provided-and-required-interfaces)           | 塗りつぶした円で終わる線（*ボール*、*ロリポップ*）              | コンポーネントが環境に提供するサービス                                                      |
| [要求インターフェース](#provided-and-required-interfaces)           | 半円で終わる線（*ソケット*）                                    | コンポーネントが環境から必要とするサービス                                                  |
| [アセンブリコネクタ](#assembly-connector)                           | ボールの上に置かれたソケット                                    | あるコンポーネントの要求が、別のコンポーネントの提供によって満たされる                      |
| [ポート](#ports-and-delegation-connectors)                          | コンポーネントの境界上にある小さな正方形                        | インターフェースを公開する、名前付きの相互作用点                                            |
| [デリゲーションコネクタ](#ports-and-delegation-connectors)          | ポートから内部コンポーネントへ向かう矢印                        | ポートに到着したものを、それを処理する部分へ転送する                                        |
| [インターフェース](#provided-and-required-interfaces)（長方形表記） | キーワード `<<interface>>` を付けた長方形                       | 操作を明記した契約で、名前のみを示すボールを補完する                                        |
| [依存関係](#dependencies)                                           | 開いた矢じりの破線矢印                                          | 名前付きインターフェースを介さず、依存元が依存先を必要とする                                |
| [アーティファクト](#artifacts-and-manifestation)                    | キーワード `<<artifact>>` を付けた長方形                        | 物理的なファイル: `.jar`、`.dll`、`.war`、スクリプト、設定ファイル                       |
| [マニフェステーション](#artifacts-and-manifestation)                | アーティファクトからコンポーネントへ向かう、`<<manifest>>` とラベル付けされた破線矢印 | アーティファクトが、そのコンポーネントの物理的な実現である                          |
| [入れ子のコンポーネント](#nested-components)                        | 別のコンポーネントの内部に描かれたコンポーネント                | 内部構造で、外側のコンポーネントを構成する*部品*                                            |
| ノート                                                              | 破線につながる角折れ長方形                                      | 意味を持たないコメント                                                                      |

図を読みやすく保つための命名規則:

- コンポーネントは責務を表す名詞で命名する: `PaymentService` とし、`DoPayment` や `Payments2` としない。
- インターフェースはサービスにちなんで命名し、通常は先頭に `I` を付ける: `IPayment`、`IInventory`。
- 同じインターフェース名は、常に同じ契約を指す。図の中で、1つの名前を2つの異なるものに使ってはならない。

## 構成要素 {/*#building-blocks*/}

### コンポーネント {/*#component*/}

コンポーネントに決まった大きさはない。典型的には、配置可能なサービス、ライブラリ、アーキテクチャの層、ドメインの自己完結した領域が選ばれる。

```text
 ╭──────────────────────╮
 │ <<component>>     ⊞  │
 │ PaymentService       │
 ╰──────────────────────╯
```

### 提供インターフェースと要求インターフェース {/*#provided-and-required-interfaces*/}

コンポーネント間の依存関係は、可能な限り、内部への直接アクセスではなくインターフェースを通じて表現する。例外については[依存関係](#dependencies)を参照。

- **提供インターフェース**は、先端に塗りつぶした円を持つ線で描かれる。*これが提供されており、利用できる*という約束である。
- **要求インターフェース**は、先端に半円を持つ線で描かれる。*これが必要であり、誰かが供給しなければならない*という要求である。

```text
   provided interface                  required interface
   (ball, lollipop)                    (socket)

 ╭──────────────────────╮            ╭──────────────────────╮
 │ <<component>>     ⊞  │            │ <<component>>     ⊞  │
 │ PaymentService       │───○        │ OrderService         │───C
 ╰──────────────────────╯            ╰──────────────────────╯
```

ボールが示すのはインターフェース名のみである。操作自体が重要な場合、インターフェースは、キーワード `<<interface>>` と操作リストを持つ長方形としても描かれ、ボールに結び付けられる。

### アセンブリコネクタ {/*#assembly-connector*/}

アセンブリコネクタは、要求インターフェースと提供インターフェースを結ぶ。図の上では、ソケットがボールの上に置かれ、このため、この表記は*ボールとソケット*とも呼ばれる。

```text
 ╭──────────────────────╮            ╭──────────────────────╮
 │ <<component>>     ⊞  │ IPayment   │ <<component>>     ⊞  │
 │ OrderService         │───C○───────│ PaymentService       │
 ╰──────────────────────╯            ╰──────────────────────╯
```

このコネクタは、`OrderService` が `PaymentService` を `IPayment` **のみ**を通じて利用することを表す。`IPayment` を提供する任意のコンポーネントが、`PaymentService` の代わりになりうる。

### ポートとデリゲーションコネクタ {/*#ports-and-delegation-connectors*/}

ポートは、コンポーネントの境界上にある、明示的に名前を付けた相互作用点である。境界線上の小さな正方形として描かれ、その地点で到達できるインターフェースをまとめる。1つのコンポーネントが同じインターフェースを複数の場所で提供する場合、たとえばアクセス規則の異なる内部用と外部用のエントリポイントがある場合に、ポートが有用になる。

コンポーネントの内部では、デリゲーションコネクタがポートから、実際にリクエストを処理する部分へつながる。

```text
               IOrdering
                   ○
                   │
 ╭─────────────────■─────────────────────────────────────────────╮
 │ <<component>>   │                                          ⊞  │
 │ OrderManagement │  delegation                                 │
 │                 │                                             │
 │    ╭────────────┴─────────╮            ╭──────────────────╮   │
 │    │ <<component>>     ⊞  │  IPricing  │ <<component>> ⊞  │   │
 │    │ OrderIntake          │───C○───────│ PricingEngine    │   │
 │    ╰──────────────────────╯            ╰──────────────────╯   │
 │                                                               │
 ╰───────────────────────────────────────────────────────────────╯
```

外部から見えるのは、ポートにある `IOrdering` のみである。その背後に `OrderIntake` と `PricingEngine` が存在すること、およびそれらがどう結線されているかは、いつでも変更できる。

### 入れ子のコンポーネント {/*#nested-components*/}

コンポーネントは、さらに別のコンポーネントを含むことができる。内側のものは、外側のコンポーネントを構成する*部品*である。入れ子によって、コンポーネント図は複数の抽象度に対応するツールとなる。最上位では少数のサブシステムを示し、それぞれを独自の図で詳細化できる。

詳細化の一貫性を保つ規則は2つある。

- 外側のコンポーネントのすべてのインターフェースは、内側の部品に委譲されるか、外側のコンポーネント自身によって実現される。
- 内側の部品が外部に直接接続されることはない。接続は常に、それを囲むコンポーネントのポートを経由する。

### アーティファクトとマニフェステーション {/*#artifacts-and-manifestation*/}

コンポーネントは論理的な単位であり、アーティファクトは物理的なファイルである。両者の関係は*マニフェステーション*と呼ばれ、アーティファクトからコンポーネントへ向かう、キーワード `<<manifest>>` 付きの破線矢印で描かれる。

```text
 ╭──────────────────────────────╮
 │ <<artifact>>                 │
 │ payment-service.jar          │
 ╰───────────────┬──────────────╯
                 ╎
                 ╎ <<manifest>>
                 ▼
 ╭───────────────────────────────╮
 │ <<component>>              ⊞  │
 │ PaymentService                │
 ╰───────────────────────────────╯
```

この対応は1対1である必要はない。1つのアーティファクトが複数のコンポーネントを具現化することも、1つのコンポーネントが複数のアーティファクトにまたがることもある。たとえば、実装と別の設定ファイルである。

### 依存関係 {/*#dependencies*/}

インターフェースのほかに、単純な依存関係を、開いた矢じりの破線矢印として描くこともできる。これは、契約を示さずに*依存元が依存先を必要とする*ことを意味し、より弱く、精度の低い記述である。

依存関係は、固有のインターフェースを本当に持たない関係、たとえば共有データモデルの利用や、それ以上モデル化されない外部システムの利用に適している。インターフェースが存在する場合は、依存関係が*何を通じて*行われるかを示せるのはこの表記だけであるため、ボールとソケットの表記が望ましい。

## 実装への対応 {/*#mapping-to-implementation*/}

| コンポーネント図     | 典型的な実装                                                                   |
| -------------------- | ------------------------------------------------------------------------------ |
| コンポーネント       | 配置可能なサービス、Maven/Gradleモジュール、npmパッケージ、.NETアセンブリ      |
| 提供インターフェース | モジュールの公開API、RESTリソース、メッセージトピック                          |
| 要求インターフェース | 注入された依存関係、クライアントスタブ                                         |
| アセンブリコネクタ   | 依存性注入コンテナまたはコンポジションルートでの結線                           |
| ポート               | 公開されたエンドポイント。たとえばベースURLやキュー名                          |
| デリゲーションコネクタ | エントリポイントから、リクエストを処理する内部クラスへの転送                 |
| アーティファクト     | ビルド成果物: `.jar`、`.dll`、`.war`、コンテナイメージ、バンドル            |
| マニフェステーション | コンポーネントのコードをそのファイルにパッケージ化するビルドステップ           |
| 依存関係             | 合意された契約のない、インポートまたは `require`                                 |

## 他の図との区別 {/*#delimitation-from-other-diagrams*/}

### コンポーネント図とクラス図 {/*#component-diagram-and-class-diagram*/}

| 観点              | コンポーネント図                           | クラス図                              |
| ----------------- | ------------------------------------------ | ------------------------------------- |
| 示す単位          | サブシステム、サービス、モジュール         | クラス、属性、操作                    |
| 粒度              | 粗い、1つの図につき少数のボックス          | 細かい、しばしば数十のクラス          |
| 関係の種類        | 提供/要求インターフェース、アセンブリ      | 関連、継承、集約                      |
| 答える問い        | どの部分が存在し、どう結合しているか       | 1つの部分が内部でどう構成されているか |
| 典型的な対象      | アーキテクチャ、チームの境界、計画         | 単一のコンポーネントの実装            |

### コンポーネント図と配置図 {/*#component-diagram-and-deployment-diagram*/}

コンポーネント図は*論理的*であり、[配置図](./deployment-diagram.md)は*物理的*である。

| 観点              | コンポーネント図                       | 配置図                                     |
| ----------------- | -------------------------------------- | ------------------------------------------ |
| 主要な要素        | コンポーネント                         | ノード: ハードウェア、仮想マシン、コンテナ |
| 答える問い        | ソフトウェアがどう構成されているか     | ソフトウェアがどこで動くか                 |
| 関係              | インターフェースとコネクタ             | 通信経路、プロトコル                       |
| アーティファクト  | コンポーネントのマニフェステーションとして現れる | ノードへの配置として現れる         |

## 例: オンラインショップ {/*#example-online-shop*/}

ショップは、ユーザーインターフェース、注文サービス、決済サービス、在庫サービスで構成される。ユーザーインターフェースは注文がどう処理されるかを何も知らず、`IOrdering` だけを必要とする。注文サービスは `IPayment` と `IStock` を必要とするが、どのコンポーネントがそれらを供給するかは知らない。

```text
 ╭────────────────────╮          ╭────────────────────╮          ╭────────────────────╮
 │ <<component>>   ⊞  │IOrdering │ <<component>>   ⊞  │IPayment  │ <<component>>   ⊞  │
 │ ShopUI             │───C○─────│ OrderService       │───C○─────│ PaymentService     │
 ╰────────────────────╯          ╰──────────┬─────────╯          ╰────────────────────╯
                                            ∩
                                            ○  IStock
                                            │
                                 ╭──────────┴─────────╮
                                 │ <<component>>   ⊞  │
                                 │ StockService       │
                                 ╰────────────────────╯
```

この例が示すこと:

- `ShopUI` はソケットを1つだけ持つため、単一の契約に結合している。2つ目のフロントエンド、たとえばモバイルアプリを、`IOrdering` の背後を何も変更せずに追加できる。
- `OrderService` は2つのソケットを持つ。`OrderService` のテストでは、その両方を、`PaymentService` と `StockService` で、またはテストダブルで満たす必要がある。ソケットが1つ増えるごとに、用意すべき依存関係が1つ増えるため、ソケットの多いコンポーネントは単独でのテストが難しい。

現実的な拡張としては、`OrderService`、`PaymentService`、`StockService` を1つのコンポーネント `Backend` で囲み、`IOrdering` を公開してそれを `OrderService` に委譲する単一のポートを持たせる形が考えられる。その場合、`ShopUI` はそのポートに接続され、バックエンドの内部構造は交換可能になる。

## よくある間違い {/*#common-mistakes*/}

1. **インターフェースなしで接続されたコンポーネント:** 単純な線は2つのコンポーネントが結合していることを示すが、どの契約を通じてかは示さない。インターフェースが存在する場合は、ボールとソケットで描く。
2. **ボールとソケットの取り違え:** 塗りつぶした円はサービスを*提供する*コンポーネントに、半円はそれを*必要とする*コンポーネントに属する。
3. **提供元のない要求インターフェース:** 開いたソケットは、システムが動作できないことを意味する。コンポーネントが欠けているか、その要求が不要になっている。
4. **コンポーネントとして描かれたクラス:** 属性、操作、関連はクラス図に属する。
5. **境界を越えて接続された内部部品:** 内側のコンポーネントから外部へ直接つなぐコネクタは、それを囲むコンポーネントのポートを迂回している。
6. **循環依存:** 互いのインターフェースを要求し合う2つのコンポーネントは、別々に構築、配置、置換することができなくなる。
7. **異なる契約に対する1つのインターフェース名:** 同じ名前を持つ2つのボールは、同じ操作を提供しなければならない。
8. **コンポーネントとアーティファクトの混同:** `PaymentService` がコンポーネントであり、`payment-service.jar` がそれを具現化するアーティファクトである。
9. **1つの図に多すぎるコンポーネント:** ボックスが多すぎると図が読めなくなる。詳細は、単一のコンポーネントを詳細化する別の図に置くべきである。
