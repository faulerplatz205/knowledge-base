# ユースケース図

## 概要 {/*#overview*/}

ユースケース図は、UMLの**振る舞い**を表す図である。システムが環境に対して*どの*サービスを提供し、*誰*がそれを利用するかを示すが、それらのサービスが*どのように*実装されるかについては意図的に何も述べない。したがってこの図はシステムの外部から見た姿であり、定義されるのは**システムのスコープ**である。

典型的な用途:

- プロジェクトのスコープ設定: *何がシステムに含まれ、何が含まれないか*に対する早期の答え
- 機能要求を、ビジネス上の価値を持つ単位に構造化すること
- 開発者、クライアント、ドメインエキスパートに共通の語彙を提供すること
- ユースケースごとに1つの記述を持つ、要求文書の索引として機能すること

ユースケースは常に、少なくとも1人のアクターにとって**価値のある観察可能な結果を伴う、完結した自己完結型のサービス**である。`Place order`はユースケースであり、`Click the order button`はユースケースではない。

## 表記法 {/*#notation*/}

| 要素            | 表記                                                               | 意味                                                                    |
| --------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| アクター        | 棒人間、下に名前                                                   | システムの外部にあり、システムと相互作用する役割                        |
| アクター(システム) | キーワード`<<actor>>`付きの長方形、または棒人間                     | アクターの役割を担う外部システム                                        |
| システム境界    | 上辺にシステム名を記した長方形                                     | 内側に描かれたものはすべて、対象システムの一部である                    |
| ユースケース    | 内側に名前を記した楕円、常に境界の内側                             | システムの完結した1つのサービス、*動詞 + 目的語*で命名する             |
| 関連            | 矢頭のない実線                                                     | アクターがユースケースに参加する                                        |
| Include         | `<<include>>`付きの破線矢印、含まれるユースケースを指す                  | 基底ユースケースは含まれるユースケースを**常に**実行する                |
| Extend          | `<<extend>>`付きの破線矢印、**基底**ユースケースを指す                  | 拡張するユースケースは条件付きで実行される**場合がある**                |
| 拡張ポイント    | 基底ユースケースのコンパートメント内の名前付きの位置               | 拡張が挿入される場所                                                    |
| 汎化            | 一般的な要素側に白抜き三角形を持つ実線                             | アクターまたはユースケースの特化                                        |
| ノート          | 破線につながれた折り目付きの長方形                                 | 意味を持たない注釈、例えばextend関係の条件                              |

図を読みやすく保つための命名規則:

- ユースケースは、アクターの視点から、実装ではなくドメインの言葉で*動詞 + 目的語*として命名する: `Place order`や`Cancel invoice`とし、`Order management`、`orderService()`、`Set the invoice status to 0`とはしない
- アクターは人物ではなく**役割**に基づいて命名する: `Clerk`とし、`Ms Weber`とはしない。1人の人物が複数の役割を担いうるためである

## 構成要素 {/*#building-blocks*/}

### アクター {/*#actors*/}

アクターは、システムの外部にあり、システムと情報を交換する役割である。アクターは必ずしも人間とは限らない。

- **主アクター:** ユースケースを起動し、その恩恵を受ける。慣例として左側に描く
- **副アクター:** ユースケースの実行中にシステムから呼び出され、システムが必要とするものを提供する。慣例として右側に描く
- **人間のアクター:** 役割を担う人物で、棒人間として描く
- **システムアクター:** 外部システム、サービス、またはタイマーで、棒人間、またはキーワード`<<actor>>`付きの長方形として描く

### システム境界 {/*#system-boundary*/}

システム境界は、システム名を記した長方形である。責任範囲と環境を分離する。

- ユースケースはシステムのサービスであるため、**常に**境界の内側に描く
- アクターは構築の対象ではないため、**常に**境界の外側に描く
- 関連は、境界をまたぐ唯一の線である

### 関連 {/*#association*/}

アクターとユースケースの間の実線は、そのアクターがそのユースケースに参加することを意味する。関連はデータフローの方向ではなく参加を表すため、矢頭を持たない。`1`や`*`のような多重度を両端に記述してもよいが、実務ではほとんど必要とされない。

関連が存在するのはアクターとユースケースの間のみであり、2つのユースケースの間や2つのアクターの間には存在しない。

### Include {/*#include*/}

`<<include>>`は、必須の再利用を表す。基底ユースケースは、そのフローの決まった時点で、含まれるユースケースを常に実行する。破線矢印は、基底ユースケースから含まれるユースケース**へ**向かう。

```text
 ╭─────────────────────╮                     ╭─────────────────────╮
(      Place order      )╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌►(   Authenticate user   )
 ╰─────────────────────╯     <<include>>     ╰─────────────────────╯
```

含まれるユースケースは、複数の基底ユースケースで共有される断片である。`Authenticate user`は`Manage wish list`と`View invoices`でも必要であり、これを切り出すことで3回記述する手間が省ける。含まれるユースケースは単独で起動されることがないため、一般に独自のアクターとは関連付けられない。

### Extend {/*#extend*/}

`<<extend>>`は、任意の振る舞いを表す。拡張するユースケースは条件が成立する場合にのみ実行され、基底ユースケースの名前付きの**拡張ポイント**に挿入される。その破線矢印は`<<include>>`とは逆向きで、拡張するユースケースから基底ユースケース**へ**向かう。

```text
 ╭─────────────────────────────╮
(          Place order          )
(  ---------------------------  )              ╭────────────────────╮
(  extension points:            )◄╌╌╌╌╌╌┬╌╌╌╌╌(   Redeem voucher     )
(   payment method selected     )       ╎      ╰────────────────────╯
 ╰─────────────────────────────╯   <<extend>>
                                        ╎
                     ┌──────────────────┴────────╮
                     │ Condition:                │
                     │ {voucher code entered}    │
                     │ extension point:          │
                     │  payment method selected  │
                     └───────────────────────────┘
```

基底ユースケースは、拡張がなくても完結している。`Place order`はバウチャーなしでも問題なく動作するが、認証なしでは動作しない。条件は制約であるため、波括弧で囲む。UMLでは、これが参照する拡張ポイントとともに、extend関係に付けたノートに示される。多くのツールや教科書では、ノートを矢印の横に書いた`<<extend>> {condition}`に省略しており、これは同じ内容の許容された短縮形である。

2つの関係は、簡単なテストで区別できる:

- 基底ユースケースを、もう一方に一度も言及せずに記述できるか。できるなら`<<extend>>`である
- もう一方を取り除くと基底ユースケースが成立しなくなるか。成立しなくなるなら`<<include>>`である

### 汎化 {/*#generalization*/}

汎化は、アクターにもユースケースにも当てはまる*〜の一種である*という関係を表す。線は、より一般的な要素側に白抜き三角形を持つ。

アクターの汎化: 特化したアクターは、一般的なアクターのすべての関連を継承し、独自の関連を追加できる。

```text
                  ○
                 ╱│╲
                 ╱ ╲
              Customer
                  △
       ┌──────────┴──────────┐
       │                     │
       ○                     ○
      ╱│╲                   ╱│╲
      ╱ ╲                   ╱ ╲
  Registered               Guest
   customer
```

`Registered customer`と`Guest`はどちらも`Customer`のすべての関連を継承するため、`Search catalogue`を3回接続する必要はない。

```text
                  ╭───────────────╮
                 (  Pay for order  )
                  ╰───────────────╯
                          △
           ┌──────────────┴──────────────┐
           │                             │
 ╭────────────────────╮       ╭─────────────────────╮
(  Pay by credit card  )     (  Pay by direct debit  )
 ╰────────────────────╯       ╰─────────────────────╯
```

ユースケースの汎化は強力だが、使いすぎやすい。バリエーションが任意のステップのみで異なる場合は、`<<extend>>`のほうが明確な選択肢である。

## 図と記述 {/*#diagram-and-description*/}

図だけでは仕様ではなく手早い概観にすぎない。ユースケースとその関係には名前を付けるが、フローについては何も述べない。詳細は**ユースケース記述**にあり、ユースケースごとに1つ、連続した文章またはテンプレートで記述される。

| フィールド        | 内容                                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| 名前              | 図中のラベルと同一、*動詞 + 目的語*                                        |
| 概要説明          | 目的とビジネス上の価値についての1〜2文                                     |
| アクター          | 主アクター、副アクター                                                     |
| 事前条件          | ユースケースの開始前に成立していなければならないこと                       |
| 事後条件          | 正常に実行された後に成立していること                                       |
| トリガー          | ユースケースを開始するイベント                                             |
| 基本シナリオ      | すべてが順調に進む場合の、番号付きの標準フロー                             |
| 代替フロー        | それでも目標に到達する逸脱、基本シナリオに対する番号で示す                 |
| 例外              | 目標の達成を妨げる逸脱                                                     |
| 非機能要件        | 応答時間、データ量、法的制約                                               |

`Place order`の記入例:

- **事前条件:** ショッピングカートに少なくとも1つの商品が含まれており、顧客が認証済みである
- **事後条件:** 注文がステータス`paid`で保存され、確認が送信されている
- **トリガー:** 顧客がショッピングカートを確定する
- **基本シナリオ:** 1. システムが注文の概要を表示する => 2. 顧客が支払方法を選択する => 3. システムが商品を引き当てる => 4. システムが支払を処理する => 5. システムが注文を確定する
- **代替フロー2a:** 顧客がバウチャーコードを入力し、システムが金額を減額してステップ3から続行する
- **例外3a:** 商品が在庫切れになっており、システムが分納を提案するか、注文をキャンセルする

シナリオは、ユースケースを通る*具体的な1つの経路*である。基本シナリオは想定される経路であり、代替フローはそれ以外の経路である。図中で`<<extend>>`として描かれたものは、記述では代替フローとして現れ、`<<include>>`として描かれたものは、別の記述への参照として現れる。

## 要求分析における役割 {/*#role-in-requirements-analysis*/}

- **[要求仕様書](../../projectmanagement/requirements-specification.md#requirement-specification)**はクライアントが作成し、*何が*、*なぜ*必要かを記述する。ユースケースは、解決策を規定せずに1つひとつの要求を記述するため、その構造として優れている
- **[機能仕様書](../../projectmanagement/requirements-specification.md#functional-specification)**は受託者が作成し、要求を*どのように*満たすかを記述する。ユースケース図は引き継がれ、記述は詳細化され、技術的な制約が追加される
- **トレーサビリティ:** すべての要求は少なくとも1つのユースケースまで、すべてのユースケースは少なくとも1つの要求まで追跡できるべきである。要求のないユースケースは過剰な作り込みであり、ユースケースのない要求は見落とされている
- **見積りと計画:** ユースケースは、それぞれを単独で受け入れられるため、工数見積り、リリース計画、受け入れテストの自然な単位である
- **テストの基礎:** 基本シナリオからは正常系のテストケースが得られ、すべての代替フローとすべての例外からは、それぞれ少なくとも1つのテストケースが得られる

ユーザーストーリーは計画上の小さなインクリメントであり、ユースケースはあらゆる代替を含む完結したサービスである。1つのユースケースは、通常、複数のユーザーストーリーに分解される。

## 例: オンラインショップ {/*#example-online-shop*/}

対象システムはオンラインショップである。顧客はカタログを検索し、注文を行う。注文には常に認証と支払処理が必要であり、任意でバウチャーの利用により拡張できる。支払処理では外部の決済プロバイダを呼び出す。

```text
                                 Online Shop
         ┌──────────────────────────────────────────────────────────┐
         │                                                          │
         │           ╭────────────────────╮                         │
    ┌────┼──────────(   Search catalogue   )                        │
    │    │           ╰────────────────────╯                         │
 ○  │    │                                                          │
╱│╲─┤    │                                                          │
╱ ╲ │    │           ╭────────────────────╮     ╭────────────────╮  │
    └────┼──────────(     Place order      )◄╌╌(  Redeem voucher  ) │
Customer │           ╰────────────────────╯     ╰────────────────╯  │
         │                  ╎       ╎       <<extend>>              │
         │      <<include>> ╎       ╎ <<include>>                   │
         │              ┌───┘       └───────────┐                   │
         │              ▼                       ▼                   │
         │     ╭─────────────────╮      ╭────────────────╮          │  ○
         │    (  Authenticate     )    (  Process payment )─────────┼─╱│╲
         │    (      user         )     ╰────────────────╯          │ ╱ ╲
         │     ╰─────────────────╯                                  │
         │                                                          │
         └──────────────────────────────────────────────────────────┘
                                                                    Payment
                                                                   Provider
```

この例が示すこと:

- `Customer`は左側の主アクターであり、`Payment Provider`は右側の副システムアクターである。ショップが決済プロバイダを呼び出すのであり、その逆ではない
- `Authenticate user`は、これなしでは注文を行えないためincludeされており、単独で起動されることがないため独自の関連を持たない
- `Redeem voucher`は`Place order`をextendする。これを取り除いても`Place order`は完全に機能するというのが、まさに`<<extend>>`の基準である

## よくある間違い {/*#common-mistakes*/}

1. **includeとextendの取り違え:** `<<include>>`は基底ユースケースから離れる向きで*常に*を意味し、`<<extend>>`は基底ユースケースへ向かう向きで*場合によって*を意味する
2. **実線と破線の取り違え:** 関連と汎化は実線で描き、`<<include>>`と`<<extend>>`は破線矢印で描く
3. **ユースケースの代わりに処理ステップを記述:** `Enter customer number`、`Validate input`、`Save record`はフロー内のステップであり、ビジネス上の価値を持つサービスではない。これらはユースケース記述またはアクティビティ図に属する
4. **システム境界の欠落:** 境界がなければ、図はどの機能がシステムに属するかを示さなくなり、スコープが交渉可能になってしまう
5. **境界の内側にアクターを配置:** アクターは構築対象の一部ではないため、定義上、境界の外側にある。内側に描かれたアクターは、通常、コンポーネントを役割と取り違えていることを示す
6. **includeによる機能分解:** すべてのユースケースを3つのincludeされたサブユースケースに分解すると、図が呼び出しツリーになってしまう。`<<include>>`は複数の基底ユースケースにまたがる再利用のためのものであり、単一のフローを構造化するためのものではない
7. **ユースケース間の関連:** 2つの楕円の間にキーワードなしで引かれた実線は、UMLでは意味を持たない。ユースケース間の関係は`<<include>>`、`<<extend>>`、または汎化のみである
8. **個人名や個人の役職名によるアクターの命名:** アクターは役割である。同じ人物が、あるユースケースでは`Clerk`、別のユースケースでは`Customer`となりうる
9. **関連への矢頭の付加:** 関連は参加を表すものであり、方向を持たない
10. **記述のない図:** 図はユースケースに名前を付けるだけで、仕様化はしない。図しかないプロジェクトには、索引はあっても中身がない
11. **名前への技術用語の使用:** `POST /orders`や`saveOrder()`は実装であり、外部から見たサービスではない。名前はクライアントが理解できるものでなければならない
12. **extendの条件への角括弧の使用:** 条件は制約であるため、extend関係に付けたノート内の波括弧に記述する。`[condition]`は、[アクティビティ図](./activity-diagram.md)、[ステートマシン図](./state-machine-diagram.md)、[シーケンス図](./sequence-diagram.md)のガード記法である
