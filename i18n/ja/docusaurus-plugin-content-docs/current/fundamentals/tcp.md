# TCP (Transmission Control Protocol)

## 概要 {/*#overview*/}

TCPは、[OSI参照モデル](./osi-model.md)のレイヤ4にあたるコネクション型のトランスポートプロトコルであり、RFC 9293で規定されている。IPの信頼性のないパケット配送を、2つのアプリケーション間の信頼性のある順序保証付きバイトストリームに変換する。一方の側で書き込まれたデータは、もう一方の側に欠落なく、正しい順序で、重複なしに到着するか、そうでなければコネクションがエラーを通知する。TCPのエンドポイントは、IPアドレスとポート番号の組み合わせによって指定される。

---

## 特性 {/*#characteristics*/}

| 項目                  | TCPでの動作                                                               |
| --------------------- | ------------------------------------------------------------------------- |
| コネクション          | コネクション型、最初のペイロードの前にコネクションが確立される            |
| 配送                  | 信頼性あり、失われたセグメントは再送される                                |
| 順序                  | 保証される、セグメントは配送前にシーケンス番号で並べ替えられる            |
| 重複                  | 検出され破棄される                                                        |
| データモデル          | 連続したバイトストリーム、メッセージの境界は保持されない                  |
| 方向                  | 全二重、双方が同時に送信できる                                            |
| フロー制御            | あり、受信ウィンドウによる                                                |
| 輻輳制御              | あり、送信レートはネットワークの負荷に応じて調整される                    |
| ヘッダサイズ          | 最小20バイト、オプション付きで最大60バイト                                |
| ブロードキャスト / マルチキャスト | 不可、コネクションのエンドポイントは常に2つである            |

これらの保証に伴うオーバーヘッドは、ヘッダの大型化、コネクション確立のための追加の往復、および失われたセグメントを再送する際の遅延である。

## セグメントヘッダ {/*#segment-header*/}

| フィールド             | 目的                                                                   |
| ---------------------- | ---------------------------------------------------------------------- |
| 送信元ポート           | 送信側アプリケーションのポート                                         |
| 宛先ポート             | 受信側アプリケーションのポート                                         |
| シーケンス番号         | このセグメントの先頭ペイロードバイトのバイトストリーム内での位置       |
| 確認応答番号           | このセグメントの送信側が次に受信を期待するバイト                       |
| フラグ                 | 制御ビット、以下を参照                                                 |
| ウィンドウ             | このセグメントの送信側が現在受け入れ可能なバイト数                     |
| チェックサム           | ヘッダとペイロードに対する誤り検出                                     |
| オプション             | 最大セグメントサイズ、ウィンドウスケーリング、選択的確認応答           |

### 制御フラグ {/*#control-flags*/}

| フラグ                    | 意味                                                                |
| ------------------------- | ------------------------------------------------------------------- |
| `SYN` (Synchronize)     | コネクションを要求し、シーケンス番号を同期する                      |
| `ACK` (Acknowledgement) | 確認応答番号が有効である                                            |
| `FIN` (Finish)          | この方向にはこれ以上データを送信しない                              |
| `RST` (Reset)           | 正規の切断手順を踏まずにコネクションを即座に中断する                |
| `PSH` (Push)            | データを遅延なくアプリケーションに渡すよう受信側に要求する          |
| `URG` (Urgent)          | 緊急データを示す(実際にはほぼ使用されない)                          |

## コネクションの確立 (スリーウェイハンドシェイク) {/*#connection-establishment-three-way-handshake*/}

双方が自身の初期シーケンス番号(図中の`x`と`y`)を通知し、相手側の番号を`ack = x + 1`または`ack = y + 1`で確認する。

```text
Client                                           Server

  | ---- SYN, seq = x -------------------------> |   listening
  |                                              |
  | <--- SYN, ACK, seq = y, ack = x + 1 -------- |   connection accepted
  |                                              |
  | ---- ACK, ack = y + 1 ---------------------> |   connection established
  |                                              |
  | ==== payload ==============================> |
```

- クライアントは2番目のセグメントの後に、サーバは3番目のセグメントの後に、コネクションが双方向で機能することを把握する。
- ハンドシェイクにより、ペイロードの最初のバイトを送信できるようになるまでに1往復分のコストがかかる。
- 閉じているポートに送信された`SYN`には`RST`が返される。ポートスキャンは、これによって閉じたポートとフィルタされたポートを区別する。

---

## コネクションの切断 {/*#connection-teardown*/}

正規の切断では各方向を個別に閉じるため、4つのセグメントを要する。`FIN`は*この側の送信が完了した*ことのみを意味する。もう一方の方向では、引き続きデータが流れる場合がある(ハーフクローズ)。

```text
Client                                           Server

  | ---- FIN ----------------------------------> |
  | <--- ACK ----------------------------------- |
  | <--- FIN ----------------------------------- |
  | ---- ACK ----------------------------------> |
  |                                              |
  | (TIME_WAIT, then the connection is released) |
```

先に切断した側は、古いコネクションの遅延セグメントが同じポートの組を使う新しいコネクションのセグメントと取り違えられないよう、短時間`TIME_WAIT`の状態にとどまる。`RST`はこの手順を省略し、送信途中のデータをすべて破棄する。

## 信頼性 {/*#reliability*/}

- **シーケンス番号:** すべてのペイロードバイトはストリーム内での位置を持ち、これにより並べ替えと重複検出が可能になる。
- **確認応答:** 受信側は次に期待するバイトを通知し、それによってこれまでに受信したすべてを累積的に確認する。
- **再送タイムアウト:** タイムアウト内に確認応答されなかったセグメントは再送される。タイムアウトは測定されたラウンドトリップ時間から導出される。
- **高速再送:** 同じバイトに対する複数の重複した確認応答は、単一のセグメントの損失を示し、タイムアウトの満了前に再送を引き起こす。
- **チェックサム:** 破損したセグメントは破棄されるため、確認応答されない。確認応答の欠如が再送を引き起こす。
- **選択的確認応答(SACK):** 受信側がどのバイト範囲が到着したかを正確に報告できるようにするオプションであり、欠落した範囲のみが再送される。

## フロー制御 {/*#flow-control*/}

フロー制御は、*受信側*が過負荷になることを防ぐ。すべてのセグメントは、そのウィンドウフィールドで、送信側が現在バッファできるバイト数を通知する。もう一方の側は、このウィンドウが許容する量を超える未確認データを送信中の状態にしてはならない。

バッファが満杯の受信側は、ウィンドウ0を通知する。送信側は、後続のセグメントがより大きなウィンドウを通知するまで一時停止する。

## 輻輳制御 {/*#congestion-control*/}

輻輳制御は、*ネットワーク*が過負荷になることを防ぎ、受信ウィンドウとは独立して機能する。実効的な送信上限は、受信ウィンドウと輻輳ウィンドウのうち小さい方である。

| フェーズ             | 動作                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| スロースタート       | 輻輳ウィンドウは小さく始まり、指数的に増加する                            |
| 輻輳回避             | しきい値を超えると、ウィンドウは線形にのみ増加する                        |
| 損失検出             | パケット損失は輻輳を示すため、ウィンドウが縮小される                      |
| 高速リカバリ         | 高速再送の後、縮小されたウィンドウで転送が継続される                      |

## 典型的な用途 {/*#typical-use-cases*/}

### TCPとUDPの比較 {/*#tcp-vs-udp*/}

|          | TCP                                                                           | [UDP](./udp.md)                                                                 |
| -------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 基準     | 遅延よりも完全性が重要                                                        | 遅れて届いたパケットは無価値、またはコネクションのオーバーヘッドがペイロードを上回る |
| 例       | ファイル転送、Webページ、電子メール、リモート管理、データベース接続           | ライブ音声・映像、オンラインゲーム、単純な問い合わせ/応答プロトコル             |

| ポート  | サービス                                                      |
| ------- | ------------------------------------------------------------- |

| 25      | SMTP                                                          |
| 53      | DNSゾーン転送、およびUDPのサイズ上限を超える応答              |
| 80      | HTTP                                                          |
| 110/995 | POP3 / POP3S                                                  |
| 143/993 | IMAP / IMAPS                                                  |
| 443     | HTTPS                                                         |
| 3306    | MySQL / MariaDB                                               |
