# 暗号化とデジタル署名

## 概要 {/*#overview*/}

暗号化は、データを読み取れない形式に変換することで、不正なアクセスからデータを保護する。デジタル署名は、データの真正性と完全性を検証し、通信中に改ざんされていないことを保証する。

## 共通鍵暗号 {/*#symmetric-encryption*/}

送信者と受信者は、データの暗号化と復号に**同じ鍵**を使用する。

- 大量のデータの暗号化に**高速**で効率的
- **鍵の配送**が課題となる。鍵を事前に安全に共有する必要があるため
- **主なアルゴリズム:** AES (Advanced Encryption Standard)、DES (Data Encryption Standard)、3DES (Triple Data Encryption Standard)
- **典型的な用途:** 大量データの暗号化

```text
Plaintext => [Encrypt with Key] => Ciphertext => [Decrypt with Key] => Plaintext
```

### AES {/*#aes*/}

AES (Advanced Encryption Standard) は、DESの後継として2001年に標準化され、現在使用されている共通鍵アルゴリズムである。

- **ブロック暗号:** 128ビットのブロックを暗号化し、それより長いデータはブロックに分割されてパディングされる
- **鍵長:** 128、192、256ビット。これがラウンド数(10、12、14)を決定する
- **性能:** 現行のCPUではハードウェア(AES-NI)で実装されており、ディスク全体の暗号化に十分な速度が得られる
- **安全とみなされている:** すべての鍵を試す以上に優れた実用的な攻撃は存在しない

ブロック暗号は各ブロックを個別に暗号化するため、**動作モード**がブロック同士の連結方法を決定する。

| モード                        | 特性                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| ECB (Electronic Codebook)   | 各ブロックが独立して暗号化され、同一の平文ブロックは同一の暗号文ブロックになるため不適切 |
| CBC (Cipher Block Chaining) | 各ブロックが直前の暗号文ブロックと結合される。初期化ベクトルが必要で、完全性の保護はない    |
| CTR (Counter Mode)          | ブロック暗号を並列化可能なストリーム暗号に変える                                                               |
| GCM (Galois/Counter Mode)   | 現在の標準的な選択: CTRに、改ざんも検出する認証タグを加えたもの                                    |

典型的な用途: ファイルおよびディスクの暗号化(LUKS、BitLocker、VeraCrypt)、[TLS](#hybrid-encryption)でのペイロードの暗号化、暗号化アーカイブやデータベースの列。

### DESと3DES {/*#des-and-3des*/}

DESはAESの前身で、鍵長は56ビットであり、今日では数時間で総当たり攻撃が可能なため、すでに破られている。3DESはDESを3回適用して実効112ビットに達するが、低速であり、レガシーシステムにしか見られない。どちらも新規開発には使用されない。

## 公開鍵暗号 {/*#asymmetric-encryption*/}

**鍵ペア**を使用する。公開鍵(公開して共有)と秘密鍵(秘密に保持)である。

- 公開鍵で暗号化されたデータは、対応する秘密鍵でのみ復号できる
- 数学的な複雑さのため、共通鍵暗号より**低速**
- **主なアルゴリズム:** RSA (Rivest-Shamir-Adleman)、ECC (Elliptic Curve Cryptography)
- **典型的な用途:** 鍵交換(ハイブリッド暗号)、デジタル署名

```text
Plaintext => [Encrypt with Public Key of Receiver] => Ciphertext => [Decrypt with Private Key of Receiver] => Plaintext
```

### RSA {/*#rsa*/}

RSAは最もよく知られた公開鍵アルゴリズムである。名称は、考案者のRivest、Shamir、Adlemanに由来する。

- **安全性の根拠:** 2つの大きな素数の乗算は容易だが、その積を再び素因数分解することは容易ではない
- **鍵長:** 最小で2048ビット、長期的な保護には3072または4096ビット。共通鍵の鍵長とは比較できない
- **機能:** 同じ鍵ペアで暗号化とデジタル署名が可能
- **制限:** ペイロードは鍵より短くなければならないため、RSAはデータそのものではなく共通鍵を暗号化する

ECC (Elliptic Curve Cryptography) は、はるかに短い鍵で同等の安全性を実現する。256ビットのECC鍵は、おおよそ3072ビットのRSA鍵に相当する。このため、ECCは[TLS](#hybrid-encryption)(ECDHE)における鍵交換の標準となり、証明書署名(ECDSA)にも使われることが増えている。

### Diffie-Hellman {/*#diffie-hellman*/}

Diffie-Hellmanは暗号化アルゴリズムではなく、**鍵合意**の手順である。双方は、公開値と自身の秘密値から共有秘密を導出し、その秘密が送信されることはない。

```text
Alice                                  Bob
secret a                               secret b
       ── public value A ────────────►
       ◄──────────── public value B ──
shared key from (B, a)  ==  shared key from (A, b)
```

- 盗聴者は両方の公開値を見ることができるが、それらから共有鍵を導出することはできない
- **一時的**な方式(DHE、ECDHE)はセッションごとに新しい鍵ペアを生成するため、長期鍵が後に侵害されても、記録された通信は復号されない(前方秘匿性)
- Diffie-Hellman単体では、誰の認証も行わない。証明書がなければ、中間者攻撃者が双方とそれぞれ1つずつ鍵を合意し、通信を中継できる

## ハイブリッド暗号 {/*#hybrid-encryption*/}

実際には、どちらの方式も単独では使われない。公開鍵暗号が鍵の配送を解決し、共通鍵暗号が実際の処理を担う。TLSはまさにこのように両者を組み合わせている。

1. サーバーは、公開鍵を含む**証明書**で自身の身元を証明する。
2. 双方は**ECDHE**でセッション鍵を合意し、そのやり取りを証明書で認証する。
3. ペイロードは、そのセッション鍵で**共通鍵方式**により、通常はAES-GCMで暗号化される。
4. セッション鍵は、接続の終了時に破棄される。

## ハッシュ関数 {/*#hash-functions*/}

ハッシュ関数は、任意のサイズのデータを固定サイズの出力(ハッシュ/ダイジェスト)に写像する。

- **一方向:** ハッシュから元のデータを導出できない
- **決定的:** 同じ入力は常に同じハッシュを生成する
- **衝突耐性:** 異なる入力が同じハッシュを生成してはならない
- **雪崩効果:** 入力の1ビットを変更すると、ハッシュのおよそ半分のビットが変化する

典型的な用途: ダウンロードの完全性チェック、重複検出、署名、および以下の手順と組み合わせたパスワードの保存。

| アルゴリズム | ダイジェスト長 | 評価                                                                                                   |
| --------- | ------------- | ------------------------------------------------------------------------------------------------------------ |
| MD5       | 128ビット       | 破られている。衝突は数秒で生成可能。伝送エラーに対するチェックサムとしてのみ許容される |
| SHA-1     | 160ビット       | 破られている。実用的な衝突攻撃が存在し、署名にはもう使われない                                     |
| SHA-256   | 256ビット       | 現在の標準。SHA-2ファミリーの一部                                                                   |
| SHA-512   | 512ビット       | SHA-256と同様でダイジェストが長い。64ビットシステムではSHA-256より高速                                     |
| SHA-3     | 可変      | SHA-2とは異なる内部構造。SHA-2が弱体化した場合の予備として想定されている                                   |

## パスワードのハッシュ化 {/*#hashing-passwords*/}

パスワードは、平文で保存されることも、暗号化されることもない。それを復号できる鍵がどこかに存在しなければならなくなるためである。パスワードはハッシュ化され、データベースが盗まれてもパスワード自体が明らかにならないようにする。

単純な `SHA-256` では、次の2つの理由から不十分である。

- **同一のパスワードは同一のハッシュを生成する**ため、ハッシュからどのアカウントがパスワードを共有しているかが分かり、事前計算された表(レインボーテーブル)で一般的なパスワードがただちに解読される
- **ハッシュ関数は設計上高速**であり、現行のハードウェアは毎秒数十億のSHA-256ハッシュを計算できるため、短いパスワードの総当たり攻撃が現実的になる

### ソルト {/*#salt*/}

ソルトは、パスワードごとに生成され、パスワードとともにハッシュ化されるランダムな値である。ソルトは秘密ではなく、ハッシュの隣に保存される。

```text
hash = H(salt + password)
```

- ソルトが異なるため、同一のパスワードでも異なるハッシュになる
- 攻撃者はソルトごとに1つの表が必要になるため、レインボーテーブルは無価値になる
- すべてを一度に攻撃するのではなく、各パスワードを個別に攻撃しなければならない

**ペッパー**は、すべてのパスワードに共通する追加の秘密の値で、データベースの外部、たとえばアプリケーションの設定に保存される。データベースが漏えいしても設定が漏えいしない場合にのみ有効である。

### ワークファクター {/*#work-factor*/}

2つ目の対策は、ハッシュ化を意図的に低速にすることである。パスワード用に設計された手順は、内部の演算を何度も繰り返す。繰り返しの回数は**コストファクター**として設定可能で、ハードウェアが高速化するのに合わせて引き上げられる。ログインごとに約100 msの遅延は、ユーザーには知覚できず、数十億の候補を試すことを非現実的にする。

### bcrypt {/*#bcrypt*/}

bcryptはこの種の手順で最も広く使われており、Blowfish暗号に基づいている。

- ソルトは**ハッシュ内部**で生成および保存されるため、別の列は不要
- コストファクターがハッシュの一部であるため、引き上げた後でも古いハッシュを検証できる
- 意図的に低速でメモリ依存であり、SHAベースの手順よりGPUで高速化しにくい
- 制限: 入力の最初の72バイトのみが使用される

```text
$2b$12$eImiTXuWVxfM37uY4JANjQ.../hJ6CtPTuOrAXTlHGDLcJU3wG6Hpu
 │   │  └── salt (22 characters) ──┘└── hash ────────────────┘
 │   └───── cost factor 12, meaning 2^12 rounds
 └───────── algorithm identifier
```

同じ目的を持つ代替手段:

| 手順 | 備考                                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------------------------- |
| Argon2id  | Password Hashing Competitionの優勝アルゴリズム。時間、メモリ、並列度を調整可能で、新規システムに対する現在の推奨 |
| scrypt    | メモリハードであるため、専用ハードウェアでの並列化にコストがかかる                                                     |
| PBKDF2    | 広く利用可能で標準化されているが、計算量のみに依存するため、これらの選択肢の中で最も弱い                  |
| bcrypt    | 実績があり、よく理解されており、あらゆる言語で利用可能                                                                   |

パスワードの保存先に決して置いてはならないもの: 平文、可逆な暗号化、ソルトなしのハッシュ、そしてMD5、SHA-1、SHA-256のような単一の高速なハッシュ関数。

## デジタル署名 {/*#digital-signatures*/}

デジタル署名は、データが特定の当事者から送信され、改変されていないことを検証する。

**署名(送信者):**

1. メッセージの[ハッシュ](#hash-functions)を作成する
2. ハッシュを送信者自身の**秘密鍵**で暗号化する => これが署名である
3. メッセージを署名とともに送信する

**検証(受信者):**

1. 署名を送信者の**公開鍵**で復号する => 元のハッシュが明らかになる
2. 受信したメッセージを独自にハッシュ化する
3. 両方のハッシュを比較する。一致すれば、署名は有効でありメッセージは真正である

この手順はRSA署名を説明したものである。[ECDSA](#rsa)はハッシュを暗号化せず、ハッシュと秘密鍵から署名を計算する。受信者は公開鍵でそれを検証する。
