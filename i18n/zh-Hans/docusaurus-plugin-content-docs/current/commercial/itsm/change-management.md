# 变更管理

## 概览 {/*#overview*/}

**变更管理**是 ITSM 的第三层级，负责对 IT 系统变更的审批和规划。

**目标：** 确保变更不会在仓促且缺乏全面了解的情况下进行。来自不同领域的专家评估风险，以避免后续错误。只有紧急变更可以绕过该流程，因为其最高优先级是尽快恢复系统。

## 变更请求（RFC） {/*#request-for-change-rfc*/}

在执行变更之前，通常由[问题管理](./problem-management.md)创建**变更请求（RFC）**。RFC 是执行变更的正式请求，包含：

- 变更描述
- 变更原因
- 时间表
- 优先级
- 预期的副作用
- 预估成本

RFC 描述**做什么**，而不描述**怎么做**，因为"怎么做"是在变更管理流程中确定的。

## RFC 优先级划分 {/*#rfc-prioritisation*/}

收到的 RFC 按**紧迫性**和**影响**划分优先级：

### 紧迫性级别 {/*#urgency-levels*/}

| 级别                  | 描述               |
| --------------------- | ------------------ |
| **优先级低**          | 期望但不紧急       |
| **优先级中**          | 必要但不紧急       |
| **优先级高**          | 需要立即采取行动   |
| **优先级立即**        | 需要立即采取行动   |

### 影响级别 {/*#impact-levels*/}

| 级别         | 描述                               | 示例               |
| ------------ | ---------------------------------- | ------------------ |
| **影响低**   | 对 IT 服务的影响极小，工作量小     | 更换一台 PC        |
| **影响中**   | 影响适中，工作量增加               | 升级所有 PC 的操作系统 |
| **影响高**   | 对 IT 服务影响大，工作量非常大     | 服务器完全宕机     |

## 变更类型 {/*#change-types*/}

| 类型                                 | 特征                                                       | 审批                 |
| ------------------------------------ | ---------------------------------------------------------- | -------------------- |
| **标准变更**                         | 来自目录的预先批准的例行变更；风险低；自动授权             | 仅变更经理           |
| **常规变更**                         | 中等风险、中等复杂度、紧迫性适中；需要专家评估             | CAB + CIO            |
| **紧急变更（Notfall Change）**       | 紧迫性高，需要短期解决方案；为求速度绕过结构化审批流程     | EC / ECAB            |

## 审批机构 {/*#approval-bodies*/}

| 机构                                 | 描述                                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------------------------- |
| **变更经理（CM）**                   | 单独决定影响范围小的变更（标准变更）；负责时间管理和监控                                     |
| **变更咨询委员会（CAB）**            | 由来自各业务领域的专家组成的委员会；决定影响范围中等的变更（常规变更）                       |
| **首席信息官（CIO）**                | 代表 IT 利益的董事会/管理层人员；参与具有较大业务范围的决策（例如员工培训）                  |
| **紧急委员会（EC / ECAB）**          | 由被高度授权的专家组成的小型团队，负责紧急决策；处理紧急变更                                 |

## 变更规划 {/*#change-planning*/}

### 变更前瞻计划（FSC，Forward Schedule of Change） {/*#forward-schedule-of-change-fsc*/}

记录所有已规划的长期变更的日历。规划时应始终以最小化停机时间为目标。

### 配置管理数据库（CMDB） {/*#configuration-management-database-cmdb*/}

集中存放所有 CI 及其规格和许可证编号的中央数据库。对 CI 的所有变更都在此集中记录。

变更经理（CM）负责按时间控制变更的实施和监控。

## 变更的批准与执行 {/*#approving-and-executing-changes*/}

在 ITSM 中，对变更的批准/授权与规划/执行是有意分开的。这样可以确保：

- 由考虑整个系统的专家作出可持续的决策
- 避免在不考虑更大背景的情况下被动地修复错误
- 有文档记录的问责

## 变更的关闭（PIR） {/*#closing-a-change-pir*/}

变更实施后，变更管理会将所有措施以及失败的根本原因记录在 CMDB 和 KEDB 中，以备日后参考。

**实施后评审（PIR，Post Implementation Review）**记录变更的所有关键点：

- 测试结果
- 实施细节
- 与先前系统状态相比的变化
- 成本和工作量
- 时间戳

**PIR 的目标：** 通过评审和评估已完成的变更来推动持续改进。

## 变更类型与审批汇总 {/*#change-types-and-approval-summary*/}

| 变更类型 | 审批机构 | 关键特征                       |
| -------- | -------- | ------------------------------ |
| 标准变更 | 变更经理 | 基于目录、预先批准、风险低     |
| 常规变更 | CAB + CIO | 中等风险，CAB 参与            |
| 紧急变更 | EC / ECAB | 速度最快，绕过结构化流程      |
