# 其他 UML 图

## 概述 {/*#overview*/}

UML 2.5 定义了十四种图类型。此处列出其中没有独立条目的七种。

| 图 | 类别 | 核心问题 |
| ---------------------------- | --------- | -------------------------------------------------------------------------- |
| 对象图 | 结构 | 在某一时刻存在哪些具体实例，它们如何相连？ |
| 包图 | 结构 | 模型如何划分为若干单元，哪个单元依赖哪个单元？ |
| 通信图 | 行为 | 哪些对象交换消息，沿着哪些链接交换？ |
| 时序图 | 行为 | 某个元素在时间轴上的哪个时间点处于哪种状态？ |
| 交互概览图 | 行为 | 整个交互按什么顺序执行？ |
| 组合结构图 | 结构 | 分类器的内部是如何构成的，通过哪些端口与外界通信？ |
| 配置文件图 | 结构 | 如何针对某个领域或平台扩展 UML 本身？ |

---

## 对象图 {/*#object-diagram*/}

系统在某一特定时刻的快照：存在的实例以及它们之间的链接。其表示法与[类图](./class-diagram.md)相同，但处于实例层面。

核心表示法元素：

- **实例规约：** 带下划线名称的矩形，格式为 `name : Class`；名称或类可以省略（`o7 : Order`、`: Order`、`o7`）
- **属性值：** 在下部分栏中，以 `attribute = value` 的形式给出
- **链接：** 两个实例之间的普通实线，是关联在实例层面的对应物；没有多重性，因为链接始终恰好连接两个实例

纯文本无法显示下划线，在真实的表示法中，名称 `m1 : Customer` 和 `o7 : Order` 带有下划线：

```text
 ┌────────────────────┐              ┌────────────────────┐
 │ m1 : Customer      │   places     │ o7 : Order         │
 ├────────────────────┤──────────────├────────────────────┤
 │ name = "Meier"     │              │ total = 249.90     │
 │ city = "Kiel"      │              │ status = "paid"    │
 └────────────────────┘              └────────────────────┘
```

典型用法：用一个具体示例解释复杂的类图，讨论某个具体的数据组合，记录测试数据或缺陷出现时的状态。

## 包图 {/*#package-diagram*/}

包图展示模型如何被切分为若干单元，以及哪个单元依赖哪个单元。包本身不带有任何行为。

核心表示法元素：

- **包：** 带标签页的矩形；嵌套以图形方式绘制，或写作 `shop::service`
- **依赖：** 虚线箭头，从使用方指向被使用的包
- **`«import»`：** 使目标包的公共元素无需限定即可使用
- **`«access»`：** 相同的关系，但不再向外传递被导入的名称
- **`«merge»`：** 在概念上将目标包的内容复制到源包中，并与其合并
- **分层：** 包上下排列，所有依赖都指向同一方向

```text
┌──────┐
│ shop │
├──────┴──────────────────┐
│                         │
│   ┌─────────┐           │
│   │ ui      │           │
│   ├─────────┴───────┐   │
│   │                 │   │
│   └────────┬────────┘   │
│            ┆ «import»   │
│            ▼            │
│   ┌─────────┐           │
│   │ service │           │
│   ├─────────┴───────┐   │
│   │                 │   │
│   └────────┬────────┘   │
│            ┆ «import»   │
│            ▼            │
│   ┌─────────────┐       │
│   │ persistence │       │
│   ├─────────────┴───┐   │
│   │                 │   │
│   └─────────────────┘   │
│                         │
└─────────────────────────┘
```

典型用法：分层架构、将系统切分为模块、在循环依赖进入代码之前使其可见。

界限：[组件图](./component-diagram.md)描述在运行时提供和需要接口的可替换构建块，而包图只在设计时组织模型元素和源码元素。

## 通信图 {/*#communication-diagram*/}

通信图展示哪些对象交换消息，以及它们沿着哪些链接交换。对象可以自由摆放，消息的顺序由其编号决定。

核心表示法元素：

- **对象：** 带下划线 `name : Class` 的矩形，与对象图中相同
- **链接：** 两个对象之间的实线
- **消息：** 绘制在链接旁的小箭头，标注为 `1: placeOrder()`
- **分层顺序编号：** `1`、`1.1`、`1.2`，其中 `1.1` 和 `1.2` 作为处理消息 `1` 的一部分依次发送
- **迭代标记与守卫条件：** `*` 和 `[condition]`，作为消息标签的一部分

```text
  ┌──────────┐   1: placeOrder() ►  ┌─────────────┐
  │ : Client │──────────────────────│ : OrderCtrl │
  └──────────┘   ◄ 1.3: confirm()   └─────────────┘
                                           │
                                           │ ▼ 1.1: checkStock()
                                           │ ▼ 1.2: reserve()
                                           │
                                    ┌─────────────┐
                                    │ : Warehouse │
                                    └─────────────┘
```

典型用法：使哪些对象相互通信变得可见，评判设计的耦合程度，以及结构比确切顺序更重要的小型交互。

界限：[序列图](./sequence-diagram.md)沿着从上到下的明确时间轴展示同一交互，并提供诸如 `alt`、`opt` 和 `loop` 的组合片段。对象、消息及其顺序可以从一种图转换到另一种图，但组合片段在通信图中没有对应物。备选和循环在序列图中更易阅读，链接网络则在通信图中更易看清。

## 时序图 {/*#timing-diagram*/}

时序图展示一个或多个元素的状态或值如何沿着明确的时间轴变化。

核心表示法元素：

- **时间轴：** 水平方向，带刻度，每条生命线一个泳道
- **状态生命线：** 在纵轴所列状态之间的阶梯线
- **值生命线：** 紧凑的带状形式，其中的交叉标记值的变化
- **持续时间与时间约束：** `{d..3*d}` 和 `{t = 0}`
- **事件与消息：** 泳道之间的箭头
- **刻度标记：** 时间刻度的单位

```text
 : Motor
           │
   active  │         ┌──────────────┐
           │         │              │
   idle    ├─────────┘              └──────────
           │         ├── {20..40} ──┤
           └────┬────┬────┬────┬────┬────┬────┬───► t
           0    10   20   30   40   50   60   70  ms
```

典型用法：实时系统和嵌入式系统、总线和网络协议、与硬件相关的控制，以及对延迟、超时和最短保持时间的要求。

界限：[状态机图](./state-machine-diagram.md)定义可能存在哪些状态和转换，不带时间轴。时序图展示元素在何时处于这些状态中的哪一个。

## 交互概览图 {/*#interaction-overview-diagram*/}

交互概览图将多个序列图、通信图或时序图编排为一个控制流，每个节点都是一个完整的交互。

核心表示法元素：

- **框架：** 带有标题 `sd <name>`
- **交互使用：** 带有关键字 `ref` 和现有交互图名称的矩形
- **内联交互：** 直接嵌入为节点的小型序列图
- **控制元素：** 活动图中的全部控制元素，即初始节点、判定、合并、分叉、汇合、终止节点

```text
 ┌ sd Checkout ─────────────────────────────┐
 │                  ●                       │
 │                  │                       │
 │                  ▼                       │
 │          ┌───────────────┐               │
 │          │ ref  Login    │               │
 │          └───────────────┘               │
 │                  │                       │
 │             ╱─────────╲                  │
 │            ╱  paid ?   ╲                 │
 │            ╲           ╱                 │
 │             ╲─────────╱                  │
 │       [yes]  │       │  [no]             │
 │     ┌────────┘       └────────┐          │
 │     ▼                         ▼          │
 │ ┌───────────────┐   ┌───────────────┐    │
 │ │ ref  Ship     │   │ ref  Cancel   │    │
 │ └───────────────┘   └───────────────┘    │
 │     │                         │          │
 │     └────────┐       ┌────────┘          │
 │              ▼       ▼                   │
 │                  ◉                       │
 └──────────────────────────────────────────┘
```

典型用法：由许多单独交互组成的协议或长时间运行的业务事务的整体视图。

界限：[活动图](./activity-diagram.md)使用相同的控制元素，但其节点是单个动作。交互概览图也可以替代一张塞满嵌套 `alt` 和 `loop` 片段的庞大序列图。

## 组合结构图 {/*#composite-structure-diagram*/}

组合结构图审视单个分类器的内部：它由哪些部件构成，这些部件如何连接，以及它通过哪些交互点与其环境相连。

核心表示法元素：

- **部件：** 分类器框架内部的矩形，写作 `role : Type`，可带可选的多重性，例如 `wheels : Wheel [4]`
- **端口：** 分类器边界上的小方块，是具名且有类型的交互点
- **接口：** 提供接口为棒棒糖 `─○`，需求接口为插座 `─(`
- **连接件：** 两个部件之间的装配连接件，部件与端口之间的委托连接件
- **协作：** 带具名角色的虚线椭圆，独立于具体的类描述协作模式

```text
 ┌ Car ──────────────────────────────────────┐
 │                                           │
 │ ┌────────────┐        ┌──────────────┐    │
 │ │ e : Engine │────────│ g : Gearbox  │────┼──□───○ Drive
 │ └────────────┘        └──────────────┘    │
 │                                           │
 └───────────────────────────────────────────┘
```

典型用法：组件的内部架构、系统设计和嵌入式设计中部件的连接，以及将设计模式描述为角色之间的协作。

界限：[类图](./class-diagram.md)说明哪些类之间存在一般性的关系，组合结构图则说明某个整体内部的实例如何以特定角色相互连接。[组件图](./component-diagram.md)使用相同的棒棒糖与插座表示法，但处于整个系统可部署构建块的层面，而不是某个分类器的内部。

## 配置文件图 {/*#profile-diagram*/}

配置文件图针对某个领域或目标平台扩展 UML 本身。

核心表示法元素：

- **配置文件：** 带有关键字 `«profile»` 的包
- **构造型：** 带有关键字 `«stereotype»` 的矩形，扩展现有的元类；任何不是预定义 UML 关键字的尖括号引号内名称，都是在某个配置文件中定义的构造型
- **扩展：** 从构造型指向元类、带实心箭头的实线，例如 `«metaclass» Class`
- **标记值：** 构造型的属性，例如 `table : String`，在带有该构造型的元素处填写
- **约束：** 花括号中的规则，以 OCL 或自由文本书写
- **应用：** 从包指向配置文件的 `«apply»` 依赖；其元素随后可以带有 `«entity»`、`«controller»` 等

```text
 ┌ «profile» Persistence ─────────────────────┐
 │                                            │
 │  ┌─────────────────┐     ┌───────────────┐ │
 │  │ «stereotype»    │────►│ «metaclass»   │ │
 │  │ Entity          │     │ Class         │ │
 │  ├─────────────────┤     └───────────────┘ │
 │  │ table : String  │                       │
 │  └─────────────────┘                       │
 └────────────────────────────────────────────┘
```

与元模型的关系：UML 由四层架构描述。`M0` 存放真实对象，`M1` 存放模型，`M2` 存放定义类或关联是什么的 UML 元模型，`M3` 存放 MOF（Meta Object Facility，元对象设施），即书写元模型本身所用的语言。配置文件是 UML 的轻量级扩展机制：它扩展 `M2` 层而不修改它，因此带配置文件的模型仍可在工具之间交换。重量级扩展则会直接改变元模型，从而创建一种新语言。

典型用法：诸如 SysML 或 MARTE 的领域特定建模语言、将模型映射到 JPA 或 EJB 等平台，以及公司范围的建模约定。
