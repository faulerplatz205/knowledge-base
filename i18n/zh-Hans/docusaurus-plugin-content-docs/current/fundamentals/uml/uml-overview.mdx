# UML 概览

## 概述 {/* #overview */}

**统一建模语言（Unified Modeling Language，UML）**是用于软件系统建模的标准化图形符号，由 **对象管理组织（Object Management Group，OMG）**维护。当前版本为 **UML 2.5**（自 2017 年起为 2.5.1），定义了 **14 种图类型**。

UML 解决一个实际问题：文字含糊不清，而源代码又过于细致，难以用于讨论。图介于两者之间。它展示系统中当前正在讨论的部分，并有意略去其余一切。

典型应用：

- 在实现任何内容之前与客户共同记录需求
- 设计面向对象系统的静态结构
- 跨越团队和部门边界澄清流程或算法
- 为现有系统编写文档，以便交接或扩展
- 无需阅读代码即可讨论架构决策

---

## UML 是什么与不是什么 {/* #what-uml-is-and-what-it-is-not */}

UML **是**：

- **一种符号体系：** 一套含义明确的固定符号词汇
- **一种标准：** 同一个符号在每家公司、每种工具中含义相同
- **与语言无关：** 类图对 Java、C# 或 TypeScript 只字未提
- **有选择性的：** 每张图只为一个方面建模，绝不涵盖整个系统

UML **不是**：

- **方法或过程模型：** UML 没有规定*何时*由谁制作哪种图。这由过程模型决定（[Scrum](../../projectmanagement/scrum.md)、V 模型、统一过程）。UML 是符号，过程模型才是方法。
- **编程语言：** 模型可以转换为代码骨架，但图是不可执行的，也不能取代实现。
- **完整描述：** 模型始终是一种简化。包含代码所含一切内容的图相对于代码没有任何优势。
- **数据建模标准：** [ER 模型](../databases/er-model.md)是用于数据库设计的独立符号体系，不属于 UML，尽管类图可以表达类似的事实。
- **质量保证：** 划分不当的系统，无论画得多么整齐，依然划分不当。

这一领域最常见的误解是将 UML 当作方法论。会画用例图并不能说明需求*何时*收集、*由谁*批准，以及*如何*纳入项目计划。

## 14 种图类型 {/* #the-14-diagram-types */}

UML 2.5 将其图分为两个顶层组。**结构图**描述系统由什么构成，**行为图**描述系统做什么。**交互图**是行为图的一个子组：它们通过参与者之间的消息交换来描述行为。

| #   | 图                                                        | 组别                    | 回答的问题                                                                            |
| --- | --------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------- |
| 1   | [类图](./class-diagram.md)                                | 结构                    | 存在哪些类，它们包含什么，彼此如何关联？                                              |
| 2   | [对象图](./further-uml-diagrams.md)                       | 结构                    | 在某一时间点存在哪些具体的对象和值？                                                  |
| 3   | [包图](./further-uml-diagrams.md)                         | 结构                    | 大型模型如何划分为若干组，哪些部分依赖哪些部分？                                      |
| 4   | [组件图](./component-diagram.md)                          | 结构                    | 软件由哪些可替换的部分构成，它们具有哪些接口？                                        |
| 5   | [组合结构图](./further-uml-diagrams.md)                   | 结构                    | 单个元素如何由相互协作的部分在内部构建？                                              |
| 6   | [部署图](./deployment-diagram.md)                         | 结构                    | 哪些工件运行在哪些节点上，这些节点如何连接？                                          |
| 7   | [配置文件图](./further-uml-diagrams.md)                   | 结构                    | UML 自身如何为某个领域扩展（构造型、标记值）？                                        |
| 8   | [用例图](./use-case-diagram.md)                           | 行为                    | 系统做什么，面向哪些参与者？                                                          |
| 9   | [活动图](./activity-diagram.md)                           | 行为                    | 各步骤按什么顺序运行，包括分支、循环和并行工作？                                      |
| 10  | [状态机图](./state-machine-diagram.md)                    | 行为                    | 对象可以处于哪些状态，哪些事件引起迁移？                                              |
| 11  | [序列图](./sequence-diagram.md)                           | 行为 / 交互             | 对象之间交换哪些消息，按什么时间顺序？                                                |
| 12  | [通信图](./further-uml-diagrams.md)                       | 行为 / 交互             | 谁与谁交谈，参与者之间如何连接？                                                      |
| 13  | [时序图](./further-uml-diagrams.md)                       | 行为 / 交互             | 状态如何沿时间轴变化，适用哪些时间约束？                                              |
| 14  | [交互概览图](./further-uml-diagrams.md)                   | 行为 / 交互             | 多个交互如何组合为一个整体流程？                                                      |

所有图共有的符号集在[符号基础](./uml-notation-basics.md)中说明。

## 结构图 {/* #structure-diagrams */}

结构图展示处于静止状态的系统。其中时间不起作用，也不包含执行顺序。

- **类图：** 面向对象设计的核心图。带有属性和操作的类，通过关联、聚合、组合、泛化和依赖相连，并标注可见性和多重性。
- **对象图：** 类图的快照。它展示的不是类 `Order`，而是带有实际属性值的对象 `order42`。适用于用示例使一组复杂的关系具体化。
- **包图：** 将模型元素分组为包，并展示包之间的依赖。使架构预期的分层可见，并揭示循环依赖。
- **组件图：** 带有提供接口和需求接口的组件（球窝符号）。描述软件如何被划分为可替换的单元。
- **组合结构图：** 深入单个分类器内部，展示其部件、端口和连接器。在嵌入式和系统工程之外很少使用。
- **部署图：** 节点（硬件或执行环境）、部署在其上的工件以及它们之间的通信路径。从软件设计到运维的桥梁。
- **配置文件图：** UML 自身的扩展机制。构造型、标记值和约束使该语言适应某个领域，例如 `«entity»` 或 `«controller»`。

## 行为图 {/* #behavioural-diagrams */}

行为图展示随时间发生的事情：以什么顺序、由什么触发、产生什么结果。

- **用例图：** 参与者、用例和系统边界。它有意保持粗粒度，充当需求的目录，而不是流程的描述。
- **活动图：** 经由动作的控制流，带有判定、合并、分叉和汇合，可选择性地按泳道分组。最接近经典流程图的 UML 图，既适用于业务流程，也适用于算法。
- **状态机图：** 单个对象的生命周期。状态、由事件触发的迁移、守卫、入口和出口动作。当对象根据其历史对相同输入作出不同反应时，这是首选的图。

### 交互图 {/* #interaction-diagrams */}

四种交互图从不同角度描述同一主题：参与者交换消息。

- **序列图：** 生命线水平排列，时间向下流动，消息为生命线之间的箭头。最强调时间顺序，因此是四者中使用最广泛的。
- **通信图：** 同样的信息排列为由链接的参与者构成的网络，消息以编号而不是位置来排序。最强调*谁与谁相连*。
- **时序图：** 参与者的状态变化绘制在显式的时间轴上。用于持续时间和时间约束重要的场合，例如实时系统和嵌入式系统。
- **交互概览图：** 节点为完整交互而非单个动作的活动图。用于将多个序列图编排为一个整体流程。

序列图和通信图在语义上大体等价，许多工具可将其中一种自动转换为另一种。

## 选择合适的图 {/* #choosing-the-right-diagram */}

| 需要回答的问题                                  | 合适的图      |
| ----------------------------------------------- | ------------- |
| 谁使用系统，用来做什么？                        | 用例图        |
| 流程的各步骤按什么顺序运行？                    | 活动图        |
| 编码开始之前算法如何构造？                      | 活动图        |
| 需要哪些类，它们如何关联？                      | 类图          |
| 具体情形下数据是什么样的？                      | 对象图        |
| 对象如何协作以实现一个用例？                    | 序列图        |
| 订单、工单或设备会经历哪些状态？                | 状态机图      |
| 系统如何被划分为可替换的模块？                  | 组件图        |
| 哪台服务器、哪个容器、哪个客户端？              | 部署图        |
| 如何使大型模型保持有序？                        | 包图          |
| 必须遵守哪些时间约束？                          | 时序图        |

选择的经验法则：

- **一个问题，一张图。** 同时回答三个问题的图通常哪一个都回答不清。
- **先结构还是先行为？** 需求从行为开始（用例、活动），实现从结构开始（类、组件）。
- **抽象层次保持不变。** 将业务术语与数据库列混在一起的图，对任何一类受众都难以使用。
- **无人阅读的图是浪费。** 受众决定细节程度：客户需要用例图和活动图，开发人员需要类图和序列图，运维需要部署图。
- **维护成本不可忽视。** 与代码脱节的图比没有图更糟，因为它们被人信任却是错误的。

实践中，少数几种图类型承担了几乎全部工作：类图、活动图、用例图、序列图和状态机图。其余类型较为专门，仅在出现其特定问题时才会用到。

## 软件设计过程中的 UML {/* #uml-in-the-software-design-process */}

UML 并不绑定于某一种过程模型，但其图自然地对应于开发的各个阶段。

| 阶段         | 问题                           | 典型的图                         |
| ------------ | ------------------------------ | -------------------------------- |
| 需求分析     | 系统应当做什么？               | 用例图、活动图                   |
| 领域建模     | 领域中存在哪些概念？           | 类图（作为领域模型）、对象图     |
| 设计         | 解决方案如何构建？             | 类图、序列图、状态机图           |
| 架构         | 系统如何划分和分布？           | 组件图、包图、部署图             |
| 实现         | 设计如何落地？                 | 作为代码骨架的类图               |
| 测试         | 必须覆盖哪些流程？             | 活动图、序列图、状态机图         |
| 文档         | 系统如何工作？                 | 以上所有，精简至要点             |

软件设计中的建模服务于三个目的：

- **沟通：** 为背景不同的人提供共同的图景
- **分析：** 矛盾和缺漏在实现之前就变得可见
- **文档：** 无需阅读全部源代码即可理解系统

## 常见错误 {/* #common-mistakes */}

1. **将 UML 当作方法：** UML 定义的是符号，而不是步骤。步骤来自过程模型。
2. **将交互图算作第三个主要组：** 它们是行为图的一个子组。
3. **混淆活动图与序列图：** 活动图展示动作之间的控制流，序列图展示对象之间的消息。
4. **混淆类图与对象图：** 类图展示类型，对象图展示带有具体值的实例。
5. **将用例图用作流程描述：** 它列出系统所提供的内容，用例内部的流程属于活动图。
6. **将 ER 模型算作 UML 图：** 它是用于数据建模的独立符号体系。
7. **一切皆建模：** 以全部细节覆盖整个系统的模型，成本高于收益，并且在第一次变更后就已过时。
8. **临时发明符号：** UML 的价值在于符号在各处含义相同，自创的箭头恰恰破坏这一点。
