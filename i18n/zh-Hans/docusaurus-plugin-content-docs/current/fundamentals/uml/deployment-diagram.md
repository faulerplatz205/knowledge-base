# 部署图

## 概述 {/*#overview*/}

部署图是一种**结构型** UML 图。它展示已完成的系统在物理上如何分布：存在哪些硬件和哪些运行时环境，其上安装了哪些文件，以及这些部分通过哪些通信路径交换数据。

典型应用：

- 为运维和交接记录应用程序的系统全景
- 展示客户端-服务器或三层架构及其网络边界
- 规划安装：哪个制品被复制到哪台机器上
- 描述容器或云部署及其协议和副本数量
- 为关于可用性、扩展和安全区域的讨论提供基础

---

## 表示法 {/*#notation*/}

| 元素 | 表示法 | 含义 |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 节点 | 长方体（三维盒子） | 运行或存储某些内容的执行资源 |
| 设备 | 带有关键字 `<<device>>` 的长方体 | 物理硬件：服务器、工作站、智能手机、路由器、打印机 |
| 执行环境 | 带有 `<<executionEnvironment>>` 的长方体，通常嵌套在设备内部 | 承载制品的软件：操作系统、JVM、应用服务器、容器运行时、DBMS |
| 制品 | 带有关键字 `<<artifact>>` 的矩形或文档图标 | 由开发过程产生的物理文件 |
| 部署 | 绘制在节点内部的制品，或虚线 `<<deploy>>` 箭头 | 制品安装在该节点上 |
| 具现 | 从制品指向组件或类的虚线 `<<manifest>>` 箭头 | 制品是某个逻辑元素的物理实现 |
| 通信路径 | 两个节点之间的实线 | 节点之间交换数据的连接，不带方向 |
| 协议 | 路径上的构造型，例如 `<<HTTPS>>`、`<<TCP/IP>>`、`<<JDBC>>` | 该连接上使用的协议 |
| 多重性 | 通信路径末端的数字，例如 `2` 或 `1..*` | 该端有多少个节点与另一端的一个节点相连 |
| 嵌套 | 绘制在节点内部的节点或制品 | 包含关系：硬件包含运行时，运行时包含文件 |
| 实例 | 带前导冒号并加下划线的名称，例如 `:AppServer` | 具体的实例，而不是类型 |
| 注释 | 通过虚线相连的折角矩形 | 无语义的说明 |

使图保持可读的命名规则：

- 节点按类型命名，`ApplicationServer`，或按具体机器命名，`appsrv01:ApplicationServer`。在绘图工具中，实例名带有下划线。
- 制品使用包含扩展名的真实文件名：`shop.war`，而不是 `Shop application`。
- 每条通信路径都带有协议构造型，未加标注的线只表示*以某种方式相连*。
- 关键字和构造型写在书名号（guillemets）中，`«device»`。写法 `<<device>>` 是基于文本的工具所使用的 ASCII 形式，下文即采用这种形式。

## 构成要素 {/*#building-blocks*/}

### 节点 {/*#node*/}

节点按关键字分为两类：

- **`<<device>>`：** 物理硬件，例如服务器、工作站、手机或嵌入式控制器
- **`<<executionEnvironment>>`：** 承载制品并为其提供内存管理、事务或请求分发等服务的软件环境

执行环境通常嵌套在设备内部。没有关键字的节点只是*某种*执行资源。

```text
        ┌────────────────────────────────────────┐
       ╱                                        ╱│
      ┌────────────────────────────────────────┐ │
      │  <<device>>                            │ │
      │  ApplicationServer                     │ │
      │                                        │ │
      │  ┌──────────────────────────────────┐  │ │
      │  │  <<executionEnvironment>>        │  │ │
      │  │  Tomcat 10                       │  │ │
      │  │                                  │  │ │
      │  │  ┌────────────────────────────┐  │  │ │
      │  │  │  <<artifact>>              │  │  │ │
      │  │  │  shop.war                  │  │  │ │
      │  │  └────────────────────────────┘  │  │ │
      │  └──────────────────────────────────┘  │ ╱
      └────────────────────────────────────────┘╱
```

在绘图工具中，每个节点都是长方体，包括嵌套的节点。此处的图将内部节点绘制为普通矩形，以便嵌套关系在纯文本中保持可读。

### 制品与部署 {/*#artifact-and-deployment*/}

在实践中，制品就是文件。典型例子有 `shop.war`、`payment-service.jar`、`setup.exe`、`schema.sql`、`nginx.conf` 以及诸如 `shop-app:2.4.0` 的容器镜像。

有两种表示法可以表明制品安装在某个节点上：

- **嵌套：** 将制品矩形绘制在节点内部。这种形式更紧凑，也是迄今为止更常见的一种。
- **依赖：** 带关键字 `<<deploy>>` 的虚线箭头从制品指向节点。当同一个制品部署到多个节点上时，这种形式很有用。

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈┈ <<deploy>> ┈┈┈┈┈┈▶ │  <<device>>            │
 │  shop.war              │                          │  ApplicationServer     │
 └────────────────────────┘                          └────────────────────────┘
```

具现是指向设计的对应关系。带关键字 `<<manifest>>` 的虚线箭头从制品指向其在物理上实现的组件或类，从而表明模型的哪一部分最终落入该文件中。

```text
 ┌────────────────────────┐                          ┌────────────────────────┐
 │  <<artifact>>          │ ┈┈┈┈ <<manifest>> ┈┈┈┈┈▶ │  <<component>>         │
 │  payment-service.jar   │                          │  PaymentService        │
 └────────────────────────┘                          └────────────────────────┘
```

### 通信路径 {/*#communication-path*/}

通信路径是不带箭头的实线，因为连接本身没有方向，并以构造型的形式标注协议。

```text
    ┌──────────────────────┐                  ┌──────────────────────┐
   ╱                      ╱│                 ╱                      ╱│
  ┌──────────────────────┐ │                ┌──────────────────────┐ │
  │  <<device>>          │ │ 2            1 │  <<device>>          │ │
  │  AppServer           │ ├──── <<JDBC>> ──┤  DatabaseServer      │ │
  │                      │ ╱                │                      │ ╱
  └──────────────────────┘╱                 └──────────────────────┘╱
```

常见的协议构造型有 `<<HTTP>>`、`<<HTTPS>>`、`<<TCP/IP>>`、`<<JDBC>>`、`<<REST>>`、`<<AMQP>>`、`<<SSH>>` 和 `<<SMTP>>`。选择其中哪一个取决于所需的详细程度：`<<TCP/IP>>` 指明传输方式，`<<HTTPS>>` 还进一步说明连接是加密的，这通常是更有用的信息。

### 多重性与嵌套 {/*#multiplicity-and-nesting*/}

多重性写在通信路径的末端，并且需要使用类型名称：诸如 `appsrv01:ApplicationServer` 的实例始终恰好是一台机器。

嵌套可以跨越多个层级，每一层都运行在包围它的那一层之上：

```text
<<device>>                  ServerHardware
  <<executionEnvironment>>    Linux
    <<executionEnvironment>>    Docker Engine
      <<artifact>>                shop-app:2.4.0
```

对图的目的无关紧要的层级会被省略，例如容量规划中的容器运行时。相反，在发布计划中，镜像的版本标签则是关键信息。

## 示例：三层 Web 商店 {/*#example-three-tier-web-shop*/}

该商店由浏览器前端、容器中的应用程序和关系型数据库组成。每一层都运行在各自的机器上，应用服务器有两台，而数据库只能从应用服务器访问。

```text
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ClientPC                                  │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Browser                             │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 0..*
               <<HTTPS>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  ApplicationServer                         │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  Docker Engine                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-app:2.4.0                │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
                          │ 2
                <<JDBC>>  │
                          │ 1
      ┌────────────────────────────────────────────┐
     ╱                                            ╱│
    ┌────────────────────────────────────────────┐ │
    │  <<device>>                                │ │
    │  DatabaseServer                            │ │
    │                                            │ │
    │  ┌──────────────────────────────────────┐  │ │
    │  │  <<executionEnvironment>>            │  │ │
    │  │  PostgreSQL 16                       │  │ │
    │  │                                      │  │ │
    │  │  ┌────────────────────────────────┐  │  │ │
    │  │  │  <<artifact>>                  │  │  │ │
    │  │  │  shop-schema.sql               │  │  │ │
    │  │  └────────────────────────────────┘  │  │ │
    │  └──────────────────────────────────────┘  │ ╱
    └────────────────────────────────────────────┘╱
```

这个示例说明了：

- 在 `<<JDBC>>` 路径的应用服务器一端，多重性 `2` 表明有两台应用服务器访问数据库，客户端一端的 `0..*` 表明可以连接任意数量的客户端，包括零个。
- 对于*何时*发生哪次调用，图中只字未提。调用的顺序属于[序列图](./sequence-diagram.md)。

## 常见错误 {/*#common-mistakes*/}

1. **节点内部放置类或组件：** 节点包含制品。逻辑元素属于[类图](./class-diagram.md)或组件图，并通过 `<<manifest>>` 与制品相连。
2. **通信路径没有协议：** 线上没有 `<<HTTPS>>` 或 `<<JDBC>>`，图就不再显示哪些连接是加密的，或防火墙必须开放哪些端口。
3. **混淆设备与执行环境：** `<<device>>` 是硬件，`<<executionEnvironment>>` 是运行在其上的软件。容器不是设备。
4. **通信路径上带箭头：** 路径是无向的。方向属于诸如 `<<deploy>>` 或 `<<manifest>>` 的依赖。
5. **绘制每一个文件：** 图中只应包含对安装和运行有意义的内容，而不是每个库和配置文件。
6. **缺少多重性：** 由四台机器组成的集群被绘制为没有 `4` 的单个节点，会隐藏其规模。
7. **将逻辑层等同于节点：** 表示层、逻辑层和数据层是逻辑上的划分，节点则是物理上的划分。三层完全可能运行在同一台机器上。
