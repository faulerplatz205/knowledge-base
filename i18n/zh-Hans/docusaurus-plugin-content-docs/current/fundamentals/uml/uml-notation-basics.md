# UML 符号基础

## 概述 {/*#overview*/}

少数几种符号元素几乎出现在每一种 UML 图中，与图类型无关。可见性标记、多重性、关键字和构造型、注释、约束以及图框架在[类图](./class-diagram.md)、[组件图](./component-diagram.md)和[状态机图](./state-machine-diagram.md)中含义相同。

---

## 可见性 {/*#visibility*/}

可见性规定谁可以访问某个特征（属性、操作，或包或组件的成员）。它以单个字符直接写在特征名称之前。

| 标记   | 名称      | 允许访问者                           | 典型用途                 |
| ------ | --------- | ------------------------------------ | ------------------------ |
| `+`    | public    | 所有能看到该分类器的元素             | 类的接口                 |
| `-`    | private   | 仅分类器自身                         | 内部状态、辅助操作       |
| `#`    | protected | 分类器及其特化（子类）               | 供子类使用的扩展点       |
| `~`    | package   | 同一包中的所有元素                   | 单个模块内部的协作       |

另有两种标记常与可见性混淆，但表达的是别的含义：

- 名称前的 `/` 标记**派生**特征，其值由其他特征计算得出（`/ age` 来自 `dateOfBirth`）。
- 带下划线的名称标记**静态**特征，它属于分类器而不是某个具体对象。

下面的类使用了所有这些标记。纯文本无法显示下划线，因此静态属性 `MAX_LIMIT` 改用 `(static)` 标记：

```text
┌──────────────────────────────────────┐
│               Account                │
├──────────────────────────────────────┤
│ + accountNumber: String              │
│ - balance: Decimal                   │
│ # owner: Customer                    │
│ ~ auditLog: LogEntry [0..*]          │
│ / available: Decimal                 │
│ + MAX_LIMIT: Decimal = 5000 (static) │
├──────────────────────────────────────┤
│ + deposit(amount: Decimal)           │
│ + withdraw(amount: Decimal): Bool    │
│ - validate(amount: Decimal): Bool    │
└──────────────────────────────────────┘
```

可见性在 UML 中是可选的。缺少标记表示*未指定*，而不是 *public*，尽管许多工具默认设为 public。

## 多重性 {/*#multiplicities*/}

多重性规定关联的一端可以有多少个对象参与，或者一个属性可以持有多少个值。它写在关联端旁边，或写在属性类型之后的方括号中。

| 符号     | 范围                 | 读法                                               |
| -------- | -------------------- | -------------------------------------------------- |
| `1`      | 恰好 1               | 必选，恰好一个对象                                 |
| `0..1`   | 0 或 1               | 可选，至多一个对象                                 |
| `*`      | 0 到无界             | `0..*` 的简写，没有隐含的下界 1                   |
| `0..*`   | 0 到无界             | 可选，任意数量                                     |
| `1..*`   | 1 到无界             | 必选，至少一个                                     |
| `n..m`   | n 到 m               | 显式范围，例如 `2..4`                             |
| `5`      | 恰好 5               | 固定数量                                           |
| `1..3,7` | 1 到 3，或恰好 7     | 多个范围                                           |

读写多重性的规则：

- 多重性放在它所描述的类旁边，表示该类的多少个对象与另一端的一个对象相链接。
- 下界决定关系是可选（`0`）还是必选（`1` 或更高）。
- 上界决定实现中持有单个引用（`1`）还是集合（`*`）。
- 省略的多重性在形式上是未定义的，大多数工具和教材将其理解为 `1`。

### 读一个关联 {/*#reading-an-association*/}

```text
┌──────────────┐ 1          0..* ┌──────────────┐
│   Customer   ├─────────────────┤    Order     │
└──────────────┘   places   ▶    └──────────────┘
```

这句话由一端的类、关联名称和另一端的多重性构成，然后在相反方向上重复：

- 一个 `Customer` 下达**零个或多个** `Order` 对象。
- 一个 `Order` 由**恰好一个** `Customer` 下达。

关联名称之后的小实心三角形 `▶` 是**阅读方向**标记。它说明名称在哪个方向上构成句子，不含其他语义。该三角形是可选的，没有它时名称按从左到右或从上到下的方向阅读。

## 关键字与构造型 {/*#keywords-and-stereotypes*/}

尖括号引号（`«…»`）中的标签为现有模型元素增添含义，而无需为其发明新的形状。它写在元素名称的上方或前面。

```text
┌──────────────────────┐
│     «interface»      │
│      Printable       │
├──────────────────────┤
│ + print(): void      │
└──────────────────────┘
```

在无法输入尖括号引号时，可以用双尖括号 `<<interface>>` 代替，因此两种写法在实践中都会出现。

以这种方式书写的标签有两类：

- **关键字**由 UML 自身预定义。它指明某个元类或其固定变体，是保留字，无需事先声明即可使用。
- **构造型**由建模者或工具定义，使元素适应某个领域、某种技术或公司标准。它仅在其被定义之处才有意义。

UML 预定义的关键字：

| 关键字                     | 适用对象       | 含义                           |
| -------------------------- | -------------- | ------------------------------ |
| `<<interface>>`            | 类             | 声明没有实现的操作             |
| `<<enumeration>>`          | 类             | 具有固定字面量集合的类型       |
| `<<include>>`              | 用例关系       | 一个用例始终使用另一个用例     |
| `<<extend>>`               | 用例关系       | 一个用例可选地扩展另一个用例   |
| `<<use>>`                  | 依赖           | 客户端需要提供者               |
| `<<create>>`               | 消息           | 该消息创建接收对象             |
| `<<destroy>>`              | 消息           | 该消息销毁接收对象             |
| `<<device>>`               | 节点           | 一件物理硬件                   |
| `<<executionEnvironment>>` | 节点           | 设备上的运行时环境             |
| `<<artifact>>`             | 制品           | 可部署的文件                   |

构造型建立在这些关键字之上，只要在某处有定义，同样是合法的。对于小型项目，列出所用构造型的简短图例就足够了。分析建模中的经典例子有：`<<entity>>` 表示持久化的业务对象，`<<boundary>>` 表示位于系统边界的元素，`<<control>>` 表示协调元素。

## 注释 {/*#notes-and-comments*/}

注释是带折角的矩形，通过虚线连接到它所说明的元素。它不含语义，是写给读者的自由文本。

```text
┌──────────────┐         ┌───────────────────────────┐
│   Invoice    │- - - - -│ Net amounts only, VAT is  └─┐
└──────────────┘         │ added by the tax service.   │
                         └─────────────────────────────┘
```

使用注释的指导：

- 注释解释*为什么*，而不是*是什么*，用文字重复元素名称没有任何价值。
- 一个注释可以通过多条虚线连接到多个元素。
- 典型内容是假设、待解决的问题以及带理由的决策。
- 只有借助注释才能理解的模型通常存在结构问题。

## 标记值 {/*#tagged-values*/}

标记值为模型元素附加一个具名属性，以花括号中的 `name = value` 书写。标记值通常由构造型引入，由构造型定义存在哪些标记及其含义。

```text
┌───────────────────────────────────┐
│             «entity»              │
│             Customer              │
│ {table = "CUST", schema = "crm"}  │
└───────────────────────────────────┘
```

典型应用：

- 技术映射信息，例如持久化所用的表名或列名
- 诸如 `{author = "Team A", version = "1.2", status = "reviewed"}` 之类的流程元数据
- 诸如 `{maxResponseTime = "200ms"}` 之类的非功能需求
- 由模型驱动工具链使用的代码生成提示

多个标记值在同一对花括号内以逗号分隔，或写在连接到该元素的注释中，每行一个。

## 约束 {/*#constraints*/}

约束是模型有效时必须成立的条件。它写在花括号中，直接置于元素旁或写在附带的注释中。

| 约束                   | 适用对象       | 含义                                 |
| ---------------------- | -------------- | ------------------------------------ |
| `{readOnly}`           | 属性、关联端   | 值设定一次，之后不再修改             |
| `{abstract}`           | 类、操作       | 没有实现，可替代斜体                 |
| `{xor}`                | 两个关联       | 两个关联中恰好一个可以被实例化       |
| `{complete, disjoint}` | 泛化集         | 每个对象恰好属于一个子类             |

自由文本约束同样有效，在实践中也远为常见：

```text
┌──────────────┐         ┌─────────────────────────────┐
│   Account    │- - - - -│ {balance >= overdraftLimit} └─┐
└──────────────┘         └───────────────────────────────┘
```

### OCL {/*#ocl*/}

对于需要形式化表述的条件，OMG 定义了**对象约束语言**（Object Constraint Language，OCL），这是与 UML 配合使用的一种独立的文本语言。上述注释中的条件用 OCL 写作：

```text
context Account
  inv: balance >= overdraftLimit
```

`context` 指明该条件适用的类，`inv` 标记不变式，即必须始终成立的条件。在实践中，花括号中的非形式化条件通常已经足够，关键是将其附加到正确的元素上。

## 角色名与可导航性 {/*#role-names-and-navigability*/}

关联端可以带有**角色名**，说明该类在这一关系中扮演的角色。角色名写在它所描述的那一端，使用小写，并在实现中成为属性名。

```text
┌──────────────┐ employer        employee ┌──────────────┐
│   Company    ├──────────────────────────┤    Person    │
└──────────────┘ 1                    0..*└──────────────┘
```

读法：一个 `Person` 恰好拥有一个以 `employer` 为角色的 `Company`，一个 `Company` 拥有零个或多个以 `employee` 为角色的 `Person` 对象。实现中，`Person` 将带有字段 `employer`，`Company` 将带有集合 `employee`。

当两个类之间被多次连接，或者一个类与自身相关联时，角色名就必不可少：

```text
┌────────────────────┐
│      Employee      │
└──┬──────────────┬──┘
   │ 0..1         │ 0..*
   │ supervisor   │ subordinate
   └──────────────┘
```

读法：一个 `Employee` 至多有一个以 `supervisor` 为角色的其他 `Employee`，以及零个或多个以 `subordinate` 为角色的其他对象。

赋予关联方向的元素：

- **阅读方向（`▶`）：** 位于关联名称旁，纯粹是阅读辅助
- **可导航性（开放箭头）：** 位于一端，表示可以从另一端到达该端
- **不可导航性（小叉号 `x`）：** 位于一端，明确表示无法到达该端
- **没有箭头：** 可导航性未指定，实践中理解为*双向可导航*

## 命名约定 {/*#naming-conventions*/}

以下约定不属于 UML 规范，但在实践中几乎通行。

| 元素       | 约定                         | 示例                          |
| ---------- | ---------------------------- | ----------------------------- |
| 类         | PascalCase，单数名词         | `Invoice`、`CustomerAccount`              |
| 接口       | PascalCase，通常为形容词     | `Printable`、`Comparable`              |
| 属性       | camelCase，名词              | `orderDate`、`totalAmount`             |
| 操作       | camelCase，动词 + 宾语       | `calculateTotal()`                      |
| 角色名     | camelCase，表示角色的名词    | `employer`、`lineItems`            |
| 关联名     | 第三人称单数动词             | `places`、`contains`            |
| 包         | 小写，单数                   | `billing`、`reporting`            |
| 用例       | 动词原形 + 宾语              | `Place order`                      |
| 参与者     | 角色名词，绝不使用人名       | `Customer`、`Payment Service`            |
| 动作       | 动词原形 + 宾语              | `Validate order`                      |
| 状态       | 形容词或分词                 | `Paid`、`Awaiting approval`            |
| 组件       | 描述服务的名词               | `OrderService`                      |
| 节点       | 描述设备或主机的名词         | `Application Server`                      |

两条规则适用于所有元素：

- 整个模型中一个概念只用一个名称，在一张图中名为 `Customer` 的类，在下一张图中不应叫 `Client`。
- 模型所用的语言在整个模型中一次性选定，不混用。

## 图框架 {/*#diagram-frames*/}

每张 UML 图都可以绘制在框架内：框架是一个矩形，其左上角带有五边形标签，标明图的种类和名称。

```text
┌─────────────────────────────────────────────┐
│ sd Place Order ╱                            │
├───────────────┘                             │
│                                             │
│          (contents of the diagram)          │
│                                             │
└─────────────────────────────────────────────┘
```

框架标题遵循 `<kind> <name>` 的模式，可选地带参数。常见的种类关键字，包括简写形式和工具同样接受的完整形式：

| 简写      | 完整形式        | 图                              |
| --------- | --------------- | ------------------------------- |
| `sd`  | `interaction`        | 序列图、通信图、时序图          |
| `act`  | `activity`        | 活动图                          |
| `stm`  | `state machine`        | 状态机图                        |
| `cmp`  | `component`        | 组件图                          |
| `dep`  | `deployment`        | 部署图                          |
| `cls`  | `class`        | 类图                            |
| `uc`  | `use case`        | 用例图                          |
| `pkg`  | `package`        | 包图                            |

框架为必需而非可选的情形：

- 在[序列图](./sequence-diagram.md)中，框架是标准配置，嵌套的组合片段（`alt`、`opt`、`loop`、`ref`）本身也绘制为框架
- 一张图被另一张图引用时，因为引用使用框架名称
- 一页或一份文档中出现多张图并需要加以区分时

对于单独占据一页的单张图，通常省略框架，由标题取而代之。

## 到代码的映射 {/*#mapping-to-code*/}

| 符号                   | 程序中的构造                                 |
| ---------------------- | -------------------------------------------- |
| `+`                    | `public`                                     |
| `-`                    | `private`                                    |
| `#`                    | `protected`                                  |
| `~`                    | Java 中的包私有，C# 中的 `internal`    |
| 带下划线的名称         | `static`                                     |
| 名称前的 `/`           | 计算该值的 getter，没有存储字段              |
| `1`                    | 不得为 `null` 的字段                |
| `0..1`                 | 可空字段，`Optional<T>`、`T?`          |
| `{readOnly}`           | `final`、`readonly`、`const`                 |
| `<<interface>>`        | `interface`                                  |
| `<<enumeration>>`      | `enum`                                       |
| `{abstract}`           | `abstract class`                             |
| 角色名                 | 持有该引用的字段名                           |
| OCL 中的 `inv`           | 在构造函数和每个 setter 中检查               |

## 常见错误 {/*#common-mistakes*/}

1. **将 `-` 误认为短横线：** 前置的 `-` 是可见性标记 *private*，而不是装饰，私有属性无法从其他类访问。
2. **将 `*` 读作“多个，但至少一个”：** `*` 表示 `0..*`，如果要求至少一个对象，则应写作 `1..*`。
3. **多重性放在错误的一端：** 类旁边的多重性表示从对端看有多少个*该类*的对象参与。
4. **花括号与尖括号引号互换：** `{...}` 容纳约束或标记值，`«...»` 容纳关键字或构造型，二者不可互换。
5. **没有定义的构造型：** 在任何地方都没有说明的自创构造型是装饰，而不是信息。
6. **角色名与类名相同：** 在 `Customer` 上写角色 `customer` 没有增加任何信息，角色名只有在传达比类型更多的内容时才值得书写。
7. **注释承载模型语义：** 系统必须强制执行的条件应放在约束中，而不是文字注释里。
8. **混淆阅读方向与可导航性：** 实心三角形 `▶` 涉及句子，开放箭头涉及访问。
9. **语言混用与名称不一致：** 同一概念使用两个名称，会在读者脑中产生两个概念。
10. **到处省略可见性并将一切实现为 public：** 未指定的可见性是模型中的缺口，而不是一项决策。
