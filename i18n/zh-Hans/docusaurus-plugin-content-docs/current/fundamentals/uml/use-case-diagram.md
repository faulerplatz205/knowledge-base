# 用例图

## 概述 {/*#overview*/}

用例图是一种**行为型** UML 图。它展示系统向其环境提供*哪些*服务以及*谁*使用这些服务，但有意不涉及这些服务*如何*实现。因此，该图是系统的外部视图，它所定义的是**系统范围**。

典型应用：

- 界定项目范围：对*什么属于系统、什么不属于系统*的早期回答
- 将功能需求组织为具有业务价值的单元
- 为开发人员、客户和领域专家提供共同的词汇
- 作为需求文档的索引，每个用例对应一份描述

用例始终是对至少一个参与者而言**完整、自成一体且带有可观察的有价值结果**的服务。`Place order` 是用例，`Click the order button` 不是。

## 符号 {/*#notation*/}

| 元素           | 符号                                                     | 含义                                                       |
| -------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 参与者         | 火柴人，名称在下方                                       | 系统外部与其交互的角色                                     |
| 参与者（系统） | 带关键字 `<<actor>>` 的矩形或火柴人                          | 以参与者身份出现的外部系统                                 |
| 系统边界       | 上边缘标有系统名称的矩形                                 | 绘制在内部的一切都是所考察系统的一部分                     |
| 用例           | 内含名称的椭圆，始终位于边界内                           | 系统的一项自成一体的服务，以*动词 + 宾语*命名              |
| 关联           | 不带箭头的实线                                           | 参与者参与某个用例                                         |
| Include        | 带 `<<include>>` 的虚线箭头，指向被包含的用例                  | 基用例**始终**执行被包含的用例                             |
| Extend         | 带 `<<extend>>` 的虚线箭头，指向**基**用例                    | 扩展用例**可以**在某个条件下执行                           |
| 扩展点         | 基用例的某个分区中的具名位置                             | 插入扩展的位置                                             |
| 泛化           | 实线，在一般元素处带空心三角形                           | 参与者或用例的特化                                         |
| 注释           | 虚线连接的折角矩形                                       | 无语义的说明，例如 extend 关系的条件                       |

保持图可读的命名规则：

- 用例以*动词 + 宾语*命名，采用参与者的视角和领域语言，而非实现语言：`Place order` 和 `Cancel invoice`，而不是 `Order management`、`orderService()` 或 `Set the invoice status to 0`
- 参与者以**角色**命名，而不是以人命名：`Clerk`，而不是 `Ms Weber`，因为同一个人可以担任多个角色

## 构成要素 {/*#building-blocks*/}

### 参与者 {/*#actors*/}

参与者是系统外部与系统交换信息的角色。参与者不一定是人。

- **主要参与者：** 触发用例并从中获益。按惯例绘制在左侧
- **次要参与者：** 在用例运行期间被系统调用，并提供系统所需的内容。按惯例绘制在右侧
- **人类参与者：** 担任某个角色的人，绘制为火柴人
- **系统参与者：** 外部系统、服务或定时器，绘制为火柴人或带关键字 `<<actor>>` 的矩形

### 系统边界 {/*#system-boundary*/}

系统边界是标有系统名称的矩形。它将责任范围与环境分开：

- 用例**始终**绘制在边界内，因为它们是系统的服务
- 参与者**始终**绘制在边界外，因为它们不是被构建的对象
- 关联是唯一跨越边界的线

### 关联 {/*#association*/}

参与者与用例之间的实线表示该参与者参与该用例。它不带箭头，因为它表达的是参与而不是数据流的方向。端点处可以写诸如 `1` 或 `*` 的多重性，但在实践中很少需要。

关联只存在于参与者与用例之间，绝不存在于两个用例之间，也不存在于两个参与者之间。

### Include {/*#include*/}

`<<include>>` 描述强制性的复用。基用例在其流程的固定位置始终执行被包含的用例。虚线箭头从基用例**指向**被包含的用例。

```text
 ╭─────────────────────╮                     ╭─────────────────────╮
(      Place order      )╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌►(   Authenticate user   )
 ╰─────────────────────╯     <<include>>     ╰─────────────────────╯
```

被包含的用例是由多个基用例共享的片段。`Authenticate user` 也被 `Manage wish list` 和 `View invoices` 所需要，将其提取出来可避免描述三次。被包含的用例通常不与自己的参与者关联，因为它从不单独启动。

### Extend {/*#extend*/}

`<<extend>>` 描述可选的行为。扩展用例仅在某个条件成立时运行，并插入到基用例的具名**扩展点**处。其虚线箭头的方向与 `<<include>>` 相反：从扩展用例**指向**基用例。

```text
 ╭─────────────────────────────╮
(          Place order          )
(  ---------------------------  )              ╭────────────────────╮
(  extension points:            )◄╌╌╌╌╌╌┬╌╌╌╌╌(   Redeem voucher     )
(   payment method selected     )       ╎      ╰────────────────────╯
 ╰─────────────────────────────╯   <<extend>>
                                        ╎
                     ┌──────────────────┴────────╮
                     │ Condition:                │
                     │ {voucher code entered}    │
                     │ extension point:          │
                     │  payment method selected  │
                     └───────────────────────────┘
```

基用例在没有扩展时也是完整的。`Place order` 没有优惠券也能正常工作，而没有认证则无法工作。该条件是一种约束，因此写在花括号中。UML 将其连同所指的扩展点一起显示在附加到 extend 关系的注释中。许多工具和教材将该注释简化为写在箭头旁的 `<<extend>> {condition}`，这是对同一内容可容忍的简写形式。

一个简单的测试可以区分这两种关系：

- 描述基用例时能否完全不提及另一个用例？如果能，则为 `<<extend>>`
- 移除另一个用例后基用例是否会失效？如果会，则为 `<<include>>`

### 泛化 {/*#generalization*/}

泛化表达*是……的一种*，适用于参与者，也适用于用例。线在较一般的元素处带有空心三角形。

参与者的泛化：特化的参与者继承一般参与者的每一个关联，并可添加自己的关联。

```text
                  ○
                 ╱│╲
                 ╱ ╲
              Customer
                  △
       ┌──────────┴──────────┐
       │                     │
       ○                     ○
      ╱│╲                   ╱│╲
      ╱ ╲                   ╱ ╲
  Registered               Guest
   customer
```

`Registered customer` 和 `Guest` 都继承 `Customer` 的每一个关联，因此 `Search catalogue` 无需连接三次。

```text
                  ╭───────────────╮
                 (  Pay for order  )
                  ╰───────────────╯
                          △
           ┌──────────────┴──────────────┐
           │                             │
 ╭────────────────────╮       ╭─────────────────────╮
(  Pay by credit card  )     (  Pay by direct debit  )
 ╰────────────────────╯       ╰─────────────────────╯
```

用例的泛化功能强大，但容易被滥用。当各变体仅在某个可选步骤上不同时，`<<extend>>` 是更清晰的选择。

## 图与描述 {/*#diagram-and-description*/}

单独的图只是快速概览，而不是规约：它给出用例及其关系的名称，但对流程只字未提。细节存在于**用例描述**中，以连续文本或模板形式书写，每个用例一份。

| 字段       | 内容                                                       |
| ---------- | ---------------------------------------------------------- |
| 名称       | 与图中的标签相同，*动词 + 宾语*                            |
| 简要描述   | 一两句话说明目的和业务价值                                 |
| 参与者     | 主要参与者、次要参与者                                     |
| 前置条件   | 用例开始之前必须成立的条件                                 |
| 后置条件   | 成功运行之后成立的条件                                     |
| 触发器     | 启动用例的事件                                             |
| 主场景     | 带编号的标准流程，一切顺利                                 |
| 备选流程   | 仍能达成目标的偏离，按主场景编号                           |
| 异常       | 导致无法达成目标的偏离                                     |
| 非功能性   | 响应时间、数据量、法律约束                                 |

`Place order` 的填写示例：

- **前置条件：** 购物车中至少有一件商品，客户已通过认证
- **后置条件：** 订单以状态 `paid` 存储，并已发送确认
- **触发器：** 客户确认购物车
- **主场景：** 1. 系统显示订单摘要 => 2. 客户选择支付方式 => 3. 系统预留商品 => 4. 系统处理支付 => 5. 系统确认订单
- **备选流程 2a：** 客户输入优惠券代码，系统减少金额并从步骤 3 继续
- **异常 3a：** 某件商品已无库存，系统提供部分发货或取消订单

场景是穿过用例的*一条具体路径*：主场景是预期路径，备选流程是其余路径。图中绘制为 `<<extend>>` 的内容在描述中表现为备选流程，绘制为 `<<include>>` 的内容则表现为对另一份描述的引用。

## 在需求分析中的作用 {/*#role-in-requirements-analysis*/}

- **[需求规格说明书](../../projectmanagement/requirements-specification.md#requirement-specification)**由客户编写，说明需要*什么*以及*为什么*。用例是其出色的结构，因为每个用例都描述一项需求而不规定解决方案
- **[功能规格说明书](../../projectmanagement/requirements-specification.md#functional-specification)**由承包方编写，说明需求*如何*得到满足。用例图被沿用，描述得到细化，并补充技术约束
- **可追溯性：** 每项需求都应能追溯到至少一个用例，每个用例也应能追溯到至少一项需求。没有需求的用例是镀金，没有用例的需求则被遗忘了
- **估算与规划：** 用例是工作量估算、发布规划和验收测试的天然单元，因为每个用例都可以单独验收
- **测试依据：** 主场景产生正常路径的测试用例，每个备选流程和每个异常至少产生一个进一步的测试用例

用户故事是规划中的小增量，用例是包含所有备选方案的完整服务。一个用例通常会分解为多个用户故事。

## 示例：网上商店 {/*#example-online-shop*/}

所考察的系统是一家网上商店。客户搜索商品目录并下订单。下订单始终需要认证和支付处理，并可通过兑换优惠券进行可选扩展。支付处理调用外部支付提供商。

```text
                                 Online Shop
         ┌──────────────────────────────────────────────────────────┐
         │                                                          │
         │           ╭────────────────────╮                         │
    ┌────┼──────────(   Search catalogue   )                        │
    │    │           ╰────────────────────╯                         │
 ○  │    │                                                          │
╱│╲─┤    │                                                          │
╱ ╲ │    │           ╭────────────────────╮     ╭────────────────╮  │
    └────┼──────────(     Place order      )◄╌╌(  Redeem voucher  ) │
Customer │           ╰────────────────────╯     ╰────────────────╯  │
         │                  ╎       ╎       <<extend>>              │
         │      <<include>> ╎       ╎ <<include>>                   │
         │              ┌───┘       └───────────┐                   │
         │              ▼                       ▼                   │
         │     ╭─────────────────╮      ╭────────────────╮          │  ○
         │    (  Authenticate     )    (  Process payment )─────────┼─╱│╲
         │    (      user         )     ╰────────────────╯          │ ╱ ╲
         │     ╰─────────────────╯                                  │
         │                                                          │
         └──────────────────────────────────────────────────────────┘
                                                                    Payment
                                                                   Provider
```

此示例说明以下内容：

- `Customer` 是左侧的主要参与者，`Payment Provider` 是右侧的次要系统参与者：由商店调用它，而不是相反
- `Authenticate user` 被包含，因为没有它就无法下订单，并且它没有自己的关联，因为它从不单独启动
- `Redeem voucher` 扩展 `Place order`：移除它之后 `Place order` 仍完全可用，这正是 `<<extend>>` 的判断标准

## 常见错误 {/*#common-mistakes*/}

1. **include 与 extend 互换：** `<<include>>` 的箭头背离基用例，表示*始终*，`<<extend>>` 的箭头指向基用例，表示*可能*
2. **实线与虚线互换：** 关联和泛化绘制为实线，`<<include>>` 和 `<<extend>>` 绘制为虚线箭头
3. **用流程步骤代替用例：** `Enter customer number`、`Validate input`、`Save record` 是流程中的步骤，而不是具有业务价值的服务。它们属于用例描述或活动图
4. **缺少系统边界：** 没有边界，图就不再说明哪些功能属于系统，范围也就变得可以商榷
5. **参与者位于边界内：** 按定义，参与者位于边界外，因为它们不属于被构建的内容。绘制在内部的参与者通常意味着把组件误当成了角色
6. **通过 include 进行功能分解：** 将每个用例拆成三个被包含的子用例会使图变成调用树。`<<include>>` 用于跨多个基用例的复用，而不是用于组织单个流程
7. **用例之间的关联：** 两个椭圆之间不带关键字的实线在 UML 中没有意义。用例之间的关系只有 `<<include>>`、`<<extend>>` 或泛化
8. **参与者以个人姓名或职位命名：** 参与者是角色。同一个人在一个用例中可能是 `Clerk`，在另一个用例中则是 `Customer`
9. **关联上带箭头：** 关联表达参与，不带方向
10. **只有图而没有描述：** 图给出用例的名称，但并不规定它们。只有图的项目有的是索引，没有内容
11. **名称中使用技术术语：** `POST /orders` 或 `saveOrder()` 属于实现，而不是从外部看到的服务。名称必须能让客户理解
12. **extend 条件使用方括号：** 该条件是一种约束，因此应放在花括号中，写在附加到 extend 关系的注释里。`[condition]` 是[活动图](./activity-diagram.md)、[状态机图](./state-machine-diagram.md)和[序列图](./sequence-diagram.md)的守卫符号
