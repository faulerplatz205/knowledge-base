# 状态机图

## 概述 {/*#overview*/}

状态机图是一种**行为型** UML 图。它描述*单个*对象、组件或系统的生命周期：它可以处于哪些状态，哪些事件使其从一个状态进入下一个状态，以及过程中发生什么。

典型应用：

- 商店系统中的订单状态（`New`、`Paid`、`Shipped`、`Delivered`、`Cancelled`）
- 会话或登录处理（`Anonymous`、`Authenticated`、`Locked`、`Expired`）
- 设备和连接状态（`Off`、`Booting`、`Ready`、`Error`）
- 协议和解析器逻辑，其中下一个字符根据状态以不同方式解释
- 某个类的内部行为，其方法仅在特定状态下才允许调用

## 符号 {/*#notation*/}

| 元素           | 符号                                | 含义                                                   |
| -------------- | ----------------------------------- | ------------------------------------------------------ |
| 初始伪状态     | 实心圆 `●`                      | 生命周期的起点，每个区域恰好一个                       |
| 状态           | 带名称的圆角矩形                    | 对象在其中等待的情形，以形容词或名词命名                 |
| 迁移           | 从一个状态指向另一个状态的箭头      | 状态变化，标注为 `trigger [guard] / effect`，各部分均可选                 |
| 触发器         | 迁移上的事件名                      | 提供该迁移的事件，例如 `cancel`、`timeout`                |
| 完成迁移       | 无触发器的迁移                      | 源状态的行为一结束即触发                               |
| 守卫           | 迁移上的 `[condition]`                    | 布尔条件，仅当其求值为真时迁移才触发                   |
| 效果           | 迁移上的 `/ action`                    | 迁移触发期间执行的动作，不得阻塞                       |
| 自迁移         | 离开并重新进入同一状态的箭头        | 状态被离开后再次进入，`exit` 和 `entry` 会执行        |
| 内部迁移       | 状态框内的 `trigger / effect`                  | 不改变状态的响应，`exit` 和 `entry` **不**执行        |
| 入口活动       | 状态框内的 `entry / action`                  | 每次进入该状态时执行，与所用迁移无关                   |
| do 活动        | 状态框内的 `do / activity`                  | 状态处于活动期间持续执行，可被中断                     |
| 出口活动       | 状态框内的 `exit / action`                  | 每次离开该状态时执行，与所用迁移无关                   |
| 复合状态       | 包含更多状态的状态框                | 分解为子状态的状态                                     |
| 区域           | 复合状态的一部分，以虚线分隔        | 同时处于活动状态的子状态                               |
| 选择           | 迁移上的菱形                        | 在效果之后求值的分支，出向迁移带有守卫                 |
| 浅历史         | 内含 `H` 的圆                   | 重新进入时，恢复该复合状态中最后活动的子状态           |
| 深历史         | 内含 `H*` 的圆                   | 恢复最后活动的子状态，包括所有嵌套层级                 |
| 终止状态       | 环中的实心圆 `◉`                | 生命周期在此结束，对象不再接受事件                     |

保持图可读的命名规则：

- 状态描述的是条件而非活动：`Paid`、`Waiting for payment`，而不是 `Pay`
- 触发器以事件命名，而非以处理它的方法命名：`cancel`，而不是 `handleCancel`
- 效果和内部活动以带括号的操作命名：`/ refundPayment()`

## 构成要素 {/*#building-blocks*/}

### 状态与迁移 {/*#states-and-transitions*/}

```text
              ●
              │
              ▼
   ╭────────────────────────╮
   │         Idle           │
   ╰────────────────────────╯
              │
              │ coinInserted [amount >= price] / unlock()
              ▼
   ╭────────────────────────╮
   │        Ready           │
   ╰────────────────────────╯
              │
              │ productSelected / dispense()
              ▼
              ◉
```

读作一句话：*在状态 `Idle` 下，当事件 `coinInserted` 发生且条件 `amount >= price` 成立时，执行 `unlock()`，状态机转入 `Ready`*。如果事件发生但守卫为假，则该事件被丢弃，状态不变。

### 自迁移 {/*#self-transition*/}

自迁移之后，对象所处的状态与之前相同。在此过程中，状态被离开后再次进入，因此 `exit` 和 `entry` 会执行，`do` 活动会重新启动。

```text
        ┌───────────────────────────────────┐
        │   digitPressed / appendDigit()    │
        │                                   │
        │   ╭───────────────────────────╮   │
        └──►│        Collecting         │───┘
            ╰───────────────────────────╯
```

如果不希望重新启动 `entry`、`do` 和 `exit`，则改用**内部迁移**。它写在状态框内部，并使状态保持活动：

```text
╭───────────────────────────────────────────╮
│               Collecting                  │
├───────────────────────────────────────────┤
│ digitPressed / appendDigit()              │
╰───────────────────────────────────────────╯
```

例如，以 `entry / startTimer()` 实现的超时会被自迁移重置，而被内部迁移保持运行。

### 内部活动 {/*#internal-activities*/}

三个关键字描述属于状态本身而非迁移的行为：

- `entry / action`：每次进入时执行一次，先于任何 do 活动
- `do / activity`：状态处于活动期间执行，可能运行很长时间，并可被出向迁移中断
- `exit / action`：每次退出时执行一次，在 do 活动结束或中止之后

```text
╭───────────────────────────────────────────╮
│                 Heating                   │
├───────────────────────────────────────────┤
│ entry / switchHeaterOn()                  │
│ do / measureTemperature()                 │
│ exit / switchHeaterOff()                  │
╰───────────────────────────────────────────╯
```

状态变化的顺序始终为：源状态的 `exit`，然后是迁移的效果，最后是目标状态的 `entry`。

将动作放入 `entry` 而不是放在每个进入的迁移上，可以消除重复，并保证日后新增指向该状态的迁移时不会遗漏该动作。

### 复合状态 {/*#composite-states*/}

复合状态包含其自身的状态机。它使图保持小巧，并允许只为一组子状态绘制一次迁移。

```text
╭────────────────────────────────────────────────────────╮
│ Active                                                 │
│                                                        │
│    ●                                                   │
│    │                                                   │
│    ▼                                                   │
│  ╭───────────────────╮  connected  ╭───────────────────╮
│  │     Dialling      │────────────►│    Talking        │
│  ╰───────────────────╯             ╰───────────────────╯
│                                                        │
╰────────────────────────────────────────────────────────╯
              │
              │ hangUp
              ▼
   ╭───────────────────╮
   │       Idle        │
   ╰───────────────────╯
```

迁移 `hangUp` 起始于复合状态的*边界*，因此对 `Dialling` 和 `Talking` 同样适用。

值得牢记的规则：

- 复合状态需要自己的初始伪状态，否则无法确定哪个子状态变为活动
- 每个区域在同一时间恰好有一个子状态处于活动，同时包含它的复合状态也处于活动
- 迁移也可以直接指向某个子状态，这样会绕过初始伪状态
- 复合状态内的终止状态会结束该内部状态机，随后触发复合状态的出向完成迁移

### 区域与并行状态 {/*#regions-and-parallel-states*/}

复合状态可以通过虚线划分为**区域**。每个区域都有自己的初始伪状态、子状态和迁移。复合状态处于活动期间，每个区域中同时有一个子状态处于活动。这用于为一个对象的相互独立的方面建模，例如录制的音频和视频。

```text
╭──────────────────────────────────────────────────────────╮
│ Recording                                                │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮   muteAudio   ╭───────────────╮       │
│  │ AudioRunning  │──────────────►│  AudioMuted   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  │
│                                                          │
│    ●                                                     │
│    │                                                     │
│    ▼                                                     │
│  ╭───────────────╮  pauseVideo   ╭───────────────╮       │
│  │ VideoRunning  │──────────────►│ VideoPaused   │       │
│  ╰───────────────╯               ╰───────────────╯       │
│                                                          │
╰──────────────────────────────────────────────────────────╯
```

事件会提供给每个区域。它可以在一个区域、多个区域中触发迁移，也可以不触发任何迁移。

### 历史状态 {/*#history-state*/}

历史状态回答*状态机在中断之后从何处继续*这一问题。没有它，重新进入复合状态总是从其初始伪状态开始。

```text
              ╭──────────────────────────────────────────╮
              │ Playing                                  │
   resume     │                                          │
 ┌───────────►│   (H)                                    │
 │            │    │                                     │
 │            │    ▼                                     │
 │            │  ╭───────────╮        ╭───────────╮      │
 │            │  │  Track 1  │───────►│  Track 2  │      │
 │            │  ╰───────────╯        ╰───────────╯      │
 │            ╰──────────────────────────────────────────╯
 │                           │ pause
 │            ╭──────────────▼───────────╮
 └────────────│          Paused          │
              ╰──────────────────────────╯
```

浅历史 `(H)` 恢复该层级上最后活动的子状态。深历史 `(H*)` 恢复包括所有嵌套层级在内的最后配置。如果复合状态此前从未被进入过，则指向历史状态的迁移会回退到初始伪状态。

## 状态迁移表 {/*#state-transition-table*/}

状态机图也可以写成**状态迁移表**。该表比图更易于检查完整性，因为按状态对行分组后，缺失的状态与事件组合会很显眼。

| 当前状态 | 事件              | 守卫              | 效果                   | 下一状态    |
| -------- | ----------------- | ----------------- | ---------------------- | ----------- |
| `New`  | `itemAdded`           | –                 | `recalculateTotal()`                | –           |
| `New`  | `paymentReceived`           | –                 | `capturePayment()`                | `Paid`     |
| `New`  | `cancel`           | –                 | `releaseReservation()`                | `Cancelled`     |
| `Paid`  | `dispatched`           | `allItemsInStock`           | `sendTrackingMail()`                | `Shipped`     |
| `Paid`  | `cancel`           | –                 | `refundPayment()`               | `Cancelled`    |
| `Shipped` | `delivered`          | –                 | –                      | `Delivered`    |

表中未出现的组合不触发任何迁移。该事件被丢弃，没有任何效果。

*下一状态*列为空而*效果*列有内容的行描述内部迁移。当前状态与下一状态相同的行描述自迁移。

## 示例：订单状态 {/*#example-order-status*/}

商店系统中订单从创建到交付或取消的生命周期。

```text
                          ●
                          │
                          ▼
                ╭────────────────────────╮
                │          New           │
                │ entry / reserveItems() │
                ╰────────────────────────╯
                     │              │
    paymentReceived  │              │ cancel
    / capturePayment()              │ / releaseReservation()
         ┌───────────┘              └────────────┐
         ▼                                       │
╭────────────────────────╮                       │
│          Paid          │──────────────────────►┤
╰────────────────────────╯  cancel               │
         │                  / refundPayment()    │
         │ dispatched [allItemsInStock]          │
         │ / sendTrackingMail()                  ▼
         ▼                          ╭────────────────────────╮
╭────────────────────────╮          │       Cancelled        │
│        Shipped         │          ╰────────────────────────╯
╰────────────────────────╯                       │
         │                                       │
         │ delivered                             │
         ▼                                       │
╭────────────────────────╮                       │
│       Delivered        │                       │
╰────────────────────────╯                       │
         │                                       │
         └───────────────────┐   ┌───────────────┘
                             ▼   ▼
                             ◉
```

此示例说明以下内容：

- 退款位于迁移 `Paid => Cancelled` 上，而**不是**作为 `Cancelled` 的 `entry` 活动，因为从 `New` 取消的订单从未付款。
- `dispatched` 带有守卫。如果库存不足，订单停留在 `Paid`。
- `Shipped` 没有针对 `cancel` 的迁移。业务规则*已发货的订单不能再取消*通过不存在迁移来表达。

在代码中实现时，每个状态成为枚举的一个值，迁移表成为针对状态和事件的 `switch`。表中未列出的一切都落入默认分支并被拒绝。因此，无效的状态变化在构造上就不可能发生。

## 与活动图的区分 {/*#delimitation-from-the-activity-diagram*/}

| 方面         | 状态机图                         | [活动图](./activity-diagram.md)                 |
| ------------ | -------------------------------- | ----------------------------------------------- |
| 节点         | **状态**，对象在等待             | **动作**，正在执行工作                          |
| 命名         | 形容词或名词：`Paid`           | 动词 + 宾语：`Capture payment`                           |
| 箭头         | 由**事件**触发                   | 在前一个动作**完成**时触发                      |
| 范围         | 一个对象的生命周期               | 一次流程运行，可能跨越多个参与者                |
| 分支         | 出向迁移上的守卫                 | 带守卫流的判定节点                              |
| 并行         | 复合状态内的区域                 | 分叉与汇合                                      |
| 典型问题     | *订单处于哪个状态？*             | *下一步是什么？*                                |

如果箭头只能标注为*之后*之类的内容，则应选用活动图。如果箭头需要 `cancel`、`timeout` 或 `paymentReceived` 这样的名称，则适合使用状态机图。

## 常见错误 {/*#common-mistakes*/}

1. **用活动作为状态名：** `Pay` 是动作，应属于活动图。状态是 `Paid` 或 `Waiting for payment`。
2. **迁移没有触发器：** 两个状态之间没有事件的箭头是完成迁移。源状态完成其行为后它立即触发。
3. **守卫重叠：** 如果两条触发器相同的迁移的守卫可能同时为真，行为即未定义。守卫必须互斥。
4. **混淆守卫与触发器：** `[cancel]` 是条件而非事件。`cancel [orderNotShipped]` 才正确地将二者区分开。
5. **缺少初始伪状态：** 没有它，起始状态未定义。每个图和每个区域恰好需要一个。
6. **无法到达的状态或死胡同状态：** 没有进入迁移的状态永远无法到达。不是终止状态却没有出向迁移的状态会使对象陷入停滞。
7. **用自迁移代替内部迁移：** 自迁移会重新启动 `entry`、`do` 和 `exit`。在 `entry` 中启动的计时器因此被重置。
8. **状态爆炸：** 将相互独立的方面合并为一组扁平状态会使状态数量成倍增加。区域或额外的属性可避免这一点。
