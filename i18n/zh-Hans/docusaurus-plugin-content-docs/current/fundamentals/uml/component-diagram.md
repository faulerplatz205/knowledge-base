# 组件图

## 概述 {/*#overview*/}

组件图是一种**结构型** UML 图。它展示系统如何被划分为可替换的构建块，以及这些构建块相互提供和需要哪些接口。

UML 意义上的组件是系统中的模块化部分，其内容是隐藏的，其行为完全由其接口定义。由此得出两个推论：

- 组件可以被任何提供相同接口的其他组件替换。
- 组件之外的任何事物都不得依赖该组件的内部工作方式。

典型应用：

- 以粗粒度概览的形式记录系统架构
- 在实现开始之前确定团队之间的接口契约
- 使依赖关系可见，从而让循环耦合或过度耦合一目了然
- 规划哪些部分可以独立构建、测试、部署或替换

## 表示法 {/*#notation*/}

| 元素 | 表示法 | 含义 |
| ------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| [组件](#component) | 带有关键字 `<<component>>` 的矩形 | 系统中可替换、自包含的部分 |
| [组件图标](#component) | 右上角带有两个突出小块的小矩形 | 组件的另一种标记方式，可代替关键字使用，也可与关键字一起使用 |
| [提供接口](#provided-and-required-interfaces) | 末端为实心圆的线（*球*，*棒棒糖*） | 组件向其环境提供的服务 |
| [需求接口](#provided-and-required-interfaces) | 末端为半圆的线（*插座*） | 组件需要从其环境获得的服务 |
| [装配连接件](#assembly-connector) | 插座置于球之上 | 一个组件的需求由另一个组件的提供所满足 |
| [端口](#ports-and-delegation-connectors) | 组件边界上的小方块 | 具名的交互点，接口通过它对外暴露 |
| [委托连接件](#ports-and-delegation-connectors) | 从端口指向内部组件的箭头 | 将到达端口的内容转发给负责处理的部分 |
| [接口](#provided-and-required-interfaces)（矩形表示法） | 带有关键字 `<<interface>>` 的矩形 | 连同其操作一起明确写出的契约，是对球的补充，而球只带有名称 |
| [依赖](#dependencies) | 带开放箭头的虚线箭头 | 源依赖于目标，但没有具名的接口 |
| [制品](#artifacts-and-manifestation) | 带有关键字 `<<artifact>>` 的矩形 | 物理文件：`.jar`、`.dll`、`.war`、脚本、配置文件 |
| [具现](#artifacts-and-manifestation) | 从制品指向组件、标有 `<<manifest>>` 的虚线箭头 | 制品是该组件的物理实现 |
| [嵌套组件](#nested-components) | 绘制在另一个组件内部的组件 | 内部结构，即外部组件所包含的*部件* |
| 注释 | 通过虚线相连的折角矩形 | 无语义的说明 |

使图保持可读的命名规则：

- 组件以名词形式按其职责命名：`PaymentService`，而不是 `DoPayment`，也不是 `Payments2`。
- 接口按服务命名，通常带有前缀 `I`：`IPayment`、`IInventory`。
- 同一个接口名始终指向同一份契约。图中不得用同一个名称表示两个不同的事物。

## 构成要素 {/*#building-blocks*/}

### 组件 {/*#component*/}

组件没有固定的大小。典型的选择有可部署的服务、库、架构的某一层或领域中自包含的某个区域。

```text
 ╭──────────────────────╮
 │ <<component>>     ⊞  │
 │ PaymentService       │
 ╰──────────────────────╯
```

### 提供接口与需求接口 {/*#provided-and-required-interfaces*/}

组件之间的依赖应尽可能通过接口表达，而不是直接访问内部。例外情形参见[依赖](#dependencies)。

- **提供接口**绘制为末端带实心圆的线。它表示的承诺是：*这是提供的，可以使用*。
- **需求接口**绘制为末端带半圆的线。它表示的需求是：*这是需要的，必须有人提供*。

```text
   provided interface                  required interface
   (ball, lollipop)                    (socket)

 ╭──────────────────────╮            ╭──────────────────────╮
 │ <<component>>     ⊞  │            │ <<component>>     ⊞  │
 │ PaymentService       │───○        │ OrderService         │───C
 ╰──────────────────────╯            ╰──────────────────────╯
```

球只带有接口名称。只要操作本身很重要，接口就会另外绘制为带有关键字 `<<interface>>` 及其操作列表的矩形，并与球相连。

### 装配连接件 {/*#assembly-connector*/}

装配连接件将需求接口与提供接口相连。在图形上，插座置于球之上，因此这种表示法也称为*球窝式（ball and socket）*。

```text
 ╭──────────────────────╮            ╭──────────────────────╮
 │ <<component>>     ⊞  │ IPayment   │ <<component>>     ⊞  │
 │ OrderService         │───C○───────│ PaymentService       │
 ╰──────────────────────╯            ╰──────────────────────╯
```

该连接件表明 `OrderService` **仅**通过 `IPayment` 使用 `PaymentService`。任何提供 `IPayment` 的组件都可以取代 `PaymentService`。

### 端口与委托连接件 {/*#ports-and-delegation-connectors*/}

端口是组件边界上明确命名的交互点。它绘制为边框上的小方块，并将在该点可访问的接口捆绑在一起。一旦某个组件在多个位置提供同一接口，端口就变得有用，例如具有不同访问规则的内部入口和外部入口。

在组件内部，委托连接件从端口通向实际处理请求的部分。

```text
               IOrdering
                   ○
                   │
 ╭─────────────────■─────────────────────────────────────────────╮
 │ <<component>>   │                                          ⊞  │
 │ OrderManagement │  delegation                                 │
 │                 │                                             │
 │    ╭────────────┴─────────╮            ╭──────────────────╮   │
 │    │ <<component>>     ⊞  │  IPricing  │ <<component>> ⊞  │   │
 │    │ OrderIntake          │───C○───────│ PricingEngine    │   │
 │    ╰──────────────────────╯            ╰──────────────────╯   │
 │                                                               │
 ╰───────────────────────────────────────────────────────────────╯
```

外部世界在端口处只能看到 `IOrdering`。其背后存在 `OrderIntake` 和 `PricingEngine`，以及它们如何连接，都可以随时更改。

### 嵌套组件 {/*#nested-components*/}

组件可以包含其他组件。内部组件是构成外部组件的*部件*。嵌套使组件图成为适用于多个抽象层次的工具：顶层展示少数几个子系统，其中每一个都可以在独立的图中进一步细化。

两条规则使细化保持一致：

- 外部组件的每个接口要么委托给某个内部部件，要么由外部组件自身实现。
- 内部部件绝不直接与外部相连。连接始终经过外围组件的端口。

### 制品与具现 {/*#artifacts-and-manifestation*/}

组件是逻辑单元，制品是物理文件。二者之间的关系称为*具现*，绘制为带关键字 `<<manifest>>`、从制品指向组件的虚线箭头。

```text
 ╭──────────────────────────────╮
 │ <<artifact>>                 │
 │ payment-service.jar          │
 ╰───────────────┬──────────────╯
                 ╎
                 ╎ <<manifest>>
                 ▼
 ╭───────────────────────────────╮
 │ <<component>>              ⊞  │
 │ PaymentService                │
 ╰───────────────────────────────╯
```

这种映射不必是一对一的。一个制品可以具现多个组件，一个组件也可以分布在多个制品中，例如一个实现文件加一个独立的配置文件。

### 依赖 {/*#dependencies*/}

除接口之外，还可以绘制简单的依赖，即带开放箭头的虚线箭头。它表示*源需要目标*，但不指明契约，是较弱且不够精确的表述。

依赖适用于确实没有自身接口的关系，例如使用共享数据模型或使用未进一步建模的外部系统。凡是存在接口之处，都优先采用球窝表示法，因为只有它才说明依赖*经由什么*运行。

## 与实现的对应关系 {/*#mapping-to-implementation*/}

| 组件图 | 典型实现 |
| -------------------- | ------------------------------------------------------------------------------ |
| 组件 | 可部署的服务、Maven/Gradle 模块、npm 包、.NET 程序集 |
| 提供接口 | 模块的公共 API、REST 资源、消息主题 |
| 需求接口 | 注入的依赖、客户端存根 |
| 装配连接件 | 依赖注入容器或组合根中的装配 |
| 端口 | 已发布的端点，例如基础 URL 或队列名称 |
| 委托连接件 | 从入口点转发到处理请求的内部类 |
| 制品 | 构建结果：`.jar`、`.dll`、`.war`、容器镜像、包 |
| 具现 | 将组件的代码打包进该文件的构建步骤 |
| 依赖 | 没有约定契约的导入或 `require` |

## 与其他图的界限 {/*#delimitation-from-other-diagrams*/}

### 组件图与类图 {/*#component-diagram-and-class-diagram*/}

| 方面 | 组件图 | 类图 |
| ----------------- | ------------------------------------------ | ------------------------------------- |
| 展示的单元 | 子系统、服务、模块 | 类、属性、操作 |
| 粒度 | 粗，每张图只有少数几个框 | 细，常有几十个类 |
| 关系类型 | 提供/需求接口、装配 | 关联、继承、聚合 |
| 回答的问题 | 存在哪些部分，它们如何耦合 | 某一部分的内部结构如何 |
| 典型受众 | 架构、团队边界、规划 | 单个组件的实现 |

### 组件图与部署图 {/*#component-diagram-and-deployment-diagram*/}

组件图是*逻辑*层面的，[部署图](./deployment-diagram.md)是*物理*层面的。

| 方面 | 组件图 | 部署图 |
| ----------------- | -------------------------------------- | ------------------------------------------ |
| 主要元素 | 组件 | 节点：硬件、虚拟机、容器 |
| 回答的问题 | 软件如何构成 | 软件运行在何处 |
| 关系 | 接口与连接件 | 通信路径、协议 |
| 制品 | 作为组件的具现出现 | 作为部署到节点上的内容出现 |

## 示例：在线商店 {/*#example-online-shop*/}

该商店由用户界面、订单服务、支付服务和库存服务组成。用户界面对订单如何处理一无所知，它只需要 `IOrdering`。订单服务则需要 `IPayment` 和 `IStock`，而不知道由哪些组件提供它们。

```text
 ╭────────────────────╮          ╭────────────────────╮          ╭────────────────────╮
 │ <<component>>   ⊞  │IOrdering │ <<component>>   ⊞  │IPayment  │ <<component>>   ⊞  │
 │ ShopUI             │───C○─────│ OrderService       │───C○─────│ PaymentService     │
 ╰────────────────────╯          ╰──────────┬─────────╯          ╰────────────────────╯
                                            ∩
                                            ○  IStock
                                            │
                                 ╭──────────┴─────────╮
                                 │ <<component>>   ⊞  │
                                 │ StockService       │
                                 ╰────────────────────╯
```

这个示例说明了：

- `ShopUI` 恰好有一个插座，因此仅与单一契约耦合。可以添加第二个前端，例如移动应用，而无需更改 `IOrdering` 背后的任何内容。
- `OrderService` 带有两个插座。对 `OrderService` 进行测试时必须填补这两个插座，使用 `PaymentService` 和 `StockService` 或测试替身。每多一个插座就多一个需要提供的依赖，因此带有许多插座的组件很难单独测试。

一种现实的扩展是将 `OrderService`、`PaymentService` 和 `StockService` 包含在一个组件 `Backend` 中，该组件带有单个端口，该端口暴露 `IOrdering` 并将其委托给 `OrderService`。随后 `ShopUI` 将连接到该端口，后端的内部结构也就变得可以互换。

## 常见错误 {/*#common-mistakes*/}

1. **组件之间未经接口直接连接：** 一条普通的线表明两个组件相互耦合，但没有表明通过哪份契约。凡是存在接口之处，都应绘制为球与插座。
2. **球与插座颠倒：** 实心圆属于*提供*服务的组件，半圆属于*需要*服务的组件。
3. **没有提供者的需求接口：** 悬空的插座意味着系统无法运行。要么缺少某个组件，要么该需求已经过时。
4. **把类绘制为组件：** 属性、操作和关联应放在类图中。
5. **内部部件绕过边界连接：** 从内部组件直接连向外部的连接件绕过了外围组件的端口。
6. **循环依赖：** 相互需要对方接口的两个组件将无法再分别构建、部署或替换。
7. **同一个接口名对应不同契约：** 两个同名的球必须提供相同的操作。
8. **混淆组件与制品：** `PaymentService` 是组件，`payment-service.jar` 是具现它的制品。
9. **一张图中组件过多：** 框太多会使图难以阅读。细节应放在细化单个组件的独立图中。
