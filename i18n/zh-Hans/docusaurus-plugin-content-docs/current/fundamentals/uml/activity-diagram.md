# 活动图

## 概述 {/*#overview*/}

活动图是一种**行为型** UML 图。它将流程描述为由控制流连接的一系列动作，其中包括分支、循环以及并行执行的步骤。

典型应用：

- 对跨多个部门或系统运行的业务流程建模
- 在实现之前描述算法，与具体语言无关
- 细化单个用例内部的步骤
- 记录现有工作流，以便与非技术相关方一起评审

---

## 表示法 {/*#notation*/}

| 元素 | 表示法 | 含义 |
| --------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| 初始节点 | 实心圆 `●` | 活动的起点，每张图恰好一个 |
| 动作 | 圆角矩形 | 一个不可再分的工作步骤，按*动词 + 宾语*命名 |
| 活动（调用） | 带耙形符号的圆角矩形 | 在独立的图中进一步分解的步骤 |
| 控制流 | 实线箭头 | 执行顺序，从一个动作指向下一个动作 |
| 守卫条件 | 写在流上的 `[condition]` | 允许经过该流的条件 |
| 判定节点 | 菱形，一个入边、多个出边 | 分支，各出边带有互斥的守卫条件 |
| 合并节点 | 菱形，多个入边、一个出边 | 将多条备选路径重新汇集，**不**等待 |
| 分叉 | 粗横条，一个入边、多个出边 | 将流拆分为并发流 |
| 汇合 | 粗横条，多个入边、一个出边 | 等待所有入边的流都到达 |
| 活动终止 | 环中的实心圆 `◉` | 结束整个活动，包括仍在运行的路径 |
| 流终止 | 带叉的圆 `⊗` | 仅结束到达此处的路径，活动继续 |
| 对象节点 | 流上的普通矩形 | 从一个动作传递给下一个动作的数据 |
| 分区 | 带标签的泳道 | 对该泳道中的动作负责的参与者、角色或系统 |
| 注释 | 通过虚线相连的折角矩形 | 无语义的说明 |

使图保持可读的命名规则：

- 动作按*动词 + 宾语*命名：`Validate order`，而不是 `Order`，也不是 `Validation`
- 守卫条件写在方括号中，直接标注在流上，而不是写在动作内部
- 分支的其余情形标注为 `[else]`，而不是取反的条件

## 构成要素 {/*#building-blocks*/}

### 顺序 {/*#sequence*/}

依次执行的动作。流从初始节点出发，经过每个动作，在活动终止节点结束。

```text
          ●
          │
          ▼
 ╭─────────────────╮
 │  Receive order  │
 ╰─────────────────╯
          │
          ▼
 ╭─────────────────╮
 │   Check stock   │
 ╰─────────────────╯
          │
          ▼
          ◉
```

### 判定与合并 {/*#decision-and-merge*/}

判定节点将流拆分为多个备选路径。恰好有一条出边被选中，因此守卫条件必须互斥，并且必须覆盖所有可能的情形。合并节点将备选路径重新汇集，它会放行每条到达的路径，且从不等待。

```text
                    │
                    ▼
              ╱───────────╲
             ╱   amount    ╲
             ╲   > 100 ?   ╱
              ╲───────────╱
               │         │
        [yes]  │         │ [no]
        ┌──────┘         └──────┐
        │                       │
        ▼                       ▼
╭───────────────╮       ╭───────────────╮
│Apply discount │       │  Keep price   │
╰───────────────╯       ╰───────────────╯
        │                       │
        └──────┐         ┌──────┘
               ▼         ▼
              ╱───────────╲
             ╱             ╲
             ╲             ╱
              ╲───────────╱
                    │
                    ▼
```

具有两个以上结果的分支使用一个带多条守卫流的判定节点，对应于 `if / else if / else` 或 `switch` 语句。无论有多少路径汇入，合并节点始终是单个菱形。

### 循环 {/*#loop*/}

循环是指向图中较早位置的控制流。在下图中，判定位于动作*之后*，因此循环体至少执行一次，对应于 `do … while` 循环。

```text
              ●
              │
              ▼
     ╭─────────────────╮
┌───►│   Read record   │
│    ╰─────────────────╯
│             │
│             ▼
│       ╱───────────╲
│      ╱    more     ╲
│      ╲  records ?  ╱
│       ╲───────────╱
│        │         │
│  [yes] │         │ [no]
└────────┘         ▼
                   ◉
```

若将判定放在动作*之前*，回边从其上方进入，则同一结构就变成前测试的 `while` 循环，其循环体可能执行零次。

### 分叉与汇合 {/*#fork-and-join*/}

分叉将一个流拆分为多个并发运行的流。汇合等待所有入边的流都到达，然后才作为单个流继续。如果没有汇合，活动可能在并行步骤仍在运行时就结束了。

```text
                  │
                  ▼
        ━━━━━━━━━━━━━━━━━━━━━
        │                   │
        ▼                   ▼
╭─────────────────╮ ╭─────────────────╮
│  Reserve stock  │ │   Charge card   │
╰─────────────────╯ ╰─────────────────╯
        │                   │
        ▼                   ▼
        ━━━━━━━━━━━━━━━━━━━━━
                  │
                  ▼
```

UML 中的并发意为*没有规定的顺序*，不一定是*在不同处理器上同时执行*。两个分支是运行在两个线程上，还是以任意顺序依次执行，属于实现层面的决定。

## 分区（泳道） {/*#partitions-swimlanes*/}

分区按执行动作的参与者、角色、部门或系统对动作进行分组。泳道可以纵向或横向绘制，流直接跨越泳道边界。

值得牢记的规则：

- 一个动作恰好属于一条泳道，泳道回答的是*由谁执行*
- 判定节点和合并节点属于做出判定的参与者所在的泳道
- 分叉可以跨越多条泳道，不同参与者的并行工作正是这样表示的
- 泳道跨越的次数是衡量流程协调工作量的粗略指标

## 与代码的对应关系 {/*#mapping-to-code*/}

| 活动图 | 程序结构 |
| ------------------------------------------- | ------------------------------------------------ |
| 顺序排列的动作 | 依次排列的语句 |
| 带两个守卫条件的判定加合并 | `if / else` |
| 带多个守卫条件加 `[else]` 的判定 | `if / else if / else` 或 `switch` |
| 回边，判定位于循环体之后 | `do … while` |
| 回边，判定位于循环体之前 | `while` 或 `for` |
| 分叉与汇合 | 线程、任务、`Promise.all`、并行流 |
| 被调用的活动 | 方法或函数调用 |
| 两个动作之间的对象节点 | 作为参数传递的返回值 |
| 活动终止 | 方法结束，`return` |
| 流终止 | 一条路径终止，其余路径继续运行 |

## 示例：处理在线订单 {/*#example-processing-an-online-order*/}

涉及三个分区：客户、商店系统和仓库。订单由商店进行校验，无效订单被拒绝，有效订单由仓库拣货并发货。

```text
      Customer       │       Shop System        │      Warehouse
─────────────────────┼──────────────────────────┼─────────────────────
          ●          │                          │
          │          │                          │
          ▼          │                          │
 ╭─────────────────╮ │                          │
 │   Place order   │ │                          │
 ╰─────────────────╯ │                          │
          │          │                          │
          └──────────┼────────────┐             │
                     │            │             │
                     │            ▼             │
                     │   ╭─────────────────╮    │
                     │   │ Validate order  │    │
                     │   ╰─────────────────╯    │
                     │            │             │
                     │            ▼             │
                     │      ╱───────────╲       │
                     │     ╱    order    ╲      │
                     │     ╲   valid ?   ╱      │
                     │      ╲───────────╱       │
                     │       │         │        │
                     │ [no]  │         │ [yes]  │
          ┌──────────┼───────┘         └────────┼──────────┐
          │          │                          │          │
          ▼          │                          │          ▼
 ╭─────────────────╮ │                          │ ╭─────────────────╮
 │ Read rejection  │ │                          │ │   Pick items    │
 ╰─────────────────╯ │                          │ ╰─────────────────╯
          │          │                          │          │
          ▼          │                          │          ▼
          ◉          │                          │ ╭─────────────────╮
                     │                          │ │   Ship parcel   │
                     │                          │ ╰─────────────────╯
                     │                          │          │
          ┌──────────┼──────────────────────────┼──────────┘
          │          │                          │
          ▼          │                          │
 ╭─────────────────╮ │                          │
 │ Receive parcel  │ │                          │
 ╰─────────────────╯ │                          │
          │          │                          │
          ▼          │                          │
          ◉          │                          │
```

这个示例说明了：

- 客户启动流程，因此初始节点位于客户泳道中
- `Validate order` 在此处是单个动作。如果校验较为复杂，则它会成为带有自己图的被调用活动
- 守卫条件 `[no]` 和 `[yes]` 互斥且覆盖所有情形，因此流在判定处永远不会卡住
- 两个分支都在活动终止节点结束，该流程有两种可能的结果
- 对订单*如何*校验或发货*需要多长时间*只字未提，活动图建模的是控制流，而不是数据结构或时序

一种现实的扩展是在 `[yes]` 之后分叉，使商店泳道中的 `Charge card` 与仓库泳道中的 `Pick items` 并发运行，并在 `Ship parcel` 之前重新汇合。

## 常见错误 {/*#common-mistakes*/}

1. **缺失或重叠的守卫条件：** 判定的每条出边都需要守卫条件，守卫条件必须互斥且完备，否则流要么无路可走，要么有多条路可走
2. **用判定代替分叉：** 菱形表示*这些路径中的一条*，粗横条表示*所有这些路径*
3. **有分叉无汇合：** 活动可能在并行流仍在运行时到达终止节点，随后终止节点会将它们丢弃
4. **有汇合无分叉：** 汇合会等待一个永远不会到达的流，导致流程死锁
5. **用名词作为动作名称：** `Invoice` 什么也没说明，`Create invoice` 则说明了
6. **条件写在动作内部：** 条件应放在出边上，动作是所做的事情，而不是所检查的内容
7. **多个初始节点：** 一个活动恰好有一个起点。并发启动应通过分叉来建模
8. **把泳道当作装饰：** 如果绘制了参与者，但流从不跨越泳道边界，则分区没有带来任何价值
9. **混淆控制流与数据流：** 动作之间传递的数据应放在对象节点中，而不是写在控制流的标签里
