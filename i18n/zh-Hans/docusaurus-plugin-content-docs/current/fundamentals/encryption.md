# 加密与数字签名

## 概述 {/*#overview*/}

加密通过将数据转换为不可读的格式，保护数据免受未经授权的访问。数字签名用于验证数据的真实性和完整性，确保数据在传输过程中未被篡改。

## 对称加密 {/*#symmetric-encryption*/}

发送方和接收方使用**同一个密钥**加密和解密数据。

- **速度快**，适合加密大量数据
- **密钥分发**是一项挑战，因为密钥必须事先安全地共享
- **常见算法：** AES（Advanced Encryption Standard，高级加密标准）、DES（Data Encryption Standard，数据加密标准）、3DES（Triple Data Encryption Standard，三重数据加密标准）
- **典型用途：** 批量数据加密

```text
Plaintext => [Encrypt with Key] => Ciphertext => [Decrypt with Key] => Plaintext
```

### AES {/*#aes*/}

AES（Advanced Encryption Standard）于 2001 年标准化，作为 DES 的继任者，是当今使用的对称算法。

- **分组密码：** 加密 128 位的数据块，较长的数据会被拆分为多个块并进行填充
- **密钥长度：** 128、192 或 256 位，决定轮数（10、12 或 14）
- **性能：** 在当前 CPU 上由硬件实现（AES-NI），速度足以用于全盘加密
- **被视为安全：** 目前不存在比穷举所有密钥更有效的实用攻击方法

由于分组密码对每个数据块单独加密，因此由**工作模式**决定各数据块如何关联：

| 模式                        | 特性                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| ECB（Electronic Codebook）   | 每个数据块独立加密，相同的明文块产生相同的密文块，因此不适用 |
| CBC（Cipher Block Chaining） | 每个数据块与前一个密文块组合，需要初始化向量，无完整性保护    |
| CTR（Counter Mode）          | 将分组密码转变为可并行的流密码                                                               |
| GCM（Galois/Counter Mode）   | 当前的默认选择：CTR 加上一个同样能检测篡改的认证标签                                    |

典型用途：文件和磁盘加密（LUKS、BitLocker、VeraCrypt）、[TLS](#hybrid-encryption) 中的负载加密、加密压缩包和数据库列。

### DES 与 3DES {/*#des-and-3des*/}

DES 是 AES 的前身，密钥长度为 56 位，如今可在数小时内被暴力破解，因此已被攻破。3DES 将 DES 应用三次，有效密钥长度达到 112 位，但速度较慢，仅见于遗留系统。两者均不用于新的开发。

## 非对称加密 {/*#asymmetric-encryption*/}

使用**密钥对**：公钥（公开共享）和私钥（保密保存）。

- 用公钥加密的数据只能用与之匹配的私钥解密
- 由于数学运算复杂，比对称加密**慢**
- **常见算法：** RSA（Rivest-Shamir-Adleman）、ECC（Elliptic Curve Cryptography，椭圆曲线密码学）
- **典型用途：** 密钥交换（混合加密）、数字签名

```text
Plaintext => [Encrypt with Public Key of Receiver] => Ciphertext => [Decrypt with Private Key of Receiver] => Plaintext
```

### RSA {/*#rsa*/}

RSA 是最知名的非对称算法，其名称取自发明者 Rivest、Shamir 和 Adleman。

- **安全基础：** 将两个大素数相乘很容易，而将乘积分解回这两个素数则很困难
- **密钥长度：** 最低 2048 位，长期保护使用 3072 或 4096 位，与对称密钥长度不可直接比较
- **功能：** 同一密钥对可用于加密和数字签名
- **限制：** 负载必须短于密钥，因此 RSA 加密的是对称密钥，而不是数据本身

ECC（Elliptic Curve Cryptography）以短得多的密钥达到相当的安全性。256 位的 ECC 密钥大致相当于 3072 位的 RSA 密钥。因此 ECC 已成为 [TLS](#hybrid-encryption) 密钥交换（ECDHE）的默认选择，并越来越多地用于证书签名（ECDSA）。

### Diffie-Hellman {/*#diffie-hellman*/}

Diffie-Hellman 不是加密算法，而是一种**密钥协商**方法。双方根据公开值和各自的秘密值推导出共享密钥，而该密钥本身从不被传输。

```text
Alice                                  Bob
secret a                               secret b
       ── public value A ────────────►
       ◄──────────── public value B ──
shared key from (B, a)  ==  shared key from (A, b)
```

- 窃听者能看到双方的公开值，但无法据此推导出共享密钥
- **临时**变体（DHE、ECDHE）为每个会话生成新的密钥对，因此即使长期密钥日后泄露，也无法解密已记录的流量（前向保密）
- 仅靠 Diffie-Hellman 无法对任何一方进行身份认证：没有证书时，中间人攻击者可与双方各协商一个密钥并转发流量

## 混合加密 {/*#hybrid-encryption*/}

在实践中，两种方法都不会单独使用：非对称密码学解决密钥分发问题，对称密码学承担实际的加密工作。TLS 正是以这种方式将二者结合：

1. 服务器通过包含其公钥的**证书**证明自己的身份。
2. 双方通过 **ECDHE** 协商会话密钥，并使用证书对该交换过程进行认证。
3. 负载使用该会话密钥进行**对称**加密，通常为 AES-GCM。
4. 连接结束时，会话密钥被丢弃。

## 哈希函数 {/*#hash-functions*/}

哈希函数将任意大小的数据映射为固定大小的输出（哈希值/摘要）。

- **单向：** 无法从哈希值推导出原始数据
- **确定性：** 相同的输入始终产生相同的哈希值
- **抗碰撞：** 不同的输入不应产生相同的哈希值
- **雪崩效应：** 输入中改变一个比特，哈希值中大约一半的比特会随之改变

典型应用：下载文件的完整性校验、重复数据检测、签名，以及结合下文方法存储密码。

| 算法 | 摘要长度 | 评估                                                                                                   |
| --------- | ------------- | ------------------------------------------------------------------------------------------------------------ |
| MD5       | 128 位       | 已被攻破，可在数秒内构造碰撞，仅可用作防止传输错误的校验和 |
| SHA-1     | 160 位       | 已被攻破，存在实用的碰撞攻击，不再用于签名                                     |
| SHA-256   | 256 位       | 当前标准，属于 SHA-2 系列                                                                   |
| SHA-512   | 512 位       | 与 SHA-256 类似但摘要更长，在 64 位系统上比 SHA-256 更快                                       |
| SHA-3     | 可变      | 内部构造与 SHA-2 不同，作为 SHA-2 被削弱时的后备方案                   |

## 密码哈希 {/*#hashing-passwords*/}

密码从不以明文存储，也从不加密存储，因为必然存在某处有可解密它们的密钥。密码经过哈希处理，使得数据库被盗时不会暴露密码本身。

仅使用普通的 `SHA-256` 对此并不足够，原因有两点：

- **相同的密码产生相同的哈希值**，因此哈希值会暴露哪些账户使用了相同的密码，而预先计算的表（彩虹表）可立即还原常见密码
- **哈希函数在设计上就很快**，当前硬件每秒可计算数十亿次 SHA-256 哈希，使得暴力破解短密码变得可行

### 盐 {/*#salt*/}

盐是为每个密码生成的随机值，与密码一起进行哈希。盐不是秘密，与哈希值一同存储。

```text
hash = H(salt + password)
```

- 由于盐不同，相同的密码会产生不同的哈希值
- 彩虹表失去价值，因为攻击者需要为每个盐准备一张表
- 每个密码都必须单独攻击，而不能一次性攻击全部密码

**胡椒**（pepper）是一个额外的秘密值，对所有密码都相同，并存储在数据库之外，例如应用程序配置中。它仅在数据库泄露而配置未泄露时才有帮助。

### 工作因子 {/*#work-factor*/}

第二项措施是有意让哈希变慢：为密码设计的方法会多次重复其内部运算。重复次数可配置为**成本因子**，并随着硬件变快而提高。每次登录约 100 ms 的延迟对用户几乎无感，却使尝试数十亿个候选密码变得不可行。

### bcrypt {/*#bcrypt*/}

bcrypt 是此类方法中使用最广泛的一种，基于 Blowfish 密码。

- 盐在哈希值**内部**生成并存储，因此无需单独的列
- 成本因子是哈希值的一部分，因此在提高成本因子之后仍可验证旧的哈希值
- 有意设计得慢且受内存限制，因此比基于 SHA 的方法更难在 GPU 上加速
- 限制：仅使用输入的前 72 个字节

```text
$2b$12$eImiTXuWVxfM37uY4JANjQ.../hJ6CtPTuOrAXTlHGDLcJU3wG6Hpu
 │   │  └── salt (22 characters) ──┘└── hash ────────────────┘
 │   └───── cost factor 12, meaning 2^12 rounds
 └───────── algorithm identifier
```

具有相同用途的替代方案：

| 方法 | 说明                                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------------------------- |
| Argon2id  | 密码哈希竞赛（Password Hashing Competition）的获胜者，可在时间、内存和并行度上调节，是当前对新系统的推荐方案 |
| scrypt    | 内存困难型，因此在专用硬件上并行化的成本很高                                                     |
| PBKDF2    | 广泛可用且已标准化，但仅受计算限制，因此是这些方案中最弱的                  |
| bcrypt    | 久经考验、易于理解、各种语言均可使用                                                                   |

密码存储中绝不应出现的做法：明文、可逆加密、未加盐的哈希，以及单次使用 MD5、SHA-1 或 SHA-256 等快速哈希函数。

## 数字签名 {/*#digital-signatures*/}

数字签名用于验证数据由特定方发送且未被更改。

**签名（发送方）：**

1. 创建消息的[哈希](#hash-functions)
2. 使用发送方自己的**私钥**加密该哈希 => 这就是签名
3. 将消息与签名一同发送

**验证（接收方）：**

1. 使用发送方的**公钥**解密签名 => 得到原始哈希
2. 对收到的消息独立计算哈希
3. 比较两个哈希：若一致，则签名有效且消息真实

此过程描述的是 RSA 签名。[ECDSA](#rsa) 不对哈希进行加密，而是根据哈希和私钥计算签名。接收方使用公钥进行验证。
