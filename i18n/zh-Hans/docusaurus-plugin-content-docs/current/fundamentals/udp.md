# UDP（用户数据报协议）

## 概述 {/*#overview*/}

UDP 是 [OSI 模型](./osi-model.md)第 4 层的无连接传输协议，规范见 RFC 768。它在 IP 的数据包传递之上几乎没有增加任何内容：仅有端口号、长度字段和校验和。每个数据报都独立寻址和路由，无需事先建立连接，也没有共享状态、确认或重传。数据报发出后，要么到达，要么丢失，发送方永远不会得知是哪种情况。UDP 端点通过 IP 地址与端口号的组合来寻址。

---

## 特性 {/*#characteristics*/}

| 属性 | UDP 中的行为 |
| --------------------- | -------------------------------------------------------------------- |
| 连接 | 无连接，数据报可立即发送 |
| 传递 | 不可靠，丢失的数据报不会被察觉，也不会被重发 |
| 顺序 | 无保证，数据报可能以不同的顺序到达 |
| 重复数据 | 可能出现，检测工作由应用程序负责 |
| 数据模型 | 面向消息，一次发送操作恰好产生一个数据报 |
| 方向 | 双方可随时发送，每个数据报各自独立 |
| 流量控制 | 无 |
| 拥塞控制 | 无，发送方可能使网络泛滥 |
| 首部大小 | 8 字节，固定 |
| 广播 / 组播 | 支持，一个数据报可以寻址多个接收方 |

作为小开销的代价，UDP 不提供任何保证。

---

## 数据报首部 {/*#datagram-header*/}

首部由四个字段组成，每个字段 2 字节：

| 字段 | 用途 |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| 源端口 | 发送方应用程序的端口，若无需应答则可为 0 |
| 目的端口 | 接收方应用程序的端口 |
| 长度 | 首部与有效载荷的长度，单位为字节 |
| 校验和 | 对首部、有效载荷以及部分 IP 首部进行错误检测，在 IPv4 中可选，在 IPv6 中强制 |

损坏的数据报会被静默丢弃。

## 无连接通信 {/*#communication-without-a-connection*/}

与 TCP 不同，TCP 的有效载荷只能在三次握手之后传输，而 UDP 的第一个数据报就已携带有效载荷。最后一个数据报之后，双方都不会保留任何连接状态。

```text
Client                                           Server

  | ---- datagram (query) ---------------------> |   application reads it
  |                                              |
  | <--- datagram (answer) --------------------- |
  |                                              |
  | ---- datagram (query) --------X              |   lost, nobody is informed
  |                                              |
  |  (timeout in the application)                |
  |                                              |
  | ---- datagram (query, repeated) -----------> |
```

- 客户端只能从应答中得知其查询已到达。没有应答可能意味着查询丢失、应答丢失或服务器不可用。
- 数据报的发送方地址从不通过握手来验证。因此可能出现伪造请求，针对 DNS 或 NTP 的放大攻击正是利用了这一点。
- 发往已关闭端口的数据报会得到 ICMP 消息*端口不可达*作为响应。开放端口和被过滤端口通常都保持沉默，因此 UDP 端口扫描往往无法区分这两者。

---

## 无流量控制与拥塞控制 {/*#no-flow-or-congestion-control*/}

UDP 会按应用程序发送的速度尽快传递数据报。如果接收缓冲区已满，后续数据报会被无通知地丢弃。如果网络过载，数据报会在路由器的队列中丢失。

通过 UDP 发送大量数据的应用程序必须自行限制速率（RFC 8085）。否则它会挤占 TCP 流量，因为 TCP 会在丢包时降低速率，而 UDP 则占用腾出的容量。

## 典型应用场景 {/*#typical-use-cases*/}

### UDP 与 TCP 对比 {/*#udp-vs-tcp*/}

| | UDP | [TCP](./tcp.md) |
| --------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 判断标准 | 迟到的数据包毫无价值，或连接的开销超过有效载荷 | 完整性比延迟更重要 |
| 示例 | 实时音视频、网络游戏、简短查询、遥测、通过组播进行的发现 | 文件传输、网页、电子邮件、远程管理、数据库连接 |

### 常用 UDP 端口 {/*#well-known-udp-ports*/}

| 端口 | 服务 | 采用 UDP 的原因 |
| -------- | ------------- | ------------------------------------------------------------------------ |
| 53 | DNS | 一次简短的查询，一次简短的应答，重试比建立连接更划算 |
| 67/68 | DHCP | 客户端尚无 IP 地址，依赖广播 |
| 69 | TFTP | 刻意保持极简，用于引导环境 |
| 123 | NTP | 重传的时间戳到达时已经过时 |
| 161/162 | SNMP | 大量小型状态消息，丢失个别消息可以接受 |
| 443 | QUIC / HTTP/3 | 可靠性由 QUIC 在 UDP 之上实现 |
| 500/4500 | IPsec (IKE) | 密钥协商与 NAT 穿越 |
| 5060 | SIP | 语音连接的信令 |

在 DNS 中，两种协议并行工作：查询和简短应答通过 UDP 传输，而区域传送以及超出 UDP 大小限制的应答则使用 TCP。该限制为 512 字节，或客户端通过 EDNS(0) 通告的缓冲区大小。
