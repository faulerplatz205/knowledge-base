# TCP（传输控制协议）

## 概述 {/*#overview*/}

TCP 是 [OSI 模型](./osi-model.md)第 4 层的面向连接的传输协议，规范见 RFC 9293。它将 IP 不可靠的数据包传递转变为两个应用程序之间可靠、有序的字节流：一端写入的数据完整、按正确顺序且无重复地到达另一端，否则连接会报告错误。TCP 端点通过 IP 地址与端口号的组合来寻址。

---

## 特性 {/*#characteristics*/}

| 属性 | TCP 中的行为 |
| --------------------- | ------------------------------------------------------------------------- |
| 连接 | 面向连接，在传输第一个有效载荷之前先建立连接 |
| 传递 | 可靠，丢失的报文段会被重传 |
| 顺序 | 有保证，报文段在交付前按序列号重新排序 |
| 重复数据 | 被检测并丢弃 |
| 数据模型 | 连续的字节流，不保留消息边界 |
| 方向 | 全双工，双方可同时发送 |
| 流量控制 | 有，通过接收窗口实现 |
| 拥塞控制 | 有，发送速率适应网络负载 |
| 首部大小 | 最小 20 字节，带选项时最大 60 字节 |
| 广播 / 组播 | 不可能，一个连接始终恰好有两个端点 |

这些保证带来的开销包括：更大的首部、连接建立所需的额外一次往返，以及每当丢失的报文段必须重传时产生的延迟。

---

## 报文段首部 {/*#segment-header*/}

| 字段 | 用途 |
| ---------------------- | ---------------------------------------------------------------------- |
| 源端口 | 发送方应用程序的端口 |
| 目的端口 | 接收方应用程序的端口 |
| 序列号 | 本报文段的第一个有效载荷字节在字节流中的位置 |
| 确认号 | 本报文段的发送方期望接收的下一个字节 |
| 标志位 | 控制位，见下文 |
| 窗口 | 本报文段的发送方当前能够接收的字节数 |
| 校验和 | 对首部和有效载荷进行错误检测 |
| 选项 | 最大报文段长度、窗口缩放、选择性确认 |

### 控制标志位 {/*#control-flags*/}

| 标志位 | 含义 |
| ----------------------- | ------------------------------------------------------------------- |
| `SYN`（同步） | 请求建立连接并同步序列号 |
| `ACK`（确认） | 确认号有效 |
| `FIN`（结束） | 此方向不再发送数据 |
| `RST`（复位） | 不经有序终止，立即中止连接 |
| `PSH`（推送） | 要求接收方不延迟地将数据传递给应用程序 |
| `URG`（紧急） | 标记紧急数据（实际上已过时） |

## 连接建立（三次握手） {/*#connection-establishment-three-way-handshake*/}

双方各自通告自己的初始序列号（图中的 `x` 和 `y`），并分别通过 `ack = x + 1` 或 `ack = y + 1` 确认对方的序列号。

```text
Client                                           Server

  | ---- SYN, seq = x -------------------------> |   listening
  |                                              |
  | <--- SYN, ACK, seq = y, ack = x + 1 -------- |   connection accepted
  |                                              |
  | ---- ACK, ack = y + 1 ---------------------> |   connection established
  |                                              |
  | ==== payload ==============================> |
```

- 客户端在第二个报文段之后、服务器在第三个报文段之后即可得知连接在两个方向上均可正常工作。
- 握手在发送第一个有效载荷字节之前需要一次往返。
- 发往已关闭端口的 `SYN` 会得到 `RST` 作为响应，端口扫描正是借此区分已关闭端口与被过滤端口。

---

## 连接终止 {/*#connection-teardown*/}

有序终止会分别关闭每个方向，因此需要四个报文段。`FIN` 仅表示*本端已发送完毕*。另一方向仍可继续传输数据（半关闭）。

```text
Client                                           Server

  | ---- FIN ----------------------------------> |
  | <--- ACK ----------------------------------- |
  | <--- FIN ----------------------------------- |
  | ---- ACK ----------------------------------> |
  |                                              |
  | (TIME_WAIT, then the connection is released) |
```

最先关闭的一方会在 `TIME_WAIT` 状态停留一小段时间，以免旧连接中延迟到达的报文段被误认为是同一端口对上新连接的报文段。`RST` 会跳过此流程，并丢弃所有仍在传输中的数据。

---

## 可靠性 {/*#reliability*/}

- **序列号：** 每个有效载荷字节在流中都有一个位置，从而可以实现重新排序和重复检测。
- **确认：** 接收方确认下一个期望的字节，从而累积确认迄今为止收到的全部数据。
- **重传超时：** 在超时时间内未被确认的报文段会被再次发送。超时时间根据测得的往返时间得出。
- **快速重传：** 针对同一字节的多个重复确认表明有单个报文段丢失，并会在超时到期之前触发重传。
- **校验和：** 损坏的报文段会被丢弃，因此永远不会被确认。缺失的确认会触发重传。
- **选择性确认（SACK）：** 一个选项，使接收方能够准确报告哪些字节范围已到达，从而只需重发缺失的范围。

---

## 流量控制 {/*#flow-control*/}

流量控制保护*接收方*不被压垮。每个报文段都会在窗口字段中通告其发送方当前能缓冲多少字节。对方在途中的未确认数据量永远不得超过此窗口所允许的范围。

缓冲区已满的接收方会通告窗口为零。发送方随即暂停，直到后续报文段通告了更大的窗口。

## 拥塞控制 {/*#congestion-control*/}

拥塞控制保护*网络*不被压垮，并独立于接收窗口工作。有效发送上限是接收窗口与拥塞窗口中较小的一个。

| 阶段 | 行为 |
| -------------------- | ------------------------------------------------------------------------- |
| 慢启动 | 拥塞窗口从较小值开始，呈指数增长 |
| 拥塞避免 | 超过阈值后，窗口仅线性增长 |
| 检测到丢包 | 窗口被缩小，因为丢包意味着出现拥塞 |
| 快速恢复 | 快速重传之后，以缩小的窗口继续传输 |

## 典型应用场景 {/*#typical-use-cases*/}

### TCP 与 UDP 对比 {/*#tcp-vs-udp*/}

| | TCP | [UDP](./udp.md) |
| --------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 判断标准 | 完整性比延迟更重要 | 迟到的数据包毫无价值，或连接的开销超过有效载荷 |
| 示例 | 文件传输、网页、电子邮件、远程管理、数据库连接 | 实时音视频、网络游戏、简单的查询/响应协议 |

### 常用 TCP 端口 {/*#well-known-tcp-ports*/}

| 端口 | 服务 |
| ------- | ------------------------------------------------------------- |
| 20/21 | FTP 数据 / 控制 |
| 22 | SSH |
| 25 | SMTP |
| 53 | DNS 区域传送以及超出 UDP 大小限制的响应 |
| 80 | HTTP |
| 110/995 | POP3 / POP3S |
| 143/993 | IMAP / IMAPS |
| 443 | HTTPS |
| 3306 | MySQL / MariaDB |
